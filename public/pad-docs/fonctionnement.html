    Comment tout fonctionne¶

    Cette page raconte la plateforme de bout en bout : ce que fait task up, ce qui se passe quand un joueur ouvre le site puis lance une instance, quand un manager importe un challenge, comment la plateforme monte en charge, comment elle se surveille et comment elle se protège. Chaque brique citée renvoie vers sa page de la section Composants ; les décisions de fond sont dans les ADR.

    Valeurs d'exemple

    Domaine example.net, plages privées du contrat (10.20.0.0/16), secrets CHANGEME. Les valeurs propres à un hôte réel sont des entrées chiffrées de l'opérateur (Valeurs de site).

    1. Vue d'ensemble¶

    Un seul hôte Proxmox porte tout. Un routeur OPNsense découpe le réseau en sept zones. Les services d'infrastructure (bordure, VPN, bastion, identité, supervision) tournent dans des LXC en Docker Compose, hors du cluster, pour survivre à sa reconstruction. Le cluster Kubernetes pad-prod (Talos, Cluster API) héberge la plateforme et les applications CTF, pilotées par ArgoCD.

    2. task up : de l'hôte vide à la plateforme¶

    task up (Taskfile racine) enchaîne treize étapes idempotentes. Chacune peut être rejouée : on corrige, on relance, et seule la partie manquante bouge. Prérequis : nix develop (Nix), clés age (SOPS), secrets/proxmox.sops.yaml et secrets/site.sops.yaml renseignés.

    flowchart LR
    A[00 réseau hôte] --> B[ansible:host]
    B --> C[10 routeur]
    C --> D[15 image Talos]
    D --> E[60 règles OPNsense]
    E --> F[20 LXC]
    F --> G[ansible:services<br/>passe 1]
    G --> H[30 Authentik]
    H --> H2[oidc-sync, ansible:services<br/>passe 2]
    H2 --> I[bootstrap:cluster]
    I --> J[bootstrap:gitops]
    J --> K[40 NetBird, 50 Warpgate, 70 DNS]
    K --> L[verify]
    # Étape Ce qu'elle crée Brique qui intervient
    1 tofu 00-host-network bridge vmbr2 VLAN-aware sans uplink, bridge de transit vmbr1 (mode NAT), interface vmbr2.10 (IP de l'hôte en zone MGMT) OpenTofu, bpg/proxmox
    2 ansible:host plafond de l'ARC ZFS (4 GiB), sysctl, DNAT de repli, node-exporter, pve-exporter (utilisateur en lecture seule), Alloy Ansible, Proxmox
    3 tofu 10-router VM OPNsense : image nano vérifiée par sha256, ISO de configuration importée au premier boot, VLANs, Unbound, SSH par clé OPNsense
    4 tofu 15-talos-image schematic Image Factory (qemu-guest-agent), image Talos, VM template clonée plus tard par Cluster API Talos
    5 tofu 60-opnsense-rules la matrice de flux : règles « automation » puis blocage final journalisé provider OPNsense, Matrice de flux
    6 tofu 20-services-lxc six LXC Debian 13 non privilégiés (nesting et keyctl) : edge, netbird, warpgate, authentik, monitoring, nbrouter ; génère l'inventaire Ansible bpg/proxmox
    7 ansible:services (passe 1) monitoring, authentik, edge : durcissement, Docker, Alloy, puis le Compose du service Docker, Traefik edge, CrowdSec, Authentik, NetBird, Warpgate
    8 tofu 30-authentik groupes du contrat, providers OAuth2 et applications (un client par brique, secrets générés), flows d'inscription (captcha), MFA du staff, anti-brute-force, forward-auth provider Authentik
    8b oidc-sync, ansible:services (passe 2) recopie des secrets OIDC dans les sops, puis warpgate, netbird et rejeu de monitoring (Grafana) Secrets, NetBird, Warpgate
    9 bootstrap:cluster cluster kind éphémère, Cluster API, pad-prod, Cilium, pivot (clusterctl move), suppression de kind kind, Cluster API, CAPMOX, Cilium
    10 bootstrap:gitops ArgoCD (Helm), Secret sops-age (clé du cluster), Secret du dépôt, Application root ArgoCD, ksops
    11 tofu 40-netbird, 50-warpgate, 70-dns groupes, networks et policies NetBird ; rôles et cibles Warpgate ; enregistrements DNS publics NetBird, Warpgate, OVH
    12 verify smoke tests : endpoints, SSO, ArgoCD, matrice de flux scripts/verify.sh

    Quelques points à retenir :

    • Pourquoi cet ordre. Le routeur et ses règles précèdent les LXC (il faut une passerelle) ; les LXC précèdent Authentik (l'IdP est un LXC) ; le cluster vient après l'identité, car ArgoCD s'y raccorde en OIDC ; NetBird et Warpgate se configurent par API une fois déployés, donc après les LXC.
    • Pourquoi deux passes de services. Les secrets des clients OIDC de NetBird, Warpgate et Grafana sont générés par 30-authentik, qui a besoin d'Authentik et de l'edge. La passe 1 déploie monitoring, Authentik et l'edge ; après 30-authentik, oidc-sync recopie les secrets (chiffrés, jamais affichés) et la passe 2 déploie Warpgate et NetBird. Les certificats ACME de l'edge sont en DNS-01 : ils ne dépendent pas de l'existence des backends. 30-authentik se joue depuis le bastion ou la zone management (la console d'Authentik n'est plus exposée à Internet).
    • Le bootstrap est reprenable. Si le pivot échoue, kind est conservé ; si le pivot a eu lieu, ses étapes sont sautées (Bootstrap).
    • Après le bootstrap, plus de kubectl apply manuel : ArgoCD déroule le contenu de gitops/ par vagues (sync-wave).

    Ce que déroule ArgoCD¶

    flowchart LR
    R[Application root] --> W10[-10 namespaces, CRD Prometheus]
    W10 --> W9[-9 Cilium]
    W9 --> W8[-8 Proxmox CCM<br/>initialise les nœuds]
    W8 --> W7[-7 cert-manager<br/>-6 Kyverno]
    W7 --> W5[-5 ArgoCD, Proxmox CSI<br/>-4 operator MariaDB, politiques, providers CAPI]
    W5 --> W3[-3 Traefik, KEDA, autoscaler, external-dns]
    W3 --> W2[-2 Valkey, Garage, Zot]
    W2 --> W1[-1 Alloy, métriques]
    W1 --> W5b[5 cluster-prod<br/>le cluster se décrit lui-même]
    W5b --> W10b[10 ApplicationSet : CTFd, front,<br/>chall-manager, netbird-sync]

    Les secrets Kubernetes sont à la vague -8 : chiffrés dans le dépôt, déchiffrés par ksops dans le repo-server d'ArgoCD avec la clé age du cluster (qui ne peut jamais lire les secrets d'infrastructure). Détail : Chaîne des secrets.

    La destruction est symétrique : task destroy (confirmation explicite) supprime le cluster (pivot inverse), puis les stacks dans l'ordre inverse ; l'hôte seul reste. task rebuild chronomètre les deux.

    3. Le parcours d'un joueur¶

    3.1 Inscription et connexion¶

    sequenceDiagram
    autonumber
    actor J as Joueur
    participant E as edge (Traefik + CrowdSec)
    participant F as Front Next.js (BFF)
    participant A as Authentik
    participant V as Valkey
    participant C as CTFd (sso_bridge)
    J->>E: HTTPS ctf.example.net
    E->>E: CrowdSec, limite de débit, en-têtes de sécurité
    E->>F: via l'ingress du cluster (HTTP)
    F-->>J: redirection vers auth.example.net
    J->>A: inscription (captcha, e-mail, mot de passe) puis connexion
    A-->>F: code OIDC (PKCE) puis claims : sub, e-mail, groupes ctf-players
    F->>V: token CTFd en cache ?
    alt absent ou expirant
        F->>C: POST /api/v1/sso/session (HMAC, horodatage, nonce)
        C-->>F: token API (TTL 900 s) et profil
        F->>V: stocke le token, verrou de renouvellement
    end
    F-->>J: cookie de session chiffré (aucun token CTFd côté navigateur)
    1. La bordure. Le trafic public arrive sur OPNsense, qui le redirige (ports 80 et 443) vers Traefik edge. Avant tout routage, le plugin bouncer interroge CrowdSec (bannissements, WAF), puis la limitation de débit et les en-têtes de sécurité s'appliquent. Traefik termine le TLS (certificat ACME par DNS-01 chez OVH) et transmet en HTTP à l'ingress du cluster (Traefik cluster, 10.20.60.200).
    2. L'inscription. Elle se passe dans Authentik : flow d'inscription avec captcha, vérification d'e-mail et politique de mot de passe, le compte est créé inactif, activé après vérification de l'e-mail, et placé dans le groupe ctf-players. CTFd n'a aucun formulaire de login (404).
    3. Le front. Auth.js conduit le flux OIDC (PKCE, state, nonce) et garde les claims dans un cookie de session chiffré (12 h).
    4. Le pont vers CTFd. Le BFF signe une requête HMAC vers sso_bridge : CTFd crée ou met à jour l'utilisateur, synchronise ses rôles depuis les groupes, et renvoie un token d'API de 900 s. Le token est partagé entre replicas via Valkey (un verrou évite N appels simultanés). Le navigateur ne le voit jamais.

    3.2 Équipe, challenges, flags¶

    Les écrans d'équipe passent par pad_teams (mots de passe d'équipe protégés contre la force brute). Les challenges, le scoreboard, les indices et les soumissions utilisent l'API native de CTFd, appelée par le BFF avec le token du joueur ; pad_public ajoute l'état de l'événement et les first bloods. Une soumission est un POST /api/v1/challenges/attempt ; le scoreboard en direct est poussé au navigateur par un flux SSE servi par le front. Les fichiers de challenge sont relayés par le BFF (l'URL signée de CTFd n'atteint jamais le navigateur).

    3.3 Lancer une instance et y accéder¶

    sequenceDiagram
    autonumber
    actor J as Joueur
    participant F as Front (BFF)
    participant C as CTFd chall_manager_bridge
    participant M as chall-manager
    participant K as Kubernetes + Cilium
    participant S as netbird-sync
    participant N as NetBird
    J->>F: Lancer l'instance
    F->>C: POST /api/v1/instances/id
    C->>C: équipe, quota (3), cooldown (30 s), pause
    C->>M: crée l'instance (scénario OCI, image, ports, limites, TTL)
    M->>K: scénario Pulumi : namespace inst-team-N, pod, Service LoadBalancer, NetworkPolicy
    K-->>M: IP du pool instances (10.20.70.100-199)
    M-->>C: connection_info et échéance
    C-->>F: 201 Instance
    K-->>S: événement Service (finalizer pad.io/netbird-sync)
    S->>N: groupe ctf-team-N, ressource IP /32, policy groupe vers ressource
    F-->>J: IP, ports, compte à rebours
    J->>N: VPN NetBird connecté
    J->>K: nc 10.20.70.101 1337 via le routing peer
    Note over C,M: À l'échéance (janitor chaque minute) ou sur DELETE : namespace détruit
    K-->>S: Service supprimé
    S->>N: supprime policy et ressource
    • Côté CTFd (chall_manager_bridge) : l'identité transmise est team-<id> (ou user-<id> en mode individuel). Le plugin vérifie l'équipe, le quota, le cooldown, la pause, puis appelle chall-manager. Le flag d'instance n'est jamais renvoyé au front.
    • Côté chall-manager : il télécharge le scénario Pulumi depuis Zot et l'exécute avec un ServiceAccount aux droits limités. Le scénario crée un namespace inst-* en PSS restricted, un pod placé sur le pool challenges (taint, hostUsers: false), un Service LoadBalancer dont l'IP vient du pool instances de Cilium, et une NetworkPolicy default-deny (entrée seulement depuis le routing peer NetBird, aucune sortie, DNS compris : le DNS limité à cluster.local est un opt-in pad.io/dns réservé aux administrateurs). Le scénario refuse toute image hors de registry.pad.internal/ctf/ ou sans empreinte @sha256. Kyverno génère à la création du namespace le default-deny, une ResourceQuota et un LimitRange, et contrôle l'admission du pod (images du registre interne par empreinte, signatures cosign selon le mode pad-image-policy).
    • Côté NetBird : netbird-sync observe le Service, lit le label pad.io/team du namespace, s'assure du groupe ctf-team-<id>, de la ressource /32 de l'instance dans le réseau pad-instances et de la policy qui relie le groupe à cette ressource. Un finalizer garantit que la policy est retirée avant la disparition du Service, et une réconciliation complète a lieu toutes les 10 minutes.
    • Côté joueur : il installe le client NetBird, s'authentifie par Authentik, et atteint l'IP de l'instance via le routing peer situé dans la zone CHALLENGES. Rien n'est exposé à Internet : la zone n'a aucune règle entrante depuis le WAN.

    Appartenance au groupe ctf-team-<id>

    La policy part du groupe NetBird de l'équipe, et c'est netbird-sync qui y rattache les joueurs : il lit les membres de l'équipe dans CTFd (endpoint interne du plugin pad_teams, jeton PAD_INTERNAL_TOKEN), les rapproche des utilisateurs NetBird par e-mail et aligne les pairs du groupe, à chaque instance et toutes les minutes (un joueur qui quitte l'équipe perd l'accès). Il suppose que la policy NetBird Default (tous vers tous) a été supprimée : sinon il refuse de démarrer (voir Actions manuelles). Le front lit en lecture seule l'état NetBird du joueur (connecté, enregistré, absent) pour le guider.

    3.4 Le flag¶

    Le joueur soumet le flag dans le front ; le BFF appelle CTFd, qui score, met à jour le scoreboard et les first bloods. Pour un challenge dynamic_instance, destroy_on_solve peut détruire l'instance. Détails du cycle : Cycle de vie d'une instance et Guide joueur.

    4. Le parcours d'un manager¶

    Un manager (groupe ctf-managers) n'est pas admin CTFd : le plugin manager_api lui donne un périmètre ciblé (import, statistiques, modération, événement).

    sequenceDiagram
    autonumber
    actor M as Manager
    participant F as Front (portail manager)
    participant C as CTFd manager_api
    participant G as Garage (S3)
    participant CM as chall-manager
    participant Z as Zot
    M->>F: dépose un ZIP (challenge.yml + fichiers)
    F->>F: valide la forme et le schéma (JSZip, zod)
    F->>C: POST /api/v1/manager/challenges/import (multipart)
    C->>C: valide à nouveau (schéma JSON), anti zip-bomb et zip-slip, lecture en mémoire
    C->>G: téléverse les fichiers (S3), saute les fichiers inchangés (sha1)
    opt bloc instance dans challenge.yml
        C->>CM: enregistre le scénario du challenge
        CM->>Z: référence OCI du scénario
    end
    C-->>F: created ou updated, type, état (masqué par défaut)
    F-->>M: résultat détaillé
    • Import par ZIP. Création ou mise à jour idempotente, clé = name. Flags, indices et tags sont remplacés. Les fichiers vont dans Garage via le fournisseur d'upload S3 de CTFd. Le challenge reste masqué tant que state: visible n'est pas demandé. Si chall-manager est injoignable (502), rien n'est créé. Le ZIP ne contient pas d'image : celle d'un challenge instancié doit déjà être dans Zot, idéalement signée (cosign). Guide : Import par ZIP.
    • Mode Git. Pour un vrai événement, les challenges vivent dans un dépôt privé séparé ; sa CI valide, construit les images, les pousse dans Zot, les signe, puis synchronise vers CTFd et publie un statut que le portail affiche. Guide : Mode Git.
    • Pendant l'événement. Test d'instance (les managers contournent quota et cooldown), pause et gel du scoreboard, bannissement et invalidation de soumissions, tout journalisé (audit JSON). Voir exploitation d'un événement.

    5. Le scaling¶

    Trois niveaux, du plus rapide au plus lent (Scaling) :

    flowchart LR
    VM[(VictoriaMetrics)] -->|utilisateurs et sessions actifs| KEDA
    KEDA -->|2 à 4 replicas| APP[front, CTFd]
    APP -->|pods Pending| CA[cluster-autoscaler]
    INST[instances en attente] -->|pods Pending| CA
    CA -->|1 à 2 nœuds| MD[MachineDeployment challenges]
    MD --> CAPI[Cluster API + CAPMOX]
    CAPI -->|clone le template Talos| NODE[nouvelle VM worker]
    Q[quotas, cooldown, TTL] -.->|bornent la demande| INST
    1. Pods : KEDA. Un ScaledObject par Deployment, deux déclencheurs : le CPU (70 %) et une métrique métier lue dans VictoriaMetrics (ctfd_active_users, pad_frontend_active_sessions). Agrégation par max() (jamais sum()), car les gauges sont identiques sur chaque pod.
    2. Nœuds : cluster-autoscaler. Quand des pods d'instance restent Pending, il augmente le MachineDeployment du pool challenges (1 à 2 nœuds). CAPMOX clone le template Talos, IPAM donne l'IP statique, CABPT fournit la configuration. Le nœud rejoint le cluster, ses pods démarrent, et il est retiré quand il se vide.
    3. Instances : quotas et TTL. 3 instances par équipe, 30 s entre deux créations, TTL borné, nettoyage par le janitor chaque minute.

    Les tests de charge (k6) servent à valider ces seuils avant un événement.

    • Lecture. Grafana (SSO Authentik) : quatre dashboards versionnés (pad-platform, pad-live-ctf, pad-security, pad-capacity).
    • Alertes. 67 alertes, chacune avec summary, description et un runbook_url vers un runbook. Alertmanager route par gravité et inhibe les cascades.
    • Dead-man's switch. La règle Watchdog est toujours active ; son heartbeat part toutes les 5 minutes vers Uptime Kuma, qui alerte s'il s'arrête. Uptime Kuma publie aussi la page de statut publique.
    • Validation. bash monitoring/scripts/check.sh (promtool, amtool, vmalert, dashboards) et la vérification d'un runbook par alerte tournent en CI. Voir Supervision.

    7. La sécurité en profondeur¶

    Aucune barrière ne suffit seule : chaque couche suppose que la précédente peut céder.

Ils sont rappelés dans les pages concernées.
