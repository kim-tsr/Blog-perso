La sécurité d'un cluster Kubernetes ne s'arrête pas au déploiement. Une fois en production, un container peut être compromis par une vulnérabilité applicative, une image malveillante ou une mauvaise configuration. **Falco** observe le noyau Linux en temps réel et déclenche des alertes dès qu'un comportement sort du cadre attendu. Voyons comment l'intégrer correctement.

## Pourquoi du runtime security ?

Les scanners d'images (Trivy, Grype) attrapent les CVE connues *avant* le déploiement. Mais une fois le pod en exécution, ils ne voient plus rien. Falco comble ce trou : il monitore les **syscalls** du kernel pour détecter, par exemple, un shell qui s'ouvre dans un container ou un binaire qui écrit dans `/etc/passwd`.

> Falco est un projet **CNCF graduated** depuis 2024. C'est aujourd'hui la référence open-source pour la détection runtime sur conteneurs.

## Installer Falco avec eBPF

L'installation via Helm reste la voie la plus propre. On choisit le driver **modern-bpf** qui ne nécessite ni module kernel ni compilation — Falco utilise CO-RE (Compile Once, Run Everywhere) pour s'adapter au kernel cible.

```bash
helm repo add falcosecurity https://falcosecurity.github.io/charts
helm install falco falcosecurity/falco \
  --namespace falco --create-namespace \
  --set driver.kind=modern-bpf \
  --set tty=true \
  --set falcosidekick.enabled=true
```

L'option `falcosidekick.enabled=true` déploie un service qui relaie les alertes vers Slack, Loki, Elasticsearch ou un webhook custom.

## Comprendre les règles

Une règle Falco décrit un comportement *interdit* avec une expression. Le format est lisible :

```yaml
- rule: Shell ouvert dans un container
  desc: Un shell interactif a été lancé dans un container
  condition: >
    spawned_process and container
    and shell_procs and proc.tty != 0
  output: >
    Shell détecté (user=%user.name container=%container.name
    command=%proc.cmdline)
  priority: WARNING
  tags: [shell, mitre_execution]
```

Les **macros** (`spawned_process`, `container`, `shell_procs`) sont définies dans les règles par défaut et permettent de rester concis.

## Écrire une règle personnalisée

Imaginons qu'on veuille alerter dès qu'un binaire **non-prévu** écrit dans un volume persistant monté en `/data` :

```yaml
- macro: app_writes_data
  condition: fd.name startswith /data and evt.type in (open,openat,creat)

- list: trusted_writers
  items: [my-app, postgres, redis-server]

- rule: Écriture suspecte dans /data
  desc: Un binaire non-autorisé écrit dans le volume persistant
  condition: app_writes_data and not proc.name in (trusted_writers)
  output: >
    Écriture suspecte (proc=%proc.name path=%fd.name
    container=%container.name)
  priority: CRITICAL
  tags: [filesystem, supply-chain]
```

## Brancher Falco sur le SIEM

Falcosidekick expose une trentaine de sorties. Pour un stack ELK/Wazuh, on pousse les alertes vers Elasticsearch :

```bash
helm upgrade falco falcosecurity/falco \
  --reuse-values \
  --set falcosidekick.config.elasticsearch.hostport=http://elastic:9200 \
  --set falcosidekick.config.elasticsearch.index=falco-alerts
```

Côté Kibana, on construit un dashboard groupé par `priority`, `container.name` et `mitre_*` pour rapprocher les détections du framework MITRE ATT&CK.

## Pièges fréquents

- **Bruit de fond** — par défaut, Falco peut générer des centaines d'alertes/heure sur un cluster mature. Désactivez les règles non-pertinentes (`Read sensitive file untrusted` est souvent trop bavarde) avant de pousser en prod.
- **kernel headers manquants** — uniquement si vous restez sur le driver `ebpf` legacy. Préférez `modern-bpf`.
- **Cluster managé (EKS/GKE/AKS)** — vérifiez la compatibilité du noyau du nœud avec CO-RE. Bottlerocket, Talos et les AMI récentes sont OK.

## Aller plus loin

Falco ne fait que détecter. Pour **réagir automatiquement** (kill du pod, isolation réseau), on chaîne Falco avec **Falcosidekick → Kubeless / Argo Events / OPA Gatekeeper**. C'est le sujet du prochain article.
