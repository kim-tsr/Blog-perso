## 🧠 Théorie : auditd est le 4ème pilier

Les 3 couches précédentes de la série construisent une défense **préventive** — elles réduisent ce qu'un attaquant peut faire. Mais aucune n'offre la **traçabilité** : quand un incident se produit (et il se produira), tu as besoin de savoir qui a fait quoi, quand et comment.

C'est le rôle d'`auditd` : un framework d'audit **kernel-side** qui capture les événements de sécurité (syscalls, accès fichiers, changements d'identité) à un niveau où aucun attaquant userspace ne peut les éviter ni les altérer.

### Architecture : kernel → auditd → SIEM

Le subsystem `audit` est intégré au kernel depuis Linux 2.6.6. Il s'interpose dans le chemin d'exécution des syscalls et génère des événements pour chaque accès correspondant à une règle active. Ces événements transitent via un socket netlink vers `auditd` en userspace, qui les écrit dans `/var/log/audit/audit.log`.

### Anatomie d'un record audit

Chaque événement audit est un **groupe de records** corrélés par un numéro de séquence (`serial`). Un événement d'accès fichier produit typiquement trois records :

```
type=SYSCALL msg=audit(1709488923.123:42): arch=c000003e syscall=2
  success=yes exit=3 a0=7ffce... a1=0 a2=0 a3=24 items=1 ppid=1234
  pid=5678 auid=1000 uid=0 gid=0 euid=0 suid=0 fsuid=0 egid=0 sgid=0
  fsgid=0 tty=(none) ses=1 comm="cat" exe="/usr/bin/cat"
  subj=unconfined key="watch-shadow"
type=PATH  msg=audit(1709488923.123:42): item=0 name="/etc/shadow"
  inode=12345 dev=fd:00 mode=0100640 ouid=0 ogid=0 rdev=00:00
  obj=system_u:object_r:shadow_t:s0
type=PROCTITLE msg=audit(...): proctitle="cat /etc/shadow"
```

`type=SYSCALL` est le record principal : il contient le numéro de syscall (`syscall=2` = `openat`), les arguments (`a0`-`a3`), le résultat, et les identités du process. `type=PATH` donne le chemin du fichier accédé avec ses métadonnées FS. `type=PROCTITLE` reconstruit la ligne de commande complète.

| Champ | Sens |
|---|---|
| `auid` | **Audit UID** — qui s'est connecté initialement (ne change pas après su/sudo) |
| `uid` | UID effectif courant |
| `ses` | Numéro de session login |
| `comm` | Nom du process (15 chars max, tronqué) |
| `exe` | Chemin absolu du binaire exécuté |
| `subj` | Label MAC (SELinux/AppArmor) |
| `key` | Tag custom de la règle qui a généré cet event |

> `auid` est la clé de l'investigation : un attaquant qui fait `su - root` ou enchaîne plusieurs `sudo` change `uid` à chaque étape, mais `auid` reste celui qui s'est connecté via SSH. Tu retrouves toujours l'origine de la session, même après 5 niveaux de sudo.

## 📋 Étape 1 — État et configuration

```bash
sudo apt install auditd audispd-plugins
sudo systemctl enable --now auditd

sudo auditctl -s
# enabled 1 failure 1 pid 1234 rate_limit 0 backlog_limit 8192 lost 0 ...
```

`auditctl -s` interroge le subsystem audit kernel et retourne : `enabled` (1=actif, 2=immutable), `failure` (mode d'action en cas d'erreur : 0=silent, 1=printk, 2=panic), `backlog_limit` (taille du buffer netlink), `lost` (nombre d'events perdus — doit rester à 0).

Config principale `/etc/audit/auditd.conf` (extraits utiles) :

```
log_file = /var/log/audit/audit.log
max_log_file = 50          # MB
num_logs = 10              # rotate 10
disk_full_action = HALT    # CRITIQUE en compliance
disk_error_action = HALT
```

`disk_full_action = HALT` est une exigence de compliance forte (PCI-DSS, SOX) : si les logs ne peuvent plus être écrits, le système **s'arrête** plutôt que de continuer sans tracer. En environnement non-compliance, tu peux mettre `SYSLOG` pour un comportement moins agressif.

## 📋 Étape 2 — 5 règles ciblées

Crée `/etc/audit/rules.d/dev-sec-ops.rules` :

```
## Vider les règles existantes (au début uniquement)
-D

## Buffers
-b 8192

## Échec → ne pas tomber en panic en lab
-f 1

## ─── R1 — Modifs de comptes (MITRE T1136 Create Account)
-w /etc/passwd        -p wa -k persistence-passwd
-w /etc/shadow        -p wa -k persistence-shadow
-w /etc/group         -p wa -k persistence-group
-w /etc/gshadow       -p wa -k persistence-gshadow
-w /etc/sudoers       -p wa -k privesc-sudoers
-w /etc/sudoers.d/    -p wa -k privesc-sudoers

## ─── R2 — Modifs SSH (MITRE T1098.004 SSH Authorized Keys)
## NB: les watches -w ne supportent PAS les globs (/home/*/.ssh ne marche pas).
## On vise root explicitement ; pour les users, voir la note ci-dessous.
-w /root/.ssh/authorized_keys -p wa -k ssh-auth-root
-w /etc/ssh/sshd_config       -p wa -k ssh-config

## ─── R3 — Modules kernel (MITRE T1547.006 Kernel Modules)
-a always,exit -F arch=b64 -S init_module,finit_module,delete_module
  -k kernel-module

## ─── R4 — Tentatives d'élévation manuelle
-a always,exit -F arch=b64 -S setuid,setgid,setreuid,setregid
  -F auid>=1000 -F auid!=4294967295 -k id-escalation

## ─── R5 — Exécution de binaires depuis /tmp ou /dev/shm
-a always,exit -F arch=b64 -S execve -F dir=/tmp        -k exec-tmp
-a always,exit -F arch=b64 -S execve -F dir=/dev/shm    -k exec-shm

## Verrouille la config (ne peut plus modifier sans REBOOT)
-e 2
```

Les règles `-w` (watch) utilisent des **inode watches** kernel : dès qu'un accès est fait sur cet inode (quelle que soit la méthode), l'event est généré. `-p wa` signifie : watcher les permissions `write` et `attribute change`. `-k tag` associe un tag arbitraire.

> ⚠️ Un watch `-w` ne supporte **pas** les wildcards : `-w /home/*/.ssh/authorized_keys` ne matche rien. Pour couvrir tous les users, génère une ligne par compte au boot — ex. dans le `.rules` via un script qui itère sur `/home/*` :
> ```bash
> for d in /home/*; do
>   auditctl -w "$d/.ssh/authorized_keys" -p wa -k ssh-auth-user
> done
> ```
> L'alternative scalable est une **règle syscall** large sur `openat` filtrée côté SIEM par nom de fichier (`name=authorized_keys`), au prix de plus de bruit à corréler.

Les règles `-a always,exit` sont des règles de syscall : elles s'appliquent à chaque `exit` du syscall spécifié. `-F arch=b64` filtre sur l'ABI 64-bit (sans cela, tu rates les appels 32-bit sur un kernel 64-bit). `-F auid>=1000` filtre sur les utilisateurs normaux (UIDs ≥ 1000, donc pas les comptes système). `-F auid!=4294967295` exclut les processes sans login session (`4294967295` = `(unsigned)-1` = la valeur `unset` de l'auid, souvent notée `-1` ou `4294967295` dans les logs).

> 💡 `-F dir=/tmp` filtre sur le **préfixe du chemin** de l'objet manipulé par le syscall (ici l'exécutable d'`execve`) : tout objet sous `/tmp/...` matche. À distinguer de `-F path=/tmp/x` qui n'observe qu'un fichier précis (via inode watch). Risque si tu confonds : `path=` sur un fichier inexistant ne matche jamais ; `dir=` couvre toute l'arborescence. Note aussi que `comm` est tronqué à 15 caractères dans chaque record — pour l'attribution fiable, base-toi sur `exe=` (chemin complet) et non `comm=`.

```bash
sudo augenrules --load
sudo auditctl -l
```

`augenrules --load` compile tous les fichiers `*.rules` de `/etc/audit/rules.d/` et les charge atomiquement. `auditctl -l` vérifie les règles actives dans le kernel.

> ⚠️ Le `-e 2` à la fin verrouille le système d'audit — tu ne peux plus modifier les règles sans REBOOT. Très bon en prod, pénible en lab. Mets `-e 1` pendant les tests.

## 📋 Étape 3 — Simuler chaque déclencheur

### R1 — Création d'utilisateur

```bash
sudo useradd attacker
sudo ausearch -k persistence-passwd -ts recent
# → SYSCALL openat sur /etc/passwd, write, par useradd
```

`useradd` appelle `openat(/etc/passwd, O_WRONLY|O_CREAT|...)` et `write()` — la watch `-w /etc/passwd -p wa` génère un event. `ausearch -k persistence-passwd -ts recent` filtre sur le tag et les 10 dernières minutes.

### R3 — Charger un module

```bash
sudo modprobe overlay   # déjà chargé sans doute, mais OK
sudo ausearch -k kernel-module -ts recent
```

`modprobe` appelle `finit_module()` — la règle `-S init_module,finit_module,delete_module` capture cet appel. C'est une règle critique : le chargement d'un module kernel est une technique de persistance furtive (rootkit, keylogger kernel).

### R4 — Élévation manuelle

```bash
# Crée un binaire suid de test
cat > /tmp/elev.c <<'EOF'
#include <unistd.h>
int main() { setuid(0); execl("/bin/sh","sh",NULL); }
EOF
gcc /tmp/elev.c -o /tmp/elev
sudo chown root:root /tmp/elev
sudo chmod 4755 /tmp/elev
/tmp/elev    # → si DAC autorise, on devient root

sudo ausearch -k id-escalation -ts recent
```

Le binaire `setuid` appelle `setuid(0)` en UID utilisateur — la règle `-S setuid -F auid>=1000` capture ce pattern d'escalade de privilèges. En plus, l'exécution depuis `/tmp` déclenche R5.

### R5 — Exec depuis /tmp

```bash
echo -e '#!/bin/sh\necho pwned' > /tmp/p.sh
chmod +x /tmp/p.sh
/tmp/p.sh

sudo ausearch -k exec-tmp -ts recent
# → SYSCALL execve, name=/tmp/p.sh, comm="p.sh"
```

`execve()` depuis `/tmp` ou `/dev/shm` est un pattern d'exécution malveillante classique : l'attaquant upload un script et l'exécute depuis un répertoire monde-inscriptible. Cette règle capture systématiquement ce pattern.

## 📋 Étape 4 — Investigation avec ausearch / aureport

### Recherche par key

```bash
sudo ausearch -k persistence-passwd
```

### Recherche par utilisateur (auid)

```bash
sudo ausearch -ua 1000 --start today
```

`-ua 1000` filtre sur l'`auid` (audit UID de connexion) — même si l'utilisateur a fait `sudo su -`, son `auid` reste 1000. C'est la puissance du champ `auid` vs `uid` pour l'attribution.

### Recherche par fichier touché

```bash
sudo ausearch -f /etc/shadow
```

### Stats globales

```bash
sudo aureport --summary
sudo aureport --auth          # tentatives d'auth
sudo aureport --file          # accès fichiers les + chauds
sudo aureport --executable    # binaires exécutés
```

`aureport` est le compagnon d'`ausearch` pour les vues agrégées. `--auth` montre toutes les tentatives d'authentification (SSH, sudo, PAM) — utile pour détecter un brute-force. `--executable` liste tous les binaires exécutés sur la machine — utile pour détecter un binaire inconnu.

### Format JSON pour SIEM

```bash
sudo ausearch -k id-escalation --format json | jq
```

Le format JSON d'`ausearch` (disponible depuis audit-userspace 3.0, présent sur Debian 12 / Ubuntu 22.04+) facilite l'ingestion dans un SIEM. Chaque event devient un objet JSON avec tous les champs structurés — prêt pour Elastic, Loki ou Wazuh. Sur une version plus ancienne, utilise `ausearch --format csv` ou le plugin `au-remote`.

## 📋 Étape 5 — Forward vers SIEM (Wazuh / Loki / syslog)

`/etc/audit/plugins.d/syslog.conf` :

```
active = yes
direction = out
path = builtin_syslog
type = builtin
args = LOG_INFO
format = string
```

Le plugin `syslog` (via `audispd`) relaie chaque event vers syslog. De là, `rsyslog` ou `journald` peuvent les forward vers Loki, Wazuh ou Elastic. Pour Wazuh : le manager a déjà des décodeurs pour `type=SYSCALL` et `type=USER_AUTH`. Tu obtiens des règles 80790 et amis qui trigerent automatiquement.

## 📋 Étape 6 — Mapping MITRE pour ton SOC

| Règle | TTP MITRE | Tactique | Réponse type |
|---|---|---|---|
| `persistence-passwd/shadow` | T1136 Create Account | Persistence | Vérifier diff /etc/passwd, alerter SOC |
| `privesc-sudoers` | T1548.003 Sudo Caching | Priv Escalation | Diff /etc/sudoers.d/, rollback git |
| `ssh-auth-root/user` + `ssh-config` | T1098.004 SSH Keys | Persistence | Vérifier clé/config, identifier owner, révoquer |
| `kernel-module` | T1547.006 Kernel Modules | Persistence | rkhunter, chkrootkit, IR mode |
| `id-escalation` | T1548 Abuse Elevation | Priv Escalation | corréler avec exec-tmp pour pattern complet |
| `exec-tmp/shm` | T1059 Command Execution | Execution | quarantine /tmp, image bootkit ? |

## 🧠 Pitfalls

❌ **Activer audit sans rate-limit en prod** : sur un serveur DB, syscalls = millions/s → log saturé → events perdus.
❌ **Watcher tout `/etc`** : trop large, plein de bruit (mtime, mount/umount).
❌ **Oublier la rotation** : audit.log grossit jusqu'à remplir / → kernel panic possible avec disk_full_action=HALT.
❌ **Ne pas tester `-e 2`** : tu te retrouves verrouillé après un reboot.
❌ **Mélanger règles d'arch x86_64 et i386** sans `-F arch=` explicite : tu rates la moitié des events.
