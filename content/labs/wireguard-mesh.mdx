## 🧠 Théorie : WireGuard, le VPN qui tient en 4000 lignes

WireGuard est un protocole VPN moderne, intégré au kernel Linux depuis 5.6 (2020). Ses choix de design tranchent avec OpenVPN/IPsec :

```
   OpenVPN                            WireGuard
   ─────────────                      ─────────────
   ~600 000 LOC (incl. OpenSSL)      ~4 000 LOC
   N algos cryptos négociés           1 algo fixé pour chaque rôle
   TCP ou UDP                         UDP only
   État connexion riche               Stateless (handshake éphémère)
   PKI X.509 (CA, certs, CRL)         Échange de clés publiques
   Démarre lent (~1s handshake)       Démarre instantané (~1 RTT)
```

### Cryptographie utilisée (toutes fixées, pas de négociation)

| Rôle | Algorithme |
|---|---|
| Échange de clés | Curve25519 (ECDH) |
| Chiffrement symétrique | ChaCha20 |
| Authentification message | Poly1305 |
| Hashing | BLAKE2s |
| HKDF | BLAKE2s |
| Anti-DoS | SipHash24 |

Pas de négociation = pas de downgrade attack. Si un algo casse demain, on bump le protocole. Simple, brutal, sûr.

### Topologie : full-mesh vs hub-and-spoke

```
   Full-mesh                       Hub-and-spoke
   ─────────                       ──────────────
        N1                              N1
       /  \                              │
      /    \                             │
    N2 ──── N3                  N2 ──── HUB ──── N3
                                       (SPOF)
   
   3 peers/nœud                    1 peer/nœud (spoke)
   Latence directe                 +1 hop systématique
   Résilient                       Hub down = mesh KO
   Config O(N²)                    Config O(N)
```

Pour 3-10 nœuds : full-mesh. Au-delà : hub-and-spoke avec multiple hubs (mode Tailscale DERP) ou orchestration (Headscale).

## 🎯 Objectif

Établir un **mesh** WireGuard où chaque nœud parle directement à chaque autre — pas de point central. Idéal pour un homelab distribué ou un cluster Kubernetes multi-site.

## 📐 Architecture cible

```
            Internet
       ┌────────┴────────┐
       │        │        │
       ▼        ▼        ▼
      N1       N2       N3
   10.50.0.1  .0.2   .0.3
       ▲        ▲        ▲
       └────────┼────────┘
                │
   Chaque flèche = tunnel WG chiffré bout-en-bout
   Pas de centralisation, pas de SPOF
```

## 📋 Étape 1 — Générer les paires de clés

Sur chaque nœud (N1, N2, N3) :

```bash
sudo apt install -y wireguard
wg genkey | tee privatekey | wg pubkey > publickey
cat privatekey publickey
```

Notez les 3 clés publiques — vous en aurez besoin sur tous les nœuds.

> 💡 La clé privée doit rester sur la machine qui la possède. La clé publique est partageable sans risque.

## 📋 Étape 2 — Configurer N1

`/etc/wireguard/wg0.conf` sur N1 :

```ini
[Interface]
PrivateKey = <PRIV_N1>
Address    = 10.50.0.1/24
ListenPort = 51820

[Peer]
# N2
PublicKey  = <PUB_N2>
AllowedIPs = 10.50.0.2/32
Endpoint   = <IP_PUB_N2>:51820
PersistentKeepalive = 25

[Peer]
# N3
PublicKey  = <PUB_N3>
AllowedIPs = 10.50.0.3/32
Endpoint   = <IP_PUB_N3>:51820
PersistentKeepalive = 25
```

Sur **chaque** autre nœud, créez un fichier équivalent avec son IP interne et les peers correspondants.

> 💡 La clé d'un mesh : **chaque** nœud doit avoir **N-1** peers déclarés. Pas de hiérarchie.

### Comprendre AllowedIPs

`AllowedIPs = 10.50.0.2/32` côté N1 pour N2 signifie :
- **Sortant** : tout paquet vers 10.50.0.2 part dans ce tunnel
- **Entrant** : tout paquet déchiffré de ce peer DOIT venir de 10.50.0.2, sinon jeté

Si vous voulez router un sous-réseau entier via N2 (ex: 192.168.10.0/24 derrière N2) :
```ini
AllowedIPs = 10.50.0.2/32, 192.168.10.0/24
```

## 📋 Étape 3 — Démarrer le tunnel

Sur les 3 nœuds :

```bash
sudo wg-quick up wg0
sudo systemctl enable wg-quick@wg0
```

Ouvrez le port UDP 51820 dans le firewall :

```bash
sudo ufw allow 51820/udp
```

## 📋 Étape 4 — Tester

Depuis N1 :

```bash
ping -c 3 10.50.0.2
ping -c 3 10.50.0.3
sudo wg show
```

`wg show` doit lister les 2 peers avec un `latest handshake` récent et du trafic dans `transfer`.

### Anatomie de wg show

```
peer: ABcd...PUB_N2
  endpoint: 203.0.113.2:51820
  allowed ips: 10.50.0.2/32
  latest handshake: 1 minute, 22 seconds ago    ← < 3 min = sain
  transfer: 4.2 KiB received, 5.1 KiB sent       ← trafic réel
  persistent keepalive: every 25 seconds
```

## 📋 Étape 5 — Test de résilience

Coupez WireGuard sur N1, puis testez depuis N2 vers N3 :

```bash
# Sur N2
ping 10.50.0.3
```

Ça doit fonctionner — c'est tout l'intérêt du mesh par rapport à un hub-and-spoke.

## 📋 Étape 6 — Mesure de perf

```bash
# Sur N3 : démarrer iperf3
iperf3 -s

# Sur N1 : benchmark via le tunnel
iperf3 -c 10.50.0.3 -t 30
```

Vous devriez avoir **~95% du débit hors tunnel**. ChaCha20 est optimisé pour les CPU modernes, l'overhead est minime même sans AES-NI.

## 🧠 Pitfalls courants

❌ **Oublier `PersistentKeepalive` derrière NAT** : le mapping NAT meurt, le peer devient injoignable depuis dehors.
❌ **`AllowedIPs = 0.0.0.0/0` sur tous les peers** : conflit de routage, un seul peer "gagne".
❌ **Même `ListenPort` sur des peers derrière le même NAT** : conflit de port forwarding.
❌ **Activer `wg-quick` sans `systemctl enable`** : reboot = tunnel down.
❌ **Pas de monitoring** : un handshake qui ne se refait pas pendant 1h doit alerter.

## ✅ Validation

- 3 handshakes établis sur chaque nœud
- Ping bi-directionnel entre tous les couples
- N2 ↔ N3 fonctionne même quand N1 est down
- iperf3 montre ~95% du débit réseau hors tunnel
