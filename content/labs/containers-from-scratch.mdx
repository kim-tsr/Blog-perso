## 🧠 Théorie : un container n'est PAS une VM

Premier malentendu à dissiper :

```
   Virtual Machine (KVM, VMware)        Container (Docker, containerd)

   ┌──────────────────┐                ┌──────────────────┐
   │  App             │                │  App             │
   ├──────────────────┤                ├──────────────────┤
   │  Bins / Libs     │                │  Bins / Libs     │
   ├──────────────────┤                ├──────────────────┤
   │  Guest OS        │                │  (PAS de guest OS)│
   │  + Kernel        │                │   - utilise le   │
   ├──────────────────┤                │   kernel HÔTE    │
   │  Hypervisor      │                ├──────────────────┤
   ├──────────────────┤                │  Container runtime│
   │  Host OS         │                ├──────────────────┤
   ├──────────────────┤                │  Host OS         │
   │  Hardware        │                ├──────────────────┤
   └──────────────────┘                │  Hardware        │
                                       └──────────────────┘

   Isolation : kernel séparé           Isolation : namespaces + cgroups
   Boot      : 30s+                    Boot      : ms
   Footprint : 500MB+                  Footprint : qq MB
   Sécurité  : forte (hyperviseur)     Sécurité  : kernel partagé = surface
```

### Les ingrédients d'un container

Un container = **6 namespaces** + **cgroups** + **rootfs séparé** + **capabilities/seccomp**.

| Composant | Rôle |
|---|---|
| `PID ns` | Isolation des processus (PID 1 séparé) |
| `Network ns` | Interfaces, routes, iptables séparés |
| `Mount ns` | Vue du FS séparée |
| `UTS ns` | hostname séparé |
| `IPC ns` | shm, semaphores séparés |
| `User ns` | UID/GID mappés (root container ≠ root hôte) |
| `cgroups` | Limites CPU, RAM, IO, devices |
| `chroot/pivot_root` | Racine FS différente |
| `capabilities` | Subset des droits root (drop NET_ADMIN, etc.) |
| `seccomp` | Whitelist des syscalls autorisés |

## 🎯 Objectif

Construire un "container" à la main, sans Docker, en assemblant ces primitives une à une. À la fin tu :
- Auras créé un mini rootfs Debian via `debootstrap`
- Auras lancé `bash` dedans avec PID, network, mount namespaces séparés
- Auras limité la RAM et le CPU via cgroups v2
- Pourras observer la différence depuis l'hôte avec `ps`, `nsenter`

## 📋 Étape 1 — Créer un rootfs minimal

```bash
sudo apt install -y debootstrap

mkdir -p /tmp/mycontainer
sudo debootstrap --variant=minbase bookworm /tmp/mycontainer http://deb.debian.org/debian

ls /tmp/mycontainer
# bin etc lib usr var ... — un système Debian minimal
```

## 📋 Étape 2 — Premier "container" avec unshare

```bash
sudo unshare \
  --pid --net --mount --uts --ipc --fork \
  --mount-proc \
  chroot /tmp/mycontainer /bin/bash
```

Tu es dans un shell où :

```bash
hostname           # → un hostname séparé (peut être changé)
ps -ef             # → seulement le PID 1 (ton bash) et le ps lui-même
ip addr            # → seulement loopback (network namespace vide)
ls /               # → rootfs Debian
exit
```

Vu depuis l'hôte (autre terminal) :

```bash
ps -ef | grep bash
# → ton bash apparaît avec un PID normal (ex: 12345)
ls /proc/12345/ns/
# → tu vois les liens vers les namespaces (pid, net, mnt, uts, ipc)
```

## 📋 Étape 3 — Limiter avec cgroups v2

```bash
# Crée un cgroup
sudo mkdir /sys/fs/cgroup/mycontainer

# Limite à 100 Mo de RAM
echo "100M" | sudo tee /sys/fs/cgroup/mycontainer/memory.max

# Limite à 20% d'un CPU
echo "20000 100000" | sudo tee /sys/fs/cgroup/mycontainer/cpu.max
# Format : "quota period" en microsecondes → 20ms toutes les 100ms = 20%

# Lance ton "container" en y attachant le shell
sudo unshare --pid --net --mount --uts --ipc --fork --mount-proc \
  chroot /tmp/mycontainer /bin/bash &

PID=$!
echo $PID | sudo tee /sys/fs/cgroup/mycontainer/cgroup.procs
```

Test la limite mémoire :

```bash
# Dans le container, tente d'allouer 200 Mo
apt install -y stress-ng
stress-ng --vm 1 --vm-bytes 200M
# → killed par OOM (cgroup limit)
```

## 📋 Étape 4 — Sécurité : drop des capabilities

Par défaut, root dans un container avec juste namespaces est… root sur l'hôte (presque). Pour vraiment isoler, on doit drop les capabilities dangereuses :

```bash
sudo apt install -y libcap2-bin

# Lance avec capabilities minimales
sudo capsh \
  --drop=cap_sys_admin,cap_net_admin,cap_sys_module,cap_sys_rawio,cap_sys_time \
  -- -c "exec unshare --pid --net --mount --uts --ipc --fork --mount-proc \
         chroot /tmp/mycontainer /bin/bash"
```

Maintenant `mount` interne échoue, `iptables` aussi — la surface d'attaque est réduite.

## 🧠 Ce que Docker ajoute par-dessus

Tout ce qu'on vient de faire à la main, Docker l'orchestre :

```
   docker run -m 100m --cpus 0.2 ubuntu bash

   ↓ sous le capot

   1. Image fetch (rootfs)
   2. clone() avec flags CLONE_NEWPID|CLONE_NEWNET|CLONE_NEWNS|...
   3. mkdir + write cgroup limits
   4. seccomp profile (default filter)
   5. capabilities drop (defaults)
   6. pivot_root + exec
```

C'est ça la "magie" Docker : un wrapper ergonomique autour de ces syscalls. Quand tu sais ce qu'il fait, debugger Kubernetes devient infiniment plus simple.

## ✅ Validation

- Tu peux entrer/sortir de ton container manuel via `unshare`
- `ps` dedans ne voit que les processes du container
- `stress-ng --vm-bytes 200M` est tué par OOM (limite cgroup respectée)
- Tu peux lister les namespaces depuis l'hôte via `/proc/PID/ns/`

## 🚀 Pour aller plus loin

- **runc** : implémente la spec OCI au-dessus de ces primitives — c'est le runtime qu'utilisent Docker, containerd, k3s
- **gVisor** : user-space kernel qui intercepte les syscalls pour fournir une isolation plus forte (au prix de la perf)
- **Kata Containers** : un container == une micro-VM (hyperviseur léger), pour quand tu ne fais pas confiance à la charge
