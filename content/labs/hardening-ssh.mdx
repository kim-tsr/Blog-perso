## 🧠 Théorie : pourquoi SSH est la première cible

Tout serveur public sur Internet voit en quelques minutes des milliers de tentatives de login sur le port 22. C'est un bruit de fond constant alimenté par des botnets (Mirai-like, mass scanners). Sans hardening :

- **MaxAuthTries** par défaut = 6 → ~6 essais de password par connexion
- **PermitRootLogin yes** par défaut sur certains AMI → cible idéale (compte connu, droits illimités)
- **PasswordAuthentication yes** → si un user a un mot de passe faible, c'est perdu

### Modèle de menace SSH

```
   Internet ─► port 22 ─► sshd
                            │
       ┌────────────────────┼────────────────────┐
       ▼                    ▼                    ▼
   Brute force          Vol de clé           0day sshd
   (password)           (~/.ssh/id_rsa       (rare mais
       │                 exposé)              critique)
       ▼                    ▼                    ▼
   fail2ban             Passphrase           Patch rapide
   no-passwords         + agent              minimiser surface
```

### Comparaison clés vs passwords

| Aspect | Password 12 caractères | Clé Ed25519 |
|---|---|---|
| Entropie max | ~78 bits (alphanum+sym) | 256 bits |
| Brute force réaliste | ~10^15 ops (faisable) | impossible (10^77) |
| Volabilité | shoulder surf, keylogger | fichier sur disque (chiffrable) |
| Rotation | manuelle, friction | scriptable |

## 🎯 Objectif

Transformer un SSH ouvert à tous les vents en un service durci : clés uniquement, MFA optionnelle, bannissement des bots, audit cryptographique.

## 📋 Étape 1 — Générer et déployer une clé Ed25519

Sur votre poste :

```bash
ssh-keygen -t ed25519 -C "kim@laptop"
ssh-copy-id user@serveur
```

Testez : `ssh user@serveur` doit fonctionner **sans mot de passe**.

> 💡 Toujours mettre une **passphrase** sur la clé privée + utiliser `ssh-agent` pour ne la taper qu'une fois par session.

## 📋 Étape 2 — Durcir sshd_config

Éditez `/etc/ssh/sshd_config` :

```text
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
KbdInteractiveAuthentication no
ChallengeResponseAuthentication no
AllowUsers kim
MaxAuthTries 3
LoginGraceTime 20
ClientAliveInterval 300
ClientAliveCountMax 2
Protocol 2
X11Forwarding no
AllowTcpForwarding no
PermitTunnel no
```

> 💡 Gardez une seconde session SSH ouverte avant de redémarrer le service — c'est votre filet de sécurité si la config est mauvaise.

```bash
sudo sshd -t   # valide la syntaxe
sudo systemctl restart ssh
```

### Anatomie de chaque directive

```
PermitRootLogin no         ─► Pas de login direct root, on passe par sudo
PasswordAuthentication no  ─► Clés uniquement = élimine 90% du bruit
AllowUsers kim             ─► Whitelist explicite
MaxAuthTries 3             ─► Limite essais/connexion
LoginGraceTime 20          ─► Connexion non terminée en 20s = close
ClientAliveInterval 300    ─► Détecte sessions zombies (NAT drop)
```

## 📋 Étape 3 — Installer fail2ban

```bash
sudo apt install -y fail2ban
sudo tee /etc/fail2ban/jail.d/ssh.local <<EOF
[sshd]
enabled = true
port    = ssh
maxretry = 4
bantime  = 1h
findtime = 10m
EOF
sudo systemctl restart fail2ban
sudo fail2ban-client status sshd
```

### Tester le banissement

Depuis une autre machine, faites volontairement 5 tentatives échouées :

```bash
for i in {1..5}; do ssh notexist@serveur; done
# Puis sur le serveur :
sudo fail2ban-client status sshd
# Banned IP list: 1.2.3.4
```

## 📋 Étape 4 — Auditer la cryptographie

```bash
pip install --user ssh-audit
~/.local/bin/ssh-audit serveur
```

L'outil note les algorithmes de chiffrement, MAC et KEX. Visez **A** ou **A+**. Désactivez les algorithmes faibles dans `sshd_config` :

```text
KexAlgorithms curve25519-sha256,curve25519-sha256@libssh.org
Ciphers chacha20-poly1305@openssh.com,aes256-gcm@openssh.com
MACs hmac-sha2-512-etm@openssh.com,hmac-sha2-256-etm@openssh.com
HostKeyAlgorithms ssh-ed25519,rsa-sha2-512
```

> ⚠️ Ces algorithmes excluent les vieux clients (OpenSSH < 6.5). Vérifie que tes scripts CI les supportent.

## 📋 Étape 5 — Bonus : 2FA TOTP

```bash
sudo apt install libpam-google-authenticator
google-authenticator   # en tant que user, génère le QR code
```

Ajoutez dans `/etc/pam.d/sshd` :

```
auth required pam_google_authenticator.so
```

Et dans `sshd_config` :

```
AuthenticationMethods publickey,keyboard-interactive
```

Désormais : clé SSH **+** code TOTP requis.

## 🧠 Anti-patterns

❌ **Changer le port (security through obscurity)** : ne ralentit que les scans naïfs. Les scanners Shodan trouvent tous les ports.
❌ **Mettre `PermitRootLogin without-password`** : oui c'est mieux que `yes`, mais `no` est meilleur — root devrait être inutilisable directement.
❌ **Laisser DSA / RSA 1024** : cassés cryptographiquement. ssh-audit le signale.
❌ **fail2ban sans persistance** : à chaque reboot le compteur reset → l'attaquant a un free pass.

## ✅ Validation

- `ssh root@serveur` → refusé
- `ssh user@serveur` avec mot de passe → refusé
- ssh-audit retourne **A**
- 5 tentatives échouées → IP bannie 1 h
- 2FA active : clé + TOTP demandés

## 🚀 Pour aller plus loin

- Ajoutez **TOTP** avec `libpam-google-authenticator` (déjà fait dans le bonus)
- Limitez l'accès SSH à un VPN WireGuard (voir le lab dédié)
- Centralisez les logs `auth.log` vers votre SIEM (cf. série API logs)
- Utilisez un **bastion SSH** unique (Teleport, Boundary) pour tout accès prod
