quiz:
  - question: "Quelle est la différence entre une approche 'prévention' (NetworkPolicies, OPA) et 'détection' (Falco) ?"
    options:
      - "La prévention est inutile si on a de la détection"
      - "Prévention = on bloque AVANT que ça arrive (refuse une connexion, un déploiement). Détection = on observe APRÈS et on alerte. Les deux sont complémentaires (defense in depth)"
      - "La détection est plus rapide que la prévention"
      - "Ce sont des synonymes"
    correct: 1
    explanation: "Defense in depth : prévention bloque les attaques connues, détection attrape ce qui passe (zero-day, abus de privilèges légitimes). Falco détecte un shell dans un container alors qu'aucune policy ne l'interdisait formellement."
  - question: "Pourquoi Falco utilise eBPF plutôt que des appels syscall classiques ?"
    options:
      - "eBPF est obligatoire pour Kubernetes"
      - "eBPF permet d'observer TOUS les syscalls de TOUS les processus depuis le kernel, sans modifier les apps ni causer d'overhead majeur"
      - "eBPF est plus simple à coder"
      - "eBPF chiffre les syscalls"
    correct: 1
    explanation: "Falco attache un programme eBPF aux tracepoints syscall du kernel. Il voit chaque exec, open, connect — sans patcher les apps, sans sidecar. Avec un driver kernel module legacy, c'est moins portable ; avec eBPF CO-RE moderne, ça marche partout."
  - question: "Une règle Falco condition: 'spawned_process and container and shell_procs' surveille quoi ?"
    options:
      - "Tous les processus dans le cluster"
      - "Uniquement les démarrages de shells (sh, bash, zsh) dans un container — un signal fort de compromission"
      - "Les redémarrages de pods"
      - "Les connexions SSH"
    correct: 1
    explanation: "Un shell interactif dans un container de production n'a quasi jamais lieu en utilisation normale. C'est typiquement un attaquant qui exec après une RCE, ou un dev qui kubectl exec pour debug. Falco alerte sur les deux — à toi de filtrer."
  - question: "Pourquoi une 'default-deny ingress' NetworkPolicy est la première étape du zero trust ?"
    options:
      - "Pour économiser de la bande passante"
      - "Par défaut sans policy, tout est autorisé entre pods d'un même namespace. Default-deny inverse la logique : rien n'est autorisé sauf ce qu'on liste explicitement"
      - "C'est obligatoire pour Kubernetes"
      - "Default-deny rend le cluster plus rapide"
    correct: 1
    explanation: "Kubernetes par défaut est un VPC plat — tout pod parle à tout pod. C'est l'opposé de zero trust. Une policy default-deny pose la première brique : chaque flux doit être explicitement justifié via une autre policy."
  - question: "Quel intérêt de connecter Falcosidekick à Alertmanager (Lab #4) plutôt qu'à Slack directement ?"
    options:
      - "Slack est moins fiable"
      - "Centraliser dans Alertmanager : tu as la même UX (silences, grouping, escalation) pour les alertes infra ET sécurité, et un seul endpoint à protéger"
      - "Pour économiser de l'argent"
      - "Falcosidekick ne supporte pas Slack"
    correct: 1
    explanation: "Plus tu fragmente tes systèmes d'alertes, plus tu rates des choses. Tout passer par Alertmanager te donne : silences pendant maintenance, dédup, routage par sévérité, et un audit centralisé. C'est la convergence Ops + Sec."

## 📋 Étape 1 — Falco via ArgoCD

Dans `homelab-gitops/infra/security/falco.yaml` :

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: falco
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://falcosecurity.github.io/charts
    chart: falco
    targetRevision: 4.8.0
    helm:
      values: |
        driver:
          kind: modern-bpf
        tty: true
        falcosidekick:
          enabled: true
          config:
            alertmanager:
              hostport: http://kube-prometheus-stack-alertmanager.monitoring:9093
        falco:
          json_output: true
          json_include_output_property: true
  destination:
    server: https://kubernetes.default.svc
    namespace: falco
  syncPolicy:
    automated: { prune: true, selfHeal: true }
    syncOptions: [ CreateNamespace=true ]
```

Commit + push. ArgoCD déploie Falco + Falcosidekick. Vérifie :

```bash
kubectl -n falco get pods
# falco-xxxxx       Running
# falco-falcosidekick-xxxx   Running
```

## 📋 Étape 2 — Tester la détection

Lance un shell dans un container — c'est ce qu'un attaquant ferait après une RCE :

```bash
kubectl -n demo exec -it deployment/whoami -- sh
exit
```

Regarde les logs Falco :

```bash
kubectl -n falco logs -l app.kubernetes.io/name=falco --tail=20 | grep -i shell
```

Tu verras quelque chose comme :

```
Notice A shell was spawned in a container (user=root container=whoami...)
```

→ Dans Alertmanager (Grafana → Alertmanager UI ou directement http://192.168.1.20:30093) tu vois l'alerte arriver.

## 📋 Étape 3 — Règle Falco personnalisée

Ajoute une règle qui surveille l'écriture dans `/etc` :

```yaml
# homelab-gitops/infra/security/falco-custom-rules.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: falco-rules
  namespace: falco
data:
  custom-rules.yaml: |
    - rule: Write below /etc
      desc: Un binaire écrit sous /etc (modif suspecte de config)
      condition: >
        evt.dir=< and open_write
        and fd.name startswith /etc
        and not user.name in (root)
        and container
      output: >
        Écriture /etc (user=%user.name container=%container.name
        path=%fd.name proc=%proc.cmdline)
      priority: WARNING
      tags: [filesystem, persistence]
```

Commit + push. Test :

```bash
kubectl -n demo exec deployment/whoami -- sh -c "echo test > /etc/test 2>&1 || true"
```

L'alerte tombe.

## 📋 Étape 4 — Zero Trust NetworkPolicies

Crée une policy `default-deny` sur `demo` (ajoute à `homelab-gitops/apps/whoami/`) :

```yaml
# default-deny-ingress.yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: demo
spec:
  podSelector: {}
  policyTypes: [ Ingress ]

---
# allow-whoami-from-monitoring.yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: allow-monitoring
  namespace: demo
spec:
  endpointSelector:
    matchLabels: { app: whoami }
  ingress:
    - fromEndpoints:
        - matchLabels:
            io.kubernetes.pod.namespace: monitoring
      toPorts:
        - ports: [{ port: "80", protocol: TCP }]
```

Commit + push. Vérifie dans Hubble UI (Lab #2) que les flux sont bien filtrés.

## 📋 Étape 5 — Active response (optionnel mais badass)

Configure Falcosidekick pour déclencher un kill-pod sur alerte CRITICAL :

```yaml
# Ajout dans le values de l'app falco
falcosidekick:
  config:
    webhook:
      address: http://kube-killer.security:8080/kill
      minimumpriority: critical
```

(Tu peux écrire un petit service `kube-killer` qui supprime le pod incriminé — la base d'un SOAR maison).
