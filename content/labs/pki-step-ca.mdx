## 🧠 Théorie : qu'est-ce qu'une PKI exactement ?

PKI (**Public Key Infrastructure**) = l'ensemble des composants qui permettent de **distribuer la confiance** via la cryptographie asymétrique. Sans PKI, chaque service devrait vérifier individuellement chaque autre — ingérable. La PKI résout le problème fondamental de la cryptographie à clé publique : comment savoir que la clé publique que vous venez de recevoir appartient vraiment à qui vous croyez ?

La réponse est la **signature de certificat** : une tierce partie de confiance (la Certificate Authority) appose sa signature cryptographique sur votre clé publique, en attestant votre identité. Si vous faites confiance à la CA, vous faites transitivement confiance à tous les certificats qu'elle a signés. C'est la chaîne de confiance.

Dans l'Internet public, une dizaine de CAs racines (DigiCert, Let's Encrypt, Sectigo...) sont pré-installées dans les OS et navigateurs — c'est votre ancrage de confiance par défaut. Dans un réseau interne, vous créez votre propre ancrage : **votre CA privée**. Les machines qui font confiance à votre CA peuvent vérifier tous les certificats que vous émettez, sans dépendre des CAs publiques ni payer par certificat.

### Anatomie d'un certificat X.509

Un certificat X.509 est un document ASN.1 (format binaire DER, souvent encodé en base64 PEM) contenant plusieurs sections critiques :

```
   ┌──────────────────────────────────────────────────┐
   │                  Certificat X.509                │
   │                                                  │
   │  Issuer       : CN=My Internal CA                │
   │  Subject      : CN=api.homelab.lan               │
   │  Validity     : 2026-06-01 → 2026-06-02         │  ← 24h !
   │  Public Key   : RSA 2048 / EC P-256              │
   │  Extensions   :                                  │
   │    KeyUsage   : DigitalSignature                 │
   │    EKU        : ServerAuth, ClientAuth           │
   │    SAN        : api.homelab.lan, 10.0.0.5       │
   │                                                  │
   │  ──── Signed by Issuer ────────────────────      │
   │  Signature : 0xDEADBEEF...                       │
   └──────────────────────────────────────────────────┘
```

Chaque champ a une fonction précise. Le **Subject** identifie le propriétaire du certificat — aujourd'hui le champ `CN` est déprécié au profit des **Subject Alternative Names (SAN)**, qui peuvent contenir plusieurs noms DNS et adresses IP. Les navigateurs et runtimes modernes ignorent le CN si des SANs sont présents. Les **Extended Key Usage (EKU)** précisent l'usage autorisé : `ServerAuth` pour TLS serveur, `ClientAuth` pour mTLS client — un certificat avec uniquement `ServerAuth` ne peut pas s'authentifier comme client mTLS.

**Pourquoi 2 niveaux ?** Si l'intermediate est compromis, on le révoque sans changer la root (qui est dans un coffre). Pas besoin de redistribuer la racine de confiance à tous les clients. La root n'est utilisée que pour signer l'intermediate — elle peut rester hors-ligne le reste du temps.

Si la root elle-même était compromise, il faudrait redistribuer manuellement la nouvelle root à chaque OS, navigateur et service qui lui fait confiance — une opération désastreuse. C'est pourquoi les CAs publiques protègent leurs roots avec des HSM (Hardware Security Modules) stockés dans des coffres physiques.

### Stratégie short-lived : pourquoi 24h ?

La révocation est le talon d'Achille de la PKI classique. Les mécanismes standards (CRL : Certificate Revocation List, OCSP : Online Certificate Status Protocol) ont des problèmes pratiques : les CRLs deviennent volumineuses, les checks OCSP ajoutent de la latence, et les implémentations en mode soft-fail (ne pas bloquer si le check échoue) rendent la révocation inefficace en cas de panne du serveur OCSP.

La solution moderne : **ne pas révoquer, expirer**. Un certificat de 24h renouvelé automatiquement par ACME devient invalide en 24h maximum après une compromission — sans CRL, sans OCSP, sans infrastructure de révocation. C'est l'approche adoptée par cert-manager dans Kubernetes, par Istio pour le mTLS entre pods, par Let's Encrypt pour les certificats publics à court terme.

### TLS classique vs mTLS

<Mermaid chart={`
sequenceDiagram
    participant C as Client
    participant S as Serveur
    Note over C,S: TLS classique (1-way auth)
    C->>S: ClientHello
    S->>C: ServerHello + Certificat serveur
    C->>S: Vérification OK — clé de session
    C->>S: Données chiffrées
    Note over C,S: mTLS (2-way auth)
    C->>S: ClientHello
    S->>C: ServerHello + Certificat serveur + CertificateRequest
    C->>S: Certificat client + Vérification OK
    S->>C: Clé de session établie
    C->>S: Données chiffrées (identité client vérifiée)
`} caption="TLS 1-way vs mTLS 2-way : dans mTLS, le serveur vérifie aussi le certificat du client" />

En TLS classique, seul le serveur prouve son identité. L'authentification du client se fait ensuite en couche applicative (mot de passe, token JWT...). En mTLS, **la couche transport authentifie les deux parties** avant même qu'une ligne de code applicatif ne s'exécute — c'est plus robuste et élimine une classe entière d'attaques.

- Monter une **CA privée** avec step-ca

## 📋 Étape 1 — Installer step-ca

```bash
# Sur une VM Linux ou en Docker
wget https://dl.smallstep.com/cli/docs-ca-install/latest/step-cli_amd64.deb
wget https://dl.smallstep.com/certificates/docs-ca-install/latest/step-ca_amd64.deb
sudo dpkg -i step-cli_amd64.deb step-ca_amd64.deb

# Initialise la PKI
step ca init \
  --name "Homelab CA" \
  --dns ca.homelab.lan \
  --address :8443 \
  --provisioner admin@homelab.lan \
  --acme
```

> 💡 Les URLs `docs-ca-install/latest` pointent vers la dernière version au moment du téléchargement. Pour un lab reproductible, préférez une version épinglée depuis les releases GitHub de smallstep (ex. `https://github.com/smallstep/cli/releases`) et vérifiez l'empreinte (`sha256sum`) avant `dpkg -i`.

La commande `step ca init` crée l'arborescence PKI complète : génère une paire de clés root, une paire de clés intermediate, un certificat root auto-signé, un certificat intermediate signé par le root, et les fichiers de configuration. Le flag `--acme` active le provisioner ACME (nommé `acme`) qui permettra aux clients certbot/acme.sh/step CLI d'obtenir des certificats automatiquement par challenge. Par défaut, `step ca init` crée **aussi** un provisioner JWK nommé d'après le flag `--provisioner` (ici `admin@homelab.lan`) — c'est lui qu'utilise `step ca certificate` sans `--provisioner` explicite. La clé root est chiffrée par le mot de passe que vous allez saisir — **c'est votre secret le plus sensible**, sans lui vous ne pouvez pas renouveler l'intermediate.

step-ca te demande un mot de passe pour la clé root (stocke-le bien — c'est ton secret le plus sensible).

```bash
# Démarrer le service
step-ca $(step path)/config/ca.json
```

## 📋 Étape 2 — Distribuer le CA cert aux clients

Récupère le bundle de confiance et installe-le là où tu en auras besoin :

```bash
# Bundle root + intermediate
step ca root /tmp/root_ca.crt

# Sur chaque client qui doit faire confiance à ta CA
sudo cp /tmp/root_ca.crt /usr/local/share/ca-certificates/homelab.crt
sudo update-ca-certificates
```

La commande `update-ca-certificates` ajoute votre CA au magasin de certificats système (`/etc/ssl/certs/ca-certificates.crt`). Après cette étape, curl, wget, Go `http.Get()`, Python `requests`, et tout outil utilisant le store système feront automatiquement confiance aux certificats signés par votre CA — sans avoir à spécifier `--cacert` à chaque commande.

Vérifie : `curl https://ca.homelab.lan:8443/health` doit retourner `OK` sans erreur TLS.

## 📋 Étape 3 — Émettre un certificat via ACME

Deux chemins coexistent, et il est important de ne pas les confondre :

**Chemin rapide (provisioner JWK)** — `step ca certificate` utilise par défaut le provisioner JWK : l'authentification se fait avec le mot de passe du provisioner, sans challenge de domaine. Pratique pour un test immédiat :

```bash
# Cert pour api.homelab.lan, valide 24h, via le provisioner JWK par défaut
step ca certificate api.homelab.lan api.crt api.key --not-after 24h

# Inspect
step certificate inspect api.crt --short
```

**Chemin ACME (ce que le lab vise réellement)** — pour passer par le provisioner `--acme` activé à l'Étape 1, il faut soit un client ACME standard (certbot, lego, acme.sh, cert-manager), soit `step` en lui désignant explicitement le provisioner ACME. C'est ce chemin qui réalise un challenge de domaine (HTTP-01 ou DNS-01) prouvant que vous contrôlez bien `api.homelab.lan` :

```bash
# Via le provisioner ACME (challenge HTTP-01) — step joue le rôle du client ACME
step ca certificate api.homelab.lan api.crt api.key \
  --provisioner acme --not-after 24h
# certbot équivalent :
# certbot certonly --standalone --server https://ca.homelab.lan:8443/acme/acme/directory -d api.homelab.lan
```

En coulisses, dans les deux cas `step` génère une paire de clés locale, crée un CSR (Certificate Signing Request), l'envoie à step-ca, qui retourne le certificat signé. La différence est l'**authentification** : JWK = secret du provisioner ; ACME = preuve cryptographique de contrôle du domaine. La clé privée ne quitte jamais la machine — seul le CSR (qui ne contient que la clé publique) transite.

Tu verras :

```
X.509v3 TLS Certificate
  Subject:     api.homelab.lan
  Issuer:      Homelab CA Intermediate CA
  Provisioner: admin@homelab.lan
  Valid from:  ...
          to:  ... (24h plus tard)
```

## 📋 Étape 4 — Configurer mTLS entre deux services

Crée un serveur Go simple qui exige un certif client signé par ta CA :

```go
// server.go
package main

import (
  "crypto/tls"
  "crypto/x509"
  "fmt"
  "net/http"
  "os"
)

func main() {
  // os.ReadFile remplace ioutil.ReadFile, déprécié depuis Go 1.16
  caCert, _ := os.ReadFile("/tmp/root_ca.crt")
  pool := x509.NewCertPool()
  pool.AppendCertsFromPEM(caCert)

  s := &http.Server{
    Addr: ":8443",
    TLSConfig: &tls.Config{
      ClientCAs: pool,
      ClientAuth: tls.RequireAndVerifyClientCert, // ← mTLS
    },
  }
  http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
    cn := r.TLS.PeerCertificates[0].Subject.CommonName
    fmt.Fprintf(w, "Hello, authenticated as %s\n", cn)
  })
  s.ListenAndServeTLS("api.crt", "api.key")
}
```

La ligne clé est `ClientAuth: tls.RequireAndVerifyClientCert` — c'est elle qui active le mTLS. Le champ `ClientCAs` précise quelles CAs sont autorisées à signer les certificats clients. Sans cette configuration, le serveur accepterait n'importe quel client sans vérification. Le handler accède aux informations du certificat client via `r.TLS.PeerCertificates` — l'identité est disponible dès la couche transport, avant même de lire le corps de la requête.

Émets un certif client puis teste :

```bash
step ca certificate client@homelab.lan client.crt client.key --not-after 24h

# Sans cert client → échec dès le handshake TLS (pas de réponse HTTP)
curl --cacert /tmp/root_ca.crt https://api.homelab.lan:8443/
# → curl: (56) ... alert certificate required  (le serveur refuse au niveau TLS)

# Avec cert client → 200 + identification
curl --cacert /tmp/root_ca.crt \
     --cert client.crt --key client.key \
     https://api.homelab.lan:8443/
# → Hello, authenticated as client@homelab.lan
```

`--cacert` indique au client curl quelle CA utiliser pour vérifier le serveur. `--cert` et `--key` fournissent le certificat et la clé privée client pour le mTLS. Point clé à bien comprendre : avec `RequireAndVerifyClientCert`, le refus se produit **pendant le handshake TLS**, avant tout traitement HTTP — il n'y a donc ni code 400 ni 401, mais une erreur TLS (`certificate required`). C'est précisément l'intérêt du mTLS : un client non autorisé n'atteint jamais la couche applicative.

> 💡 `step ca certificate` écrit dans `api.crt` le certificat feuille **suivi de l'intermediate** (le bundle). C'est ce qui permet au serveur Go de présenter la chaîne complète : un client qui ne connaît que la root peut alors la reconstruire jusqu'à un ancrage de confiance.

## 📋 Étape 5 — Révocation

```bash
# Récupère le serial number du cert client
SERIAL=$(step certificate inspect client.crt --format json | jq -r .serial_number)

# Révoque
step ca revoke $SERIAL --reason key_compromise
```

Nuance importante : la signature du certificat reste cryptographiquement valide (un vérificateur qui ne consulte ni CRL ni OCSP continuera de l'accepter jusqu'à expiration). Ce que fait `step ca revoke`, c'est marquer le serial comme révoqué dans la base de la CA, ce qui bloque surtout son **renouvellement** (passive revocation) ; step-ca ne sert pas d'OCSP/CRL par défaut. C'est exactement pourquoi la stratégie short-lived est supérieure : sur des certifs 24h renouvelés en continu, révoquer ≈ cesser de renouveler, et le certificat disparaît de lui-même sous 24h. **On attend l'expiration** plutôt que de bâtir une infrastructure de révocation fragile.

## ✅ Validation

- `step ca health` → OK
- Cert émis valide 24h
- `curl` sans cert client → bloqué par mTLS
- `curl` avec cert client → réponse avec identification du sujet

## 🚀 Pour aller plus loin

- **cert-manager** dans Kubernetes : déploie step-ca comme `Issuer`, et tous tes Ingress reçoivent un certif auto-renouvelé
- **SPIFFE/SPIRE** : pousser le concept à l'extrême — chaque workload reçoit une identité cryptographique (SVID), zero-config
- **Istio** ou **Linkerd** : mTLS automatique entre tous les pods d'un cluster, sans code applicatif
