## 🧠 Théorie : provisioning vs configuration

```
   PROVISIONING (Terraform)         CONFIGURATION (Ansible)
   ────────────────────────         ──────────────────────
   
   Crée la VM, le réseau,            Installe nginx,
   le DNS, le LB, le bucket S3       configure /etc/nginx,
                                     ouvre firewall, démarre
   
   DÉCLARATIF                         IDEMPOTENT
   "voici l'état désiré"              "amène l'OS à cet état"
   
   State file                         Pas de state — l'OS est l'état
   "cloud level"                      "OS level"
```

Confondre les deux mène à :
- Provisionner avec Ansible : pas de state, pas de planning, lent.
- Configurer avec Terraform : oublier les diffs intra-VM, pas idempotent.


## 📋 Étape 1 — Terraform : provisioning Proxmox

```hcl
# main.tf
terraform {
  required_providers {
    proxmox = {
      source  = "bpg/proxmox"
      version = "~> 0.46"
    }
  }
  backend "s3" {
    bucket = "tf-state-homelab"
    key    = "k3s-cluster/terraform.tfstate"
    region = "fr-par"
  }
}

provider "proxmox" {
  endpoint = var.pve_url
  api_token = var.pve_token
}

resource "proxmox_virtual_environment_vm" "k8s_node" {
  count     = 3
  name      = "k8s-node-${count.index + 1}"
  node_name = "pve01"
  cpu { cores = 4 }
  memory { dedicated = 8192 }

  clone {
    vm_id = 9000   # template debian-12-cloud
  }

  initialization {
    ip_config {
      ipv4 {
        address = "192.168.10.${10 + count.index}/24"
        gateway = "192.168.10.1"
      }
    }
    user_account {
      username = "ansible"
      keys     = [file("~/.ssh/id_ed25519.pub")]
    }
  }
}

output "nodes" {
  value = {
    for i, vm in proxmox_virtual_environment_vm.k8s_node :
    vm.name => vm.ipv4_addresses[1][0]
  }
}
```

```bash
terraform init
terraform plan -out plan.bin
terraform apply plan.bin
terraform output -json nodes
```

## 📋 Étape 2 — Inventaire Ansible dynamique

```python
# inventory/terraform.py
#!/usr/bin/env python3
import json, subprocess, sys
out = subprocess.check_output(['terraform', '-chdir=../terraform', 'output', '-json', 'nodes'])
nodes = json.loads(out)
inv = {
  'all': {'children': {'k3s': {'hosts': {n: {'ansible_host': ip} for n, ip in nodes.items()}}}},
  '_meta': {'hostvars': {n: {'ansible_user': 'ansible'} for n in nodes}}
}
print(json.dumps(inv))
```

```bash
chmod +x inventory/terraform.py
ansible -i inventory/terraform.py all -m ping
```

## 📋 Étape 3 — Rôle Ansible : install k3s

```yaml
# roles/k3s/tasks/main.yml
- name: Installer dépendances
  apt:
    name: [curl, iptables, kmod]
    state: present
    update_cache: yes

- name: Récupérer le script d'install k3s
  get_url:
    url: https://get.k3s.io
    dest: /tmp/install-k3s.sh
    mode: '0755'

- name: Bootstrap server sur le node #1
  shell: INSTALL_K3S_EXEC="server --cluster-init" /tmp/install-k3s.sh
  args:
    creates: /etc/rancher/k3s/k3s.yaml
  when: inventory_hostname == groups['k3s'][0]

- name: Récupérer le token cluster
  slurp:
    src: /var/lib/rancher/k3s/server/node-token
  register: token_file
  when: inventory_hostname == groups['k3s'][0]

- name: Joindre les autres nodes
  shell: |
    K3S_URL=https://{{ hostvars[groups['k3s'][0]].ansible_host }}:6443 \
    K3S_TOKEN={{ hostvars[groups['k3s'][0]].token_file.content | b64decode | trim }} \
    INSTALL_K3S_EXEC="server" /tmp/install-k3s.sh
  args:
    creates: /etc/rancher/k3s/k3s.yaml
  when: inventory_hostname != groups['k3s'][0]
```

```yaml
# site.yml
- hosts: k3s
  become: yes
  roles:
    - k3s
```

```bash
ansible-playbook -i inventory/terraform.py site.yml
```

## 📋 Étape 5 — Pipeline GitLab CI

```yaml
# .gitlab-ci.yml
stages: [plan, apply, configure]

variables:
  TF_STATE_NAME: k3s
  TF_ROOT: terraform/

plan:
  image: hashicorp/terraform:1.7
  script:
    - cd $TF_ROOT
    - terraform init
    - terraform plan -out=plan.bin

apply:
  image: hashicorp/terraform:1.7
  needs: [plan]
  when: manual
  script:
    - cd $TF_ROOT
    - terraform apply plan.bin

configure:
  image: alpine/ansible:latest
  needs: [apply]
  script:
    - ansible-playbook -i inventory/terraform.py site.yml --check    # dry run d'abord
    - ansible-playbook -i inventory/terraform.py site.yml
```

> 💡 `terraform apply` MANUEL pour éviter les destructions accidentelles, MAIS `terraform plan` automatique dans la MR pour code review du diff.

## 🧠 Pitfalls

❌ **State local en équipe** : conflit garanti.
❌ **Secrets en clair dans HCL** : utilise variables d'env ou Vault.
❌ **`shell:` partout en Ansible au lieu des modules** : casse l'idempotence.
❌ **`apt update` à chaque tâche** : lent. Utilise un block `pre_tasks` + `cache_valid_time`.
❌ **Provisionner sans destroy plan** : terraform peut détruire en cas de drift entre state et infra.

## ✅ Validation

- `terraform plan` montre 0 changes après apply
- Re-jouer `ansible-playbook` → tout `ok=N changed=0`
- `kubectl get nodes` → 3 nodes Ready
- Molecule test passe en CI
