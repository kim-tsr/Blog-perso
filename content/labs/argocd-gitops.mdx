## Théorie : qu'est-ce que GitOps exactement ?

Le terme a été forgé par Weaveworks en 2017 pour décrire une pratique opérationnelle qui pousse à son terme la logique IaC déclarative. L'idée centrale : **Git n'est pas seulement un historique de code — c'est la définition authoritative de l'état souhaité du système**. Aucune modification de production ne peut exister sans passer par un commit. Aucun rollback n'est une opération ad hoc : c'est un `git revert`.

Les quatre principes fondateurs sont : (1) **déclaratif** — l'état désiré est décrit, non scripté ; (2) **versionné et immutable** — tout changement a un SHA, une date, un auteur ; (3) **approuvé automatiquement** — un commit mergé sur la branche cible déclenche le déploiement sans intervention humaine ; (4) **réconcilié continuellement** — un agent observe en permanence l'écart entre ce qui est dans Git et ce qui est dans le cluster, et converge vers Git. Cette boucle de réconciliation remplace les pipelines "fire and forget" classiques par un système de contrôle fermé.

Le bénéfice le plus sous-estimé de GitOps n'est pas la rapidité de déploiement — c'est l'audit trail gratuit. Chaque état de production correspond à un commit : qui a changé quoi, quand, pourquoi (message de commit), approuvé par qui (review PR). En cas d'incident, la première question devient triviale : quel commit a introduit la régression ?

### Push vs Pull : une différence de sécurité fondamentale

La distinction push/pull n'est pas technique au sens algorithmique — elle est architecturale, et ses implications de sécurité sont majeures. Dans un pipeline push (Jenkins, GitHub Actions avec `kubectl apply`), la CI détient les credentials du cluster. Un secret CI compromis — une clé API exposée dans un log, une repo publique qui contenait un token — donne accès à la production. Dans un pipeline pull, l'agent (ArgoCD) vit **dans** le cluster, lit le repo Git en lecture seule, et n'expose aucun credential sortant. La surface d'attaque est radicalement réduite.

### La reconciliation loop en détail

ArgoCD implémente une boucle de contrôle classique : toutes les 3 minutes (ou sur webhook), il compare l'état réel du cluster (via l'API Kubernetes) avec l'état déclaré dans Git. Si un écart existe — une ressource manquante, un champ modifié, un déploiement scalé manuellement — ArgoCD peut soit alerter (sync manuel) soit corriger automatiquement (sync automatique + selfHeal). Ce modèle de contrôle fermé est identique à celui d'un thermostat : l'état réel converge toujours vers la consigne.

## Objectif

Installer **ArgoCD**, créer une `Application` qui pull depuis Git, voir le déploiement automatique, et tester ce qui se passe quand le cluster s'éloigne de l'état désiré.

## Étape 1 — Installer ArgoCD

```bash
kubectl create namespace argocd
kubectl apply -n argocd \
  -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
kubectl wait --for=condition=available --timeout=300s \
  deployment/argocd-server -n argocd
```

Ce manifest déploie l'ensemble du control plane ArgoCD dans le namespace `argocd` : le serveur API, le repo-server (qui clone et analyse les repos Git), l'application-controller (la boucle de réconciliation elle-même), et le Dex pour l'authentification OIDC. Le `kubectl wait` bloque jusqu'à ce que le déploiement soit prêt avant de continuer.

Récupérez le mot de passe admin initial :

```bash
kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath="{.data.password}" | base64 -d
```

Le mot de passe est stocké dans un Secret Kubernetes encodé en base64 (pas chiffré — simple encoding). Le flag `-o jsonpath` extrait le champ `data.password` directement sans passer par `jq`. Le pipe `base64 -d` décode la valeur.

Port-forward pour accéder à l'UI :

```bash
kubectl port-forward svc/argocd-server -n argocd 8080:443
# Ouvrez https://localhost:8080  (login: admin)
```

> En prod : exposez via Ingress + TLS, intégrez SSO (OIDC), changez le password initial.

## Étape 2 — Préparer le dépôt Git

Dans un dépôt vide, créez `apps/whoami/deployment.yaml` :

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: whoami
spec:
  replicas: 2
  selector: { matchLabels: { app: whoami } }
  template:
    metadata: { labels: { app: whoami } }
    spec:
      containers:
        - name: whoami
          image: traefik/whoami
          ports: [ { containerPort: 80 } ]
```

Ce Deployment déclare 2 replicas de l'image `traefik/whoami`, un serveur HTTP minimal qui retourne des informations sur le pod courant. Le champ `selector.matchLabels` définit quels pods appartiennent à ce Deployment — il doit correspondre exactement aux labels du `template.metadata.labels`. C'est le mécanisme de liaison entre Deployment et Pods dans Kubernetes.

Commitez et poussez.

## Étape 3 — Créer l'Application ArgoCD

```yaml
# argocd-app.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: whoami
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/<vous>/<repo>.git
    targetRevision: main
    path: apps/whoami
  destination:
    server: https://kubernetes.default.svc
    namespace: default
  syncPolicy:
    automated:
      prune: true       # supprime les ressources retirées de Git
      selfHeal: true    # corrige le drift manuel
    syncOptions:
      - CreateNamespace=true
```

`apiVersion: argoproj.io/v1alpha1` indique que `Application` est une Custom Resource installée par ArgoCD — Kubernetes ne la connaît pas nativement. Le champ `source.path` pointe vers le sous-dossier du repo qui contient les manifests à déployer ; ArgoCD ne déploie pas le repo entier, juste ce chemin. `destination.server: https://kubernetes.default.svc` signifie "le cluster où ArgoCD lui-même tourne" — c'est l'adresse interne de l'API Kubernetes. `prune: true` est le champ le plus dangereux : il autorise ArgoCD à **supprimer** des ressources Kubernetes si elles ont été retirées du repo Git.

> 💡 Ajoutez le finalizer `resources-finalizer.argocd.argoproj.io` dans `metadata.finalizers` de l'Application si vous voulez que supprimer l'Application supprime AUSSI les ressources qu'elle a déployées (cascade delete). Sans lui, `kubectl delete application whoami` ne retire que l'Application, en laissant le Deployment orphelin dans le cluster.

```bash
kubectl apply -f argocd-app.yaml
```

Dans l'UI, l'app passe **Syncing → Healthy** en quelques secondes.

### Anatomie des champs critiques

| Champ | Effet |
|---|---|
| `repoURL` | Source Git (HTTPS ou SSH) |
| `targetRevision` | Branche, tag, ou commit SHA |
| `path` | Sous-dossier dans le repo |
| `automated.prune` | Supprime ce qui n'est plus dans Git |
| `automated.selfHeal` | Annule les modifs manuelles |

## Étape 4 — Tester le drift

Modifiez manuellement le déploiement :

```bash
kubectl scale deployment whoami --replicas=5
```

Quelques secondes plus tard, ArgoCD ramène à **2 replicas** — c'est le `selfHeal` qui agit. En pratique : ArgoCD détecte que le champ `spec.replicas` du Deployment dans le cluster diffère de ce qui est dans Git (`2` vs `5`), et ré-applique le manifest Git. C'est ça, GitOps : **le dépôt Git est la source de vérité, pas le cluster**.

## Étape 5 — Tester le rollback

Modifiez l'image dans Git (`image: nginx`), commitez. ArgoCD synchronise. Revenez en arrière (`git revert`), ArgoCD redéploie l'ancienne version.

Le rollback GitOps est un `git revert` + push. Pas de `kubectl rollout undo` dispersé entre les sysadmins, pas d'état mental à maintenir : l'historique Git est l'historique de déploiement. Le SHA du commit en production est le SHA du commit Git.

## Étape 6 — Sync Waves (bonus)

Les Sync Waves permettent de forcer un ordre de déploiement au sein d'une même Application. Sans waves, ArgoCD applique toutes les ressources en parallèle — ce qui cause des races : un Deployment qui référence un Secret pas encore créé échouera au démarrage du pod.

```yaml
# namespace en premier
apiVersion: v1
kind: Namespace
metadata:
  name: myapp
  annotations:
    argocd.argoproj.io/sync-wave: "-2"
---
# secrets ensuite
apiVersion: v1
kind: Secret
metadata:
  name: db-creds
  namespace: myapp
  annotations:
    argocd.argoproj.io/sync-wave: "-1"
---
# deployment dépend des secrets
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: myapp
  annotations:
    argocd.argoproj.io/sync-wave: "0"
```

L'annotation `argocd.argoproj.io/sync-wave` prend une valeur entière (négative, zéro, positive). ArgoCD trie les ressources par wave croissante et attend que chaque wave soit **Healthy** avant de passer à la suivante. Wave `-2` est appliquée en premier, wave `0` en dernier. Les valeurs sont arbitraires — seul l'ordre relatif compte.

## Étape 7 — App-of-Apps

Le pattern App-of-Apps consiste à créer une Application ArgoCD racine dont le `source.path` pointe vers un dossier contenant d'autres manifests `Application`. ArgoCD déploie la racine, qui à son tour crée toutes les Applications enfants. Ajouter une nouvelle application se résume à ajouter un fichier dans ce dossier et commiter.

```yaml
# root-app.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: root
spec:
  source:
    repoURL: ...
    path: argocd-apps/   # dossier contenant N Applications
  destination:
    namespace: argocd
    server: https://kubernetes.default.svc
```

Chaque fichier dans `argocd-apps/` est une Application. Ajouter une app = commit dans ce dossier. La limite du pattern apparaît autour de 50-100 apps : à cette échelle, `ApplicationSet` avec un générateur (`git`, `list`, `cluster`, `matrix`) est plus adapté — un seul manifest template génère N Applications dynamiquement.

## Anti-patterns

❌ **Stocker des secrets en clair dans Git** : utilisez Sealed Secrets, External Secrets, ou SOPS.
❌ **Désactiver `selfHeal` "pour permettre les hotfix manuels"** : autant ne pas faire GitOps.
❌ **Un seul méga-repo monolithique** : conflits de PR, RBAC impossible. Préférez 1 repo apps + 1 repo platform.
❌ **Pas de Project ArgoCD** : tout admin → vol de role.
❌ **Sync auto sans tests CI préalables** : YAML cassé en main = prod cassée.

## Validation

- ArgoCD UI affiche l'app **Healthy + Synced**
- Modifier le déploiement à la main est annulé sous 1 minute
- `git revert` déploie l'ancienne version sans intervention
- Sync waves respectées (namespace avant deployment)

## Pour aller plus loin

- Utilisez **ApplicationSets** pour générer N apps depuis un template
- Activez **Sync Waves** pour orchestrer l'ordre de déploiement
- Branchez **OPA Gatekeeper** pour valider les manifests avant synchronisation
- Couplez avec **Argo Rollouts** pour des déploiements canary/blue-green
- Multi-cluster : un ArgoCD central qui déploie sur N clusters via ApplicationSet generator `clusters`
