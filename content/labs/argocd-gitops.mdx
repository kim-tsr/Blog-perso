## 🧠 Théorie : qu'est-ce que GitOps exactement ?

Le terme a été inventé par Weaveworks en 2017. Quatre principes fondateurs :

```
   1. DÉCLARATIF
      L'état désiré est décrit (YAML), pas impératé (script).

   2. VERSIONNÉ ET IMMUTABLE
      Source de vérité = Git. Toute l'histoire est auditable.

   3. APPROUVÉ AUTOMATIQUEMENT
      Un commit mergé = un déploiement. Pas de webhook manuel.

   4. RÉCONCILIÉ CONTINUELLEMENT
      Un agent observe l'écart entre Git (souhaité) et cluster (réel),
      et converge en boucle (la fameuse "reconciliation loop").
```

### Push vs Pull

```
   PUSH-based (Jenkins, GitHub Actions kubectl apply)
   ─────────────────────────────────────────────────
   
   Git ──► CI ──► kubectl apply ──► Cluster
              │                       
              │ ⚠️  CI a les credentials cluster
              │ ⚠️  Pas de réconciliation auto
              │ ⚠️  CI hors cluster = surface d'attaque
   
   PULL-based (ArgoCD, Flux)
   ─────────────────────────
   
   Git ◄── ArgoCD (dans le cluster) ──► Cluster (lui-même)
            │
            │ ✓ Aucun credential sortant
            │ ✓ Reconciliation toutes les 3 min
            │ ✓ Drift detection + self-heal
```

### Reconciliation loop

```
   ┌─────────────────────────────────┐
   │   while True:                   │
   │     desired = git_pull()        │ ◄── état souhaité
   │     actual  = cluster_state()   │ ◄── état réel
   │     diff = compare(actual,desired)
   │     if diff:                    │
   │       apply(diff) or alert()    │
   │     sleep(180s)                 │
   └─────────────────────────────────┘
```

## 🎯 Objectif

Installer **ArgoCD**, créer une `Application` qui pull depuis Git, voir le déploiement automatique, et tester ce qui se passe quand le cluster s'éloigne de l'état désiré.

## 📋 Étape 1 — Installer ArgoCD

```bash
kubectl create namespace argocd
kubectl apply -n argocd \
  -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
kubectl wait --for=condition=available --timeout=300s \
  deployment/argocd-server -n argocd
```

Récupérez le mot de passe admin initial :

```bash
kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath="{.data.password}" | base64 -d
```

Port-forward pour accéder à l'UI :

```bash
kubectl port-forward svc/argocd-server -n argocd 8080:443
# Ouvrez https://localhost:8080  (login: admin)
```

> 💡 En prod : exposez via Ingress + TLS, intégrez SSO (OIDC), changez le password initial.

## 📋 Étape 2 — Préparer le dépôt Git

Dans un dépôt vide, créez `apps/whoami/deployment.yaml` :

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: whoami
spec:
  replicas: 2
  selector: { matchLabels: { app: whoami } }
  template:
    metadata: { labels: { app: whoami } }
    spec:
      containers:
        - name: whoami
          image: traefik/whoami
          ports: [ { containerPort: 80 } ]
```

Commitez et poussez.

## 📋 Étape 3 — Créer l'Application ArgoCD

```yaml
# argocd-app.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: whoami
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/<vous>/<repo>.git
    targetRevision: main
    path: apps/whoami
  destination:
    server: https://kubernetes.default.svc
    namespace: default
  syncPolicy:
    automated:
      prune: true       # supprime les ressources retirées de Git
      selfHeal: true    # corrige le drift manuel
    syncOptions:
      - CreateNamespace=true
```

```bash
kubectl apply -f argocd-app.yaml
```

Dans l'UI, l'app passe **Syncing → Healthy** en quelques secondes.

### Anatomie des champs critiques

| Champ | Effet |
|---|---|
| `repoURL` | Source Git (HTTPS ou SSH) |
| `targetRevision` | Branche, tag, ou commit SHA |
| `path` | Sous-dossier dans le repo |
| `automated.prune` | Supprime ce qui n'est plus dans Git |
| `automated.selfHeal` | Annule les modifs manuelles |

## 📋 Étape 4 — Tester le drift

Modifiez manuellement le déploiement :

```bash
kubectl scale deployment whoami --replicas=5
```

Quelques secondes plus tard, ArgoCD ramène à **2 replicas** — c'est le `selfHeal` qui agit. C'est ça, GitOps : **le dépôt Git est la source de vérité**.

## 📋 Étape 5 — Tester le rollback

Modifiez l'image dans Git (`image: nginx`), commitez. ArgoCD synchronise. Revenez en arrière (`git revert`), ArgoCD redéploie l'ancienne version.

→ Rollback = un `git revert` + push. Pas de "kubectl rollout undo" dispersé entre les sysadmins.

## 📋 Étape 6 — Sync Waves (bonus)

Pour orchestrer l'ordre :

```yaml
# namespace en premier
apiVersion: v1
kind: Namespace
metadata:
  name: myapp
  annotations:
    argocd.argoproj.io/sync-wave: "-2"
---
# secrets ensuite
apiVersion: v1
kind: Secret
metadata:
  name: db-creds
  namespace: myapp
  annotations:
    argocd.argoproj.io/sync-wave: "-1"
---
# deployment dépend des secrets
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: myapp
  annotations:
    argocd.argoproj.io/sync-wave: "0"
```

## 📋 Étape 7 — App-of-Apps

Pour gérer N apps :

```yaml
# root-app.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: root
spec:
  source:
    repoURL: ...
    path: argocd-apps/   # dossier contenant N Applications
  destination:
    namespace: argocd
    server: https://kubernetes.default.svc
```

Chaque fichier dans `argocd-apps/` est une Application. Ajouter une app = commit dans ce dossier.

## 🧠 Anti-patterns

❌ **Stocker des secrets en clair dans Git** : utilisez Sealed Secrets, External Secrets, ou SOPS.
❌ **Désactiver `selfHeal` "pour permettre les hotfix manuels"** : autant ne pas faire GitOps.
❌ **Un seul méga-repo monolithique** : conflits de PR, RBAC impossible. Préférez 1 repo apps + 1 repo platform.
❌ **Pas de Project ArgoCD** : tout admin → vol de role.
❌ **Sync auto sans tests CI préalables** : YAML cassé en main = prod cassée.

## ✅ Validation

- ArgoCD UI affiche l'app **Healthy + Synced**
- Modifier le déploiement à la main est annulé sous 1 minute
- `git revert` déploie l'ancienne version sans intervention
- Sync waves respectées (namespace avant deployment)

## 🚀 Pour aller plus loin

- Utilisez **ApplicationSets** pour générer N apps depuis un template
- Activez **Sync Waves** pour orchestrer l'ordre de déploiement
- Branchez **OPA Gatekeeper** pour valider les manifests avant synchronisation
- Couplez avec **Argo Rollouts** pour des déploiements canary/blue-green
- Multi-cluster : un ArgoCD central qui déploie sur N clusters via ApplicationSet generator `clusters`
