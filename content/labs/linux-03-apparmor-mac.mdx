## 🧠 Théorie : pourquoi MAC, alors qu'on a déjà chmod et caps ?

### DAC : faillible par design

```
   Permissions Unix (DAC)            Limites
   ───────────────────────           ────────
   
   -rw-r--r-- root root /etc/shadow  ✓ user 'alice' bloqué
                                     ✗ root y accède toujours
                                     ✗ un setuid root y accède
                                     ✗ un process avec CAP_DAC_READ_SEARCH y accède
                                     ✗ si quelqu'un change les perms : game over
```

### MAC : couche orthogonale

```
       ┌──────────────────────────────────────────┐
       │   Process X tente d'ouvrir /etc/shadow   │
       └──────────────────────────────────────────┘
                          │
                          ▼
              ┌────────────────────────┐
              │  1. Check DAC          │
              │     (perms + caps)     │
              └────────────────────────┘
                          │
                          ▼
                     DAC dit OK ?
                  ┌────┴────┐
                  │         │
                NON        OUI
                  │         ▼
                  │   ┌────────────────────────┐
                  │   │  2. Check MAC          │
                  │   │     (AppArmor/SELinux) │
                  │   └────────────────────────┘
                  │         │
                  │         ▼
                  │    MAC dit OK ?
                  │   ┌────┴────┐
                  │  NON       OUI
                  │   │         │
                  ▼   ▼         ▼
                  REFUSÉ      AUTORISÉ
```

→ **Il faut que les DEUX disent oui.** Une faille DAC (ex: setuid bug) ne donne pas le contrôle si MAC bloque.

### AppArmor vs SELinux en 1 tableau

| | AppArmor | SELinux |
|---|---|---|
| **Attache** | Par path absolu | Par label FS (xattr) |
| **Lisibilité** | Profile = texte humain | Policy = TE files compilés |
| **Granularité** | Très bonne | Excellente |
| **Maintenance** | Profile par binaire | Type Enforcement complexe |
| **Distributions par défaut** | Ubuntu, Debian, openSUSE | RHEL/CentOS/Fedora, Android |
| **Courbe** | 2 jours | 2 semaines |

Choisis selon ce qu'utilise ta distrib. Les deux sont **MAC complets**.

## 📋 Étape 1 — État des lieux

```bash
sudo aa-status
# 36 profiles are loaded.
# 28 profiles are in enforce mode.
# 8 profiles are in complain mode.
# 12 processes have profiles defined.
# 12 processes are in enforce mode.
```

Inspecter un profile existant :

```bash
sudo cat /etc/apparmor.d/usr.sbin.nginx
```

Tu vois la syntaxe : règles `path mode,` (mode = `r` `w` `m` `ix`, etc.) et des includes (`#include <abstractions/base>`).

## 📋 Étape 2 — Notre cible : un script Python custom

```bash
sudo tee /usr/local/bin/log-collector <<'EOF'
#!/usr/bin/env python3
"""Lit les logs nginx et écrit un résumé."""
import os, glob
with open('/var/log/collector.out', 'w') as out:
    for f in glob.glob('/var/log/nginx/access.log*'):
        with open(f) as fh:
            out.write(f"{f}: {sum(1 for _ in fh)} lines\n")
EOF
sudo chmod +x /usr/local/bin/log-collector
sudo /usr/local/bin/log-collector   # marche, lit tout sans contrainte
```

Sans AppArmor, ce script peut lire ce qu'il veut (uid=root par défaut, ou en sudo).

## 📋 Étape 3 — Bootstrap d'un profile avec aa-genprof

```bash
sudo apt install apparmor-utils
sudo aa-genprof /usr/local/bin/log-collector
```

L'outil affiche : "Lance l'app, puis reviens ici." → on lance dans un autre terminal :

```bash
sudo /usr/local/bin/log-collector
```

Retour dans aa-genprof, tape `S` (scan) → il liste chaque accès observé :

```
Profile:    /usr/local/bin/log-collector
Path:       /var/log/nginx/access.log
New Mode:   r
Severity:   3
[1 - #include <abstractions/...> ]
 2 - /var/log/nginx/access.log r,
 3 - /var/log/nginx/*.log r,
 4 - /var/log/nginx/** r,
[(A)llow / (D)eny / (I)gnore / (G)lob / (N)ew]
```

Tu choisis le bon niveau de glob (`G` plusieurs fois pour étendre, puis `A` pour autoriser). À la fin, `F` pour finaliser.

Le profile est créé dans `/etc/apparmor.d/usr.local.bin.log-collector`.

## 📋 Étape 4 — Lire et comprendre le profile généré

```apparmor
#include <tunables/global>

/usr/local/bin/log-collector {
  #include <abstractions/base>
  #include <abstractions/python>

  /usr/bin/python3 ix,
  /usr/local/bin/log-collector r,

  /var/log/nginx/*.log r,
  /var/log/collector.out w,
}
```

Décodage :

| Token | Sens |
|---|---|
| `r` | read |
| `w` | write |
| `a` | append |
| `m` | mmap PROT_EXEC |
| `ix` | exec, inherit profile parent |
| `Px`, `Cx` | exec, switch profile |
| `Ux` | exec, unconfined (à éviter !) |
| `**` | glob récursif |
| `#include` | importe un set commun |

## 📋 Étape 5 — Complain mode pour itérer

```bash
sudo aa-complain /etc/apparmor.d/usr.local.bin.log-collector
sudo aa-status | grep log-collector
# usr.local.bin.log-collector  (complain)
```

Lance l'app dans des cas variés (rotation logs, gros volumes, edge cases…). Les violations sont loggées sans bloquer.

```bash
sudo journalctl -k --since "10 min ago" | grep apparmor=\"ALLOWED\"
# → liste de chaque accès qui aurait été bloqué en enforce
```

Affine avec `aa-logprof` : parse les logs, te propose d'ajouter les nouvelles règles.

## 📋 Étape 6 — Enforce et test

```bash
sudo aa-enforce /etc/apparmor.d/usr.local.bin.log-collector

# Test : opération autorisée
sudo /usr/local/bin/log-collector
cat /var/log/collector.out
# OK

# Test : tentative d'opération NON autorisée
sudo /usr/local/bin/log-collector --exfil /etc/shadow
# → DENIED dans les logs kernel
```

Vérification :

```bash
sudo journalctl -k | grep apparmor=\"DENIED\"
# Mar 15 14:22:01 host kernel: audit: type=1400 audit(...): apparmor="DENIED"
#   operation="open" profile="/usr/local/bin/log-collector"
#   name="/etc/shadow" pid=12345 comm="log-collector"
#   requested_mask="r" denied_mask="r" fsuid=0 ouid=0
```

→ Même en uid=0, AppArmor a refusé.

## 📋 Étape 7 — Patterns de profile avancés

### Sub-profile pour un child process

```apparmor
/usr/local/bin/app {
  /usr/bin/curl Cx -> curl_subprofile,

  profile curl_subprofile {
    network inet stream,
    /etc/ssl/certs/ r,
    /etc/resolv.conf r,
    deny /etc/shadow r,
  }
}
```

### Network rules

```apparmor
/usr/local/bin/app {
  network inet stream,         # TCP IPv4 OK
  network inet6 stream,        # TCP IPv6 OK
  deny network packet,         # AF_PACKET interdit
  deny network netlink,        # netlink interdit
}
```

### Mount, unix sockets, capabilities

```apparmor
/usr/local/bin/app {
  capability net_bind_service, # autorise CAP_NET_BIND_SERVICE
  deny capability sys_admin,   # bloque la "nouvelle root"

  unix (connect) type=stream addr="@/tmp/mysocket",
}
```

## 🧠 Pitfalls

❌ **Profile en enforce sans avoir testé en complain** : tu casses ta prod en silence (logs fragmentés, écritures partielles).
❌ **`/var/log/** w` trop large** : devient un trou. Vise `/var/log/myapp/`.
❌ **Oublier les abstractions** (`#include <abstractions/base>`) : tu rates des trucs essentiels (libc, locale, etc.).
❌ **Utiliser `Ux` au lieu de `Cx`** : tu sors du profile → annule toute la protection.
❌ **Penser que MAC remplace les autres couches** : MAC s'ajoute. Tu gardes DAC restrictif + caps drop + seccomp.

## 🔬 Validation

```bash
# Profile chargé
sudo aa-status | grep log-collector
# → ... (enforce)

# DENIED log sur tentative d'accès interdit
sudo /usr/local/bin/log-collector --exfil /etc/shadow
sudo journalctl -k | tail -5 | grep DENIED

# Profile lisible sans surprise
sudo cat /etc/apparmor.d/usr.local.bin.log-collector | grep -v ^#
```
