## 🧠 Théorie : qu'est-ce qu'un SIEM ?

```
   Sources hétérogènes        Pipeline SIEM              Sortie
   ────────────────────       ─────────────              ──────
   
   sshd auth.log     ┐                                
   nginx access      │      ┌─────────┐               
   firewall iptables ├────► │ Collect │ ───┐          
   Windows EventLog  │      └─────────┘    │          
   k8s audit log     │                     ▼          
   AWS CloudTrail    │             ┌──────────────┐   
   EDR (osquery)     ┘             │  Normalize   │   
                                   │  (ECS/wazuh) │   
                                   └──────┬───────┘   
                                          ▼          
                                   ┌──────────────┐   
                                   │   Correlate  │ ─► Règles
                                   │  (rules eng) │    composites
                                   └──────┬───────┘   
                                          ▼          
                                   ┌──────────────┐   
                                   │    Alert     │ ─► SOC
                                   │    Store     │    Slack/email
                                   │    Search    │    Tableau de bord
                                   └──────────────┘   
```

### Composants Wazuh

| Composant | Rôle |
|---|---|
| **wazuh-manager** | Reçoit les events, décode, applique les règles, déclenche les alertes |
| **wazuh-indexer** | Stockage des events (OpenSearch fork) |
| **wazuh-dashboard** | UI (Kibana fork) |
| **wazuh-agent** | Sur chaque host, collecte logs + FIM + scans + active-response |
| **rulesets** | XML déclaratifs versionnés (rules + decoders + CDB lists) |

### Différence SIEM vs EDR vs XDR

```
   EDR    : focalisé endpoint (process, FS, syscalls)        — CrowdStrike, SentinelOne
   SIEM   : focalisé logs et events centralisés              — Splunk, Wazuh, Sentinel
   XDR    : SIEM + EDR + Network + Cloud unifiés             — Palo XSIAM, MS Defender XDR
   SOAR   : automatise les réponses (orchestration)          — Splunk SOAR, Tines, Shuffle
```

## 🎯 Objectif

Installer une stack **Wazuh** complète, brancher un agent sur une seconde machine, déclencher une détection (brute-force SSH) et investiguer dans Wazuh Dashboard.

## 📋 Étape 1 — Installer Wazuh manager (Docker)

Sur la VM **manager** :

```bash
git clone https://github.com/wazuh/wazuh-docker.git -b v4.7.5
cd wazuh-docker/single-node
docker compose -f generate-indexer-certs.yml run --rm generator
docker compose up -d
```

Patientez ~3 minutes que tous les conteneurs soient `healthy`. Accédez à `https://<ip-manager>` (admin / SecretPassword).

Vérifiez les services :

```bash
docker compose ps
# wazuh.manager  ........ Up (healthy)
# wazuh.indexer  ........ Up (healthy)
# wazuh.dashboard  ...... Up (healthy)
```

## 📋 Étape 2 — Enregistrer un agent

Récupérez la clé d'enregistrement :

```bash
docker exec -it single-node-wazuh.manager-1 \
  /var/ossec/bin/manage_agents
# A → ajouter un agent, donnez un nom et l'IP cible
# E → extraire la clé
```

Sur la VM **cible** :

```bash
WAZUH_MANAGER='<ip-manager>' apt install wazuh-agent
echo "<CLE_BASE64>" | /var/ossec/bin/manage_agents -i
systemctl enable --now wazuh-agent
```

Dans le dashboard, l'agent passe **Active** au bout d'une minute.

## 📋 Étape 3 — Comprendre les règles Wazuh

Wazuh fournit la règle **5712** (`SSH authentication failed`) et **5710** (`Multiple authentication failures`). Anatomie :

```xml
<!-- /var/ossec/ruleset/rules/0095-sshd_rules.xml -->
<rule id="5712" level="5">
  <if_sid>5700</if_sid>
  <match>Failed password</match>
  <description>sshd: authentication failed.</description>
  <mitre>
    <id>T1110.001</id>
  </mitre>
  <group>authentication_failed,pci_dss_10.2.4,...</group>
</rule>

<rule id="5710" level="10" frequency="8" timeframe="120">
  <if_matched_sid>5712</if_matched_sid>
  <same_source_ip />
  <description>sshd: Multiple authentication failures.</description>
  <mitre>
    <id>T1110.001</id>
  </mitre>
</rule>
```

### Décodage

- `level="5"` → événement (loggé), pas alerté
- `level="10"` → alerte significative (déclenche notif + dashboard)
- `if_matched_sid="5712"` → corrélation : on attend N matches de la règle parent
- `frequency=8` / `timeframe=120` → 8 fois en 2 min depuis même IP
- `<mitre>` → contexte adversaire
- `<group>` → compliance + classification (PCI-DSS, NIST 800-53, GDPR)

## 📋 Étape 4 — Simuler l'attaque

Depuis votre poste, vers la VM cible :

```bash
for i in $(seq 1 20); do
  sshpass -p wrongpass ssh -o StrictHostKeyChecking=no \
    fakeuser@<ip-cible> exit 2>/dev/null
done
```

## 📋 Étape 5 — Investigation

Dans **Wazuh Dashboard → Security events** :

1. Filtrez sur `rule.id: 5710` ou `rule.level >= 10`
2. Vous voyez l'alerte **"sshd: Multiple authentication failures"**
3. Cliquez sur un événement → champ `data.srcip` = votre poste
4. Onglet **MITRE ATT&CK** → mappé sur **T1110.001 Brute Force: Password Guessing**

### Investigation guidée

Pour reconstruire le scénario complet :

```
1. timestamp du premier 5712 (failed password)
2. source.ip de l'attaque
3. quels users ont été testés ? (data.dstuser)
4. y a-t-il un 5715 (Successful authentication) dans le même timeframe ?
   → si oui, COMPROMISSION : isoler l'host, reset password
5. l'IP est-elle dans nos threat feeds ? (Wazuh → Threat Intel)
```

## 📋 Étape 6 — Réagir automatiquement

Activez l'**active-response** `firewall-drop` dans `/var/ossec/etc/ossec.conf` sur l'agent :

```xml
<active-response>
  <command>firewall-drop</command>
  <location>local</location>
  <rules_id>5710</rules_id>
  <timeout>600</timeout>
</active-response>
```

Relancez le brute-force : l'IP est **bannie 10 minutes** via iptables.

> ⚠️ Toujours ajouter une **allowlist** (`/var/ossec/etc/ossec.conf` → `<white_list>`) avec les IP de votre infra, monitoring, bastions. Sinon un faux positif peut bloquer la prod.

## 📋 Étape 7 — File Integrity Monitoring (bonus)

Wazuh peut surveiller les fichiers sensibles :

```xml
<!-- ossec.conf de l'agent -->
<syscheck>
  <directories check_all="yes" realtime="yes">/etc</directories>
  <directories check_all="yes" realtime="yes">/usr/bin,/usr/sbin</directories>
  <ignore>/etc/mtab</ignore>
  <ignore>/etc/random-seed</ignore>
</syscheck>
```

Modifiez `/etc/passwd` → alerte **rule 550** (Integrity checksum changed) instantanément.

## 🧠 Anti-patterns

❌ **Brancher tous les agents direct sur le manager sans hiérarchie** : > 1000 agents = saturation manager.
❌ **Désactiver toutes les règles "bruyantes" sans investigation** : on perd la baseline.
❌ **Active-response sans allowlist** : ban accidentel d'un VPN corp.
❌ **Ne pas tester les règles custom** : on découvre que la règle est silencieuse pendant un incident.
❌ **Garder 30 jours d'event en chaud** : coût + perfs. Hot/Warm/Cold tiering obligatoire à l'échelle.
