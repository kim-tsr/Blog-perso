  - question: "Pourquoi compiler une app avec '-fno-omit-frame-pointer' aide le profiling ?"
    options:

## 🧠 Théorie : sampling profiler en 1 schéma

```
   Pendant que ton app tourne :
   
   Time ───────────────────────────────────────────►
   
    │ samp │  samp │  samp │  samp │  samp │  samp │
    ▼      ▼       ▼       ▼       ▼       ▼       ▼
   ┌─────┐┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐
   │stack││stack│ │stack│ │stack│ │stack│ │stack│
   │main │ main │ main │ main │ main │ main 
   │ srv │  srv │  srv │  srv │  srv │  srv
   │ pars│  pars│  comp│  comp│  comp│  comp
   │ regx│  regx│  hash│      │      │  hash
   └─────┘└─────┘ └─────┘ └─────┘ └─────┘ └─────┘
   
   Agrégation :
   - main → srv → pars → regx  : 33% (2/6)
   - main → srv → comp → hash  : 33%
   - main → srv → comp         : 17%
   - main → srv → comp → ...   : 17%
   
   Conclusion : regx ET hash chacun 33% du CPU.
   Avec 99 Hz et 60s tu as ~6000 samples → statistique fiable.
```

### Pourquoi 99 Hz et pas 100 ?

99 (premier > 100, et impair) évite l'aliasing avec les timers à 100/1000 Hz du kernel et de certains drivers. Tu mesures vraiment ton app, pas un battement périodique.

### Qu'est-ce qu'un flame graph ?

```
   ┌─────────────────────────────────────────────────┐  ← Y = profondeur stack
   │              srv (60%)                          │
   ├──────────────────┬──────────────────────────────┤
   │  pars (30%)      │  comp (30%)                  │
   ├─────────┬────────┼──────────┬───────────────────┤
   │ regx 15%│ json15%│ hash 20% │   marshal 10%     │
   ├─────────┼────────┼──────────┼───────────────────┤
   │ malloc 5│        │ siphash13│                   │
   └─────────────────────────────────────────────────┘  ← largeur = % CPU
   
   X = stacks groupées (PAS le temps !)
   Tout en bas : main / entry point
   Tout en haut : fonctions leaf
   Largeur = % du CPU passé là (cumul)
```

→ pour trouver l'optimisation rentable : cherche le **plus large bloc** vers le haut.

## 📋 Étape 2 — Une app à profiler

```c
// hashloop.c — beaucoup de hashing inutile
#include <stdio.h>
#include <string.h>
#include <stdint.h>

uint32_t fnv1a(const char *s) {
    uint32_t h = 2166136261u;
    while (*s) { h ^= (unsigned char)*s++; h *= 16777619u; }
    return h;
}

int main() {
    const char *msg = "the quick brown fox jumps over the lazy dog";
    uint64_t sum = 0;
    for (int i = 0; i < 50000000; i++) sum += fnv1a(msg);
    printf("sum=%llu\n", (unsigned long long)sum);
    return 0;
}
```

```bash
gcc -O2 -fno-omit-frame-pointer -g hashloop.c -o hashloop
time ./hashloop
# real 4.5s  user 4.5s  sys 0s
```

## 📋 Étape 3 — Capturer un profil

```bash
sudo sysctl kernel.perf_event_paranoid=1   # ou -1 en lab
sudo perf record -F 99 -g -- ./hashloop

# Affichage texte
sudo perf report --stdio | head -30
```

→ tu vois en tête les fonctions qui consomment le + (overhead column).

## 📋 Étape 4 — Générer le flame graph

```bash
sudo perf script > out.stacks
~/FlameGraph/stackcollapse-perf.pl out.stacks > out.folded
~/FlameGraph/flamegraph.pl out.folded > flamegraph.svg

# Ouvrir dans un navigateur
xdg-open flamegraph.svg
```

Tu vois un SVG **interactif** :
- clic sur une fonction → zoom
- Ctrl-F → recherche
- couleurs aléatoires (sans signification)

Pour notre `hashloop` : `fnv1a` prend ~95% du temps, c'est le hot path.

## 📋 Étape 5 — Optimiser et re-mesurer

```c
// Version optimisée : précalculer le hash, ne pas le refaire
int main() {
    const char *msg = "the quick brown fox jumps over the lazy dog";
    uint32_t hash = fnv1a(msg);
    uint64_t sum = (uint64_t)hash * 50000000ULL;
    printf("sum=%llu\n", (unsigned long long)sum);
    return 0;
}
```

```bash
gcc -O2 -fno-omit-frame-pointer -g hashloop2.c -o hashloop2
time ./hashloop2     # → 0.001s
```

Bon, c'était évident sur ce cas trivial. En réel :
1. Profile → flame graph
2. Identifie la fonction la + large
3. Vérifie : appelée trop souvent ? Algorithme inefficient ? Bug N² ?
4. Patch
5. Re-profile pour confirmer

## 📋 Étape 6 — Profiler une app déjà en cours

Pour un service prod :

```bash
sudo perf record -F 99 -g -p $(pgrep -f myservice) -- sleep 30
# 30s de capture, puis stop
```

Ou tout le système (utile sur app très threadée) :

```bash
sudo perf record -F 99 -ag -- sleep 30
```

## 📋 Étape 7 — Profiling Python / Node / Java

### Python

```bash
# py-spy : sampling profiler externe (pas besoin de modifier l'app)
pip install py-spy
sudo py-spy record -o profile.svg --pid $(pgrep -f myapp.py)
# → profile.svg en flame graph directement
```

### Node.js

```bash
node --perf-basic-prof myapp.js   # active le mapfile JIT pour perf
# puis perf record/script normal
```

### Java

```bash
# async-profiler : THE référence
./profiler.sh -d 30 -f profile.html $(pgrep -f java)
```

Toutes ces stacks (mixed kernel/userspace) sont aussi visualisables en flame graph.

## 📋 Étape 8 — Cas avancés

### Profiler les cache misses (au lieu de cycles CPU)

```bash
sudo perf record -e cache-misses -g -- ./app
```

→ flame graph des fonctions qui causent le + de cache miss. Utile pour optimiser la localité mémoire.

### Profiler les off-CPU (temps bloqué)

```bash
sudo perf record -e sched:sched_switch -g -- ./app
```

→ tu vois où ton app passe son temps **endormie** (I/O, lock, mutex). Indispensable pour les apps réseau-bound.

### Heat map de latence

```bash
~/FlameGraph/HeatMap/HeatMap.pl < perf-out.txt > heatmap.svg
```

→ matrice latence × temps. Détecte les "queue de distribution" (tail latency).

## 🧠 Pitfalls

❌ **Profiler avec `-O0`** : tu mesures du code non optimisé, sans rapport avec la prod.
❌ **`perf_event_paranoid` trop strict** en lab → "Permission denied". Mets à `-1` temporairement.
❌ **Symbols manquants** → `0x????` partout. Installe les `-dbgsym` ou compile avec `-g`.
❌ **Tirer des conclusions sur 100 samples** : pas représentatif. Vise au moins 1000-10000.
❌ **Comparer 2 flame graphs sans même axe X** : utilise `difffolded.pl` pour diff coloré rouge/vert.
❌ **Ignorer le bruit GC / JIT** sur Java/Node : profile en steady-state, après warmup.

## 🔬 Validation

```bash
# 1. Capture
sudo perf record -F 99 -g -- ./hashloop
ls perf.data    # fichier généré

# 2. Top hot function
sudo perf report --stdio --no-children | head -10
# → fnv1a en tête

# 3. Flame graph généré
ls flamegraph.svg

# 4. Vérifie le contenu : on doit voir fnv1a > 90% en largeur
grep -o 'fnv1a' flamegraph.svg | wc -l > 0
```
