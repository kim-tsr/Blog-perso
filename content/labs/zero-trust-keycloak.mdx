## 🧠 Théorie : pourquoi Zero Trust ?

Le modèle de sécurité périmétrique — le « château fort » — repose sur une prémisse simple : ce qui est à l'intérieur du réseau est de confiance, ce qui est à l'extérieur ne l'est pas. Ce modèle a fonctionné quand les applications tournaient dans un datacenter physique unique, quand les employés travaillaient depuis le bureau, et quand les périmètres étaient stables.

Il est aujourd'hui fondamentalement cassé. Les applications sont dans le cloud, les données dans des SaaS, les développeurs travaillent de partout, et les fournisseurs ont des accès VPN. Le périmètre n'existe plus. Et surtout : une fois le périmètre franchi, l'attaquant se déplace **latéralement** sans obstacle — un seul point d'entrée compromis donne accès à tout ce qui fait confiance à ce qui est « dedans ». Les rapports d'incident (Verizon DBIR, Mandiant M-Trends) montrent année après année que ce mouvement latéral interne est au cœur des intrusions majeures.

Zero Trust répond à cette réalité avec un principe radical : **Never trust, always verify**. Pas de confiance implicite basée sur la position réseau, l'IP source, ou le VPN. À chaque requête vers chaque ressource, on vérifie : qui demande, depuis quel device, dans quel contexte, avec quelle sensibilité de ressource. La vérification est continue, pas one-shot au login.

### Tenets NIST et 5 piliers de maturité (CISA)

Deux références à ne pas confondre. Le **NIST SP 800-207** (2020) est le document fondateur : il énonce 7 *tenets* (ressources, sessions, vérification dynamique...) et une architecture logique en trois organes — **PE** (Policy Engine, décide), **PA** (Policy Administrator, applique la décision), **PEP** (Policy Enforcement Point, exécute sur le flux). Keycloak joue ici le rôle de PE/PA pour l'identité, oauth2-proxy et Cilium celui de PEP.

Le modèle des **5 piliers** vient du **CISA Zero Trust Maturity Model (ZTMM)**, qui opérationnalise ces principes en domaines mesurables. Chaque pilier est un axe de maturité indépendant — une organisation peut être mature sur l'identité et faible sur le réseau. Beaucoup commencent par l'identité, car c'est le vecteur d'attaque numéro 1 (phishing, credential stuffing, vol de session).

### OIDC : le protocole d'identité fédérée

OpenID Connect (OIDC) est une couche d'identité construite par-dessus OAuth 2.0. OAuth 2.0 résout le problème d'**autorisation déléguée** (une app peut agir pour le compte d'un user, avec son consentement, sans voir son mot de passe). OIDC y ajoute l'**authentification** : une preuve cryptographique de l'identité de l'utilisateur, encodée dans un ID Token (JWT).

Il existe plusieurs types de flows OIDC, chacun adapté à un type de client différent :

Le **PKCE** (Proof Key for Code Exchange, RFC 7636) est un mécanisme de sécurité qui protège contre l'interception du `code` par une autre app sur le même device. Le client génère un `code_verifier` aléatoire, en calcule le hash (`code_challenge`), et envoie le hash avec la requête initiale. Lors de l'échange du code contre le token, il envoie le `code_verifier` original — Keycloak vérifie que le hash correspond. Même si le code est intercepté, il est inutilisable sans le `code_verifier`.

### Scopes vs Claims : quelle différence ?

Les **scopes** sont des permissions demandées par le client à l'IdP : `openid` (obligatoire pour OIDC), `profile` (nom, prénom), `email`, `roles`. Ce sont des chaînes de texte dans la requête d'autorisation.

Les **claims** sont les assertions dans le token lui-même, correspondant aux scopes accordés. Le scope `profile` produit les claims `name`, `given_name`, `family_name`. Le scope `roles` produit le claim `realm_access.roles`. Les claims sont signés par l'IdP — leur intégrité est vérifiable par n'importe quel service ayant la clé publique JWKS de Keycloak.

Les **Refresh Tokens** permettent d'obtenir un nouvel access token sans re-login. Ils ont une durée de vie plus longue (heures à jours) et sont rotatifs dans Keycloak : à chaque usage, un nouveau refresh token est émis et l'ancien invalidé. En Zero Trust, on configure des access tokens courts (15 min) avec refresh : le client re-vérifie fréquemment l'identité et les droits, mais l'UX reste fluide.

## 📋 Étape 1 — Keycloak en k8s

```yaml
# keycloak.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: iam
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: keycloak
  namespace: iam
spec:
  replicas: 1
  selector:
    matchLabels: {app: keycloak}
  template:
    metadata:
      labels: {app: keycloak}
    spec:
      containers:
        - name: keycloak
          image: quay.io/keycloak/keycloak:24.0
          args: ["start-dev"]
          env:
            - {name: KC_DB, value: postgres}
            - {name: KC_DB_URL, value: "jdbc:postgresql://postgres:5432/keycloak"}
            - {name: KEYCLOAK_ADMIN, value: admin}
            - {name: KEYCLOAK_ADMIN_PASSWORD, valueFrom: {secretKeyRef: {name: kc-admin, key: password}}}
          ports: [{containerPort: 8080}]
---
apiVersion: v1
kind: Service
metadata:
  name: keycloak
  namespace: iam
spec:
  selector: {app: keycloak}
  ports: [{port: 8080}]
```

On utilise un `StatefulSet` plutôt qu'un `Deployment` parce que Keycloak en mode cluster requiert une identité stable pour les communications Infinispan (distributed cache). En mode `start-dev` (dev uniquement), ce point n'est pas critique, mais l'habitude de `StatefulSet` pour les IdPs avec état est bonne à prendre. Le mot de passe admin est récupéré depuis un Secret Kubernetes — ne jamais l'inliner dans le YAML.

> ⚠️ Le manifeste ci-dessus déclare `KC_DB=postgres` et pointe vers un service `postgres:5432` : il suppose donc qu'une instance PostgreSQL tourne déjà dans le namespace `iam` (sinon le pod boucle en `CrashLoopBackOff`). Pour un premier essai rapide, retirez les variables `KC_DB`/`KC_DB_URL` : `start-dev` utilisera alors une base H2 en mémoire, suffisante pour le lab mais **non persistante** (tout est perdu au redémarrage du pod). Pour persister, déployez un Postgres (`StatefulSet` + PVC) au préalable.

```bash
kubectl apply -f keycloak.yaml
kubectl port-forward -n iam svc/keycloak 8080:8080
# http://localhost:8080/admin (admin/SECRET)
```

## 📋 Étape 2 — Créer un realm + client OIDC

Dans l'UI Keycloak :

1. **Create realm** → `homelab`
2. **Clients → Create** :
   - Client ID: `kibana`
   - Type: OpenID Connect
   - Access Type: confidential
   - Valid Redirect URIs: `https://kibana.homelab.lan/oauth2/callback`
3. Note le **Client Secret** dans Credentials
4. **Users → Create** → alice, mot de passe temporaire + reset

Un **realm** dans Keycloak est un namespace isolé avec ses propres users, clients, rôles et configurations. Le realm `master` est réservé à l'administration Keycloak lui-même. Toutes vos applications utilisent des realms séparés — c'est un principe de séparation des préoccupations.

Un client `confidential` (par opposition à `public`) dispose d'un `client_secret` connu uniquement du serveur — le client doit s'authentifier auprès de Keycloak avant d'obtenir un token. C'est obligatoire pour les apps server-side. Les SPAs (JavaScript front-end) utilisent des clients `public` avec PKCE obligatoire.

## 📋 Étape 3 — oauth2-proxy devant une app

```yaml
# oauth2-proxy.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: oauth2-proxy
  namespace: monitoring
spec:
  replicas: 1
  selector: {matchLabels: {app: oauth2-proxy}}
  template:
    metadata: {labels: {app: oauth2-proxy}}
    spec:
      containers:
      - name: proxy
        image: quay.io/oauth2-proxy/oauth2-proxy:v7.6.0
        args:
        - --provider=keycloak-oidc
        - --oidc-issuer-url=https://keycloak.homelab.lan/realms/homelab
        - --client-id=kibana
        - --upstream=http://kibana:5601
        - --redirect-url=https://kibana.homelab.lan/oauth2/callback
        - --email-domain=*
        - --cookie-secure=true
        - --pass-access-token=true
        env:
        - {name: OAUTH2_PROXY_CLIENT_SECRET, valueFrom: {secretKeyRef: {name: kibana-oidc, key: secret}}}
        - {name: OAUTH2_PROXY_COOKIE_SECRET, valueFrom: {secretKeyRef: {name: kibana-oidc, key: cookie}}}
        ports: [{containerPort: 4180}]
```

oauth2-proxy implémente le pattern « **sidecar auth** ». Il se place devant l'application upstream (`--upstream=http://kibana:5601`) et intercepte chaque requête. Si le cookie de session est absent ou expiré, il redirige vers Keycloak. Si le token est valide, il passe la requête à Kibana en ajoutant les headers `X-Forwarded-User`, `X-Forwarded-Email`, `Authorization: Bearer <token>`. Kibana reçoit une requête déjà authentifiée sans avoir besoin de connaître Keycloak.

`--pass-access-token=true` injecte l'access token Keycloak dans un header `X-Forwarded-Access-Token` — utile si Kibana (ou une app custom) veut vérifier les rôles ou appeler des APIs tierces avec le token de l'utilisateur.

Ingress route : `https://kibana.homelab.lan` → oauth2-proxy → kibana. Toute requête sans token valide → redirect login Keycloak.

## 📋 Étape 4 — Microsegmentation Cilium L7

```yaml
# default-deny pour tout le ns
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: default-deny
  namespace: monitoring
spec:
  endpointSelector: {}
  ingress: []
  egress: []
---
# kibana peut être contacté par oauth2-proxy uniquement, et sur path /api/* uniquement
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: kibana-allow
  namespace: monitoring
spec:
  endpointSelector:
    matchLabels: {app: kibana}
  ingress:
  - fromEndpoints:
    - matchLabels: {app: oauth2-proxy}
    toPorts:
    - ports: [{port: "5601", protocol: TCP}]
      rules:
        http:
        - method: "GET"
          path: "/api/.*"
        - method: "GET"
          path: "/"
  egress:
  - toEndpoints:
    - matchLabels: {app: elasticsearch}
    toPorts:
    - ports: [{port: "9200", protocol: TCP}]
```

La politique `default-deny` avec `endpointSelector: {}` (tous les endpoints du namespace) et `ingress: []` / `egress: []` (listes vides = tout refusé) est le principe fondateur de la microsegmentation : **default-deny, allowlist explicite**. Sans cette politique, Kubernetes autorise par défaut tout trafic entre pods — l'inverse de Zero Trust.

La règle `kibana-allow` illustre la puissance de Cilium L7 : elle ne se contente pas d'autoriser le trafic TCP vers le port 5601, elle va jusqu'au niveau applicatif HTTP (`rules.http`) pour n'autoriser que les méthodes GET sur les paths `/api/.*` et `/`. Cilium inspecte le protocole applicatif via un proxy Envoy injecté par eBPF — une granularité impossible avec des NetworkPolicies Kubernetes standard (qui opèrent en L3/L4 uniquement).

> ⚠️ Le filtre `GET` seul est **pédagogique** : un vrai Kibana a besoin de `POST` (recherches, sauvegardes) et de WebSockets. Ne reproduisez ce verrouillage L7 strict que sur des APIs réellement en lecture seule. Notez aussi que le filtrage L7 a un coût : chaque connexion concernée transite par le proxy Envoy de Cilium (légère latence et CPU en plus), à réserver aux flux sensibles plutôt qu'à tout le cluster.

→ même si quelqu'un compromet le pod monitoring/curl-tool, il ne peut **pas** parler à kibana directement (ingress refusé). Seul oauth2-proxy peut. Et oauth2-proxy ne sert que les paths autorisés.

## 📋 Étape 5 — Vérifier avec Hubble

```bash
hubble observe --namespace monitoring --to-pod kibana
# → tu vois UNIQUEMENT les flows oauth2-proxy → kibana sur :5601
# → un curl from autre pod = "DROPPED by network policy"
```

Test manuel :

```bash
kubectl run debug --image=curlimages/curl -n monitoring --rm -it -- sh
/ # curl http://kibana:5601/
# → timeout (drop par CNP)

hubble observe --verdict DROPPED
# → ligne avec policy="kibana-allow"
```

Hubble est l'outil d'observabilité réseau de Cilium. Il expose un flux temps réel de tous les événements réseau (allows et drops) avec le contexte Kubernetes complet (namespace, pod, label, policy). La commande `--verdict DROPPED` filtre uniquement les paquets refusés par une network policy — c'est votre outil de debugging et d'audit de conformité Zero Trust.

## 📋 Étape 6 — Conditional Access

Dans Keycloak : **Authentication → Flows → Browser** → ajouter un `Conditional Subflow` :

```
   Browser flow
   ├── Cookie       (skip si déjà session)
   ├── Identity Provider Redirect
   └── Browser Forms
       ├── Username Password Form
       └── Conditional OTP
           ├── Condition: User Configured
           └── OTP Form
```

Le flow d'authentification Keycloak est un graphe de décision configurable. Chaque nœud est un « authenticator » : il peut s'exécuter (Required), être optionnel (Optional), ou être conditionnel (Conditional, avec une `Condition` qui évalue le contexte). La structure ci-dessus implémente un MFA adaptatif : TOTP demandé seulement aux utilisateurs qui l'ont configuré, obligatoire pour le rôle `admin`.

→ MFA TOTP optionnel si user l'a configuré, obligatoire si user appartient au role `admin`.

Tu peux aussi conditionner sur le **device**: requiert Tailscale device tagged `corp` pour accéder à kibana.

## 🧠 Pitfalls

❌ **Keycloak admin password en clair dans yaml** : utilise SealedSecrets ou ExternalSecrets.
❌ **`start-dev` en prod** : HTTP only, optimisations désactivées. Utilise `start` + reverse-proxy TLS.
❌ **NetworkPolicies sans default-deny** : tout reste autorisé sauf ce que tu listes. Inverse l'intention.
❌ **OIDC client public alors qu'on est confidential** : permet de récupérer le client_secret depuis JS.
❌ **Pas de tests d'arrêt IdP** : si Keycloak tombe, plus AUCUNE app accessible. HA obligatoire.
