## 🧠 Théorie : pourquoi Zero Trust ?

### Le château fort vs Zero Trust

```
   MODÈLE PÉRIMÉTRIQUE (château fort)
   ────────────────────────────────────
   
       Internet
          │
          ▼
   ┌─────FIREWALL─────┐
   │  TRUSTED LAN     │  ← une fois dedans, libre circulation
   │  ┌────┐  ┌────┐  │     entre tous les serveurs
   │  │app1│  │app2│  │     ⚠️ déplacement latéral facile
   │  └────┘  └────┘  │
   └──────────────────┘

   MODÈLE ZERO TRUST
   ─────────────────
   
       Internet ─ User ─ LAN ─ DMZ : tous traités pareil
                         │
                         ▼
           Chaque requête vers chaque service :
              ┌────────────────────────────┐
              │ 1. Identité valide ?       │
              │ 2. Device compliant ?       │
              │ 3. Policy autorise ?       │
              │ 4. Step-up MFA ?           │
              └────────────────────────────┘
              ↓ si tout OK ↓
                 ACCÈS SCOPED
```

### Les 5 piliers NIST SP 800-207

| Pilier | Question | Outils |
|---|---|---|
| **Identité** | Qui est-ce vraiment ? | Keycloak, Authentik, Okta, Azure AD |
| **Device** | Depuis quel équipement ? | Tailscale tags, Intune, Jamf, Kolide |
| **Réseau** | Quel chemin ? | Cilium NetworkPolicies, mTLS |
| **Workload** | Le service appelé a-t-il son ID ? | SPIFFE/SPIRE, service mesh |
| **Data** | Quelle sensibilité ? | DLP, classification, encryption |

### Architecture cible

```
   Client ──► Cloudflare ──► oauth2-proxy ──► App
                                  ▲
                                  │ OIDC
                                  ▼
                              Keycloak
                              (IdP central)
                                  │
                                  ▼
                       LDAP/OIDC fédéré
```

## 🎯 Objectif

1. Déployer Keycloak en cluster.
2. Brancher une app legacy via oauth2-proxy.
3. Appliquer des NetworkPolicies Cilium L3-L7.
4. Mesurer (Hubble) qu'aucun flow non autorisé ne passe.

## 📋 Étape 1 — Keycloak en k8s

```yaml
# keycloak.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: iam
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: keycloak
  namespace: iam
spec:
  replicas: 1
  selector:
    matchLabels: {app: keycloak}
  template:
    metadata:
      labels: {app: keycloak}
    spec:
      containers:
        - name: keycloak
          image: quay.io/keycloak/keycloak:24.0
          args: ["start-dev"]
          env:
            - {name: KC_DB, value: postgres}
            - {name: KC_DB_URL, value: "jdbc:postgresql://postgres:5432/keycloak"}
            - {name: KEYCLOAK_ADMIN, value: admin}
            - {name: KEYCLOAK_ADMIN_PASSWORD, valueFrom: {secretKeyRef: {name: kc-admin, key: password}}}
          ports: [{containerPort: 8080}]
---
apiVersion: v1
kind: Service
metadata:
  name: keycloak
  namespace: iam
spec:
  selector: {app: keycloak}
  ports: [{port: 8080}]
```

```bash
kubectl apply -f keycloak.yaml
kubectl port-forward -n iam svc/keycloak 8080:8080
# http://localhost:8080/admin (admin/SECRET)
```

## 📋 Étape 2 — Créer un realm + client OIDC

Dans l'UI Keycloak :

1. **Create realm** → `homelab`
2. **Clients → Create** :
   - Client ID: `kibana`
   - Type: OpenID Connect
   - Access Type: confidential
   - Valid Redirect URIs: `https://kibana.homelab.lan/oauth2/callback`
3. Note le **Client Secret** dans Credentials
4. **Users → Create** → alice, mot de passe temporaire + reset

## 📋 Étape 3 — oauth2-proxy devant une app

```yaml
# oauth2-proxy.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: oauth2-proxy
  namespace: monitoring
spec:
  replicas: 1
  selector: {matchLabels: {app: oauth2-proxy}}
  template:
    metadata: {labels: {app: oauth2-proxy}}
    spec:
      containers:
      - name: proxy
        image: quay.io/oauth2-proxy/oauth2-proxy:v7.6.0
        args:
        - --provider=keycloak-oidc
        - --oidc-issuer-url=https://keycloak.homelab.lan/realms/homelab
        - --client-id=kibana
        - --upstream=http://kibana:5601
        - --redirect-url=https://kibana.homelab.lan/oauth2/callback
        - --email-domain=*
        - --cookie-secure=true
        - --pass-access-token=true
        env:
        - {name: OAUTH2_PROXY_CLIENT_SECRET, valueFrom: {secretKeyRef: {name: kibana-oidc, key: secret}}}
        - {name: OAUTH2_PROXY_COOKIE_SECRET, valueFrom: {secretKeyRef: {name: kibana-oidc, key: cookie}}}
        ports: [{containerPort: 4180}]
```

Ingress route : `https://kibana.homelab.lan` → oauth2-proxy → kibana. Toute requête sans token valide → redirect login Keycloak.

## 📋 Étape 4 — Microsegmentation Cilium L7

```yaml
# default-deny pour tout le ns
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: default-deny
  namespace: monitoring
spec:
  endpointSelector: {}
  ingress: []
  egress: []
---
# kibana peut être contacté par oauth2-proxy uniquement, et sur path /api/* uniquement
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: kibana-allow
  namespace: monitoring
spec:
  endpointSelector:
    matchLabels: {app: kibana}
  ingress:
  - fromEndpoints:
    - matchLabels: {app: oauth2-proxy}
    toPorts:
    - ports: [{port: "5601", protocol: TCP}]
      rules:
        http:
        - method: "GET"
          path: "/api/.*"
        - method: "GET"
          path: "/"
  egress:
  - toEndpoints:
    - matchLabels: {app: elasticsearch}
    toPorts:
    - ports: [{port: "9200", protocol: TCP}]
```

→ même si quelqu'un compromet le pod monitoring/curl-tool, il ne peut **pas** parler à kibana directement (ingress refusé). Seul oauth2-proxy peut. Et oauth2-proxy ne sert que les paths autorisés.

## 📋 Étape 5 — Vérifier avec Hubble

```bash
hubble observe --namespace monitoring --to-pod kibana
# → tu vois UNIQUEMENT les flows oauth2-proxy → kibana sur :5601
# → un curl from autre pod = "DROPPED by network policy"
```

Test manuel :

```bash
kubectl run debug --image=curlimages/curl -n monitoring --rm -it -- sh

# → timeout (drop par CNP)

hubble observe --verdict DROPPED
# → ligne avec policy="kibana-allow"
```

## 📋 Étape 6 — Conditional Access

Dans Keycloak : **Authentication → Flows → Browser** → ajouter un `Conditional Subflow` :

```
   Browser flow
   ├── Cookie       (skip si déjà session)
   ├── Identity Provider Redirect
   └── Browser Forms
       ├── Username Password Form
       └── Conditional OTP
           ├── Condition: User Configured
           └── OTP Form
```

→ MFA TOTP optionnel si user l'a configuré, obligatoire si user appartient au role `admin`.

Tu peux aussi conditionner sur le **device**: requiert Tailscale device tagged `corp` pour accéder à kibana.

## 🧠 Pitfalls

❌ **Keycloak admin password en clair dans yaml** : utilise SealedSecrets ou ExternalSecrets.
❌ **`start-dev` en prod** : HTTP only, optimisations désactivées. Utilise `start` + reverse-proxy TLS.
❌ **NetworkPolicies sans default-deny** : tout reste autorisé sauf ce que tu listes. Inverse l'intention.
❌ **OIDC client public alors qu'on est confidential** : permet de récupérer le client_secret depuis JS.
❌ **Pas de tests d'arrêt IdP** : si Keycloak tombe, plus AUCUNE app accessible. HA obligatoire.

## ✅ Validation

- Login alice via Keycloak → access kibana
- `curl` direct kibana sans token → 302 vers /oauth2/start
- `hubble observe --verdict DROPPED` montre les tentatives non-autorisées
- MFA forcé pour role admin

## 🚀 Pour aller plus loin

- **SPIFFE/SPIRE** : identité workload (mTLS automatique entre services)
- **Tailscale** : Zero Trust device layer + ACLs déclaratives
- **Cloudflare Access** ou **BeyondCorp** GCP : équivalents managés
- **Open Policy Agent (OPA)** : moteur de policy unifié (k8s admission + microservices)
- **Pomerium** : alternative à oauth2-proxy avec plus de features (per-route policies)
