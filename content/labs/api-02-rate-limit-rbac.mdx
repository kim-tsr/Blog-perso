## 🧠 Théorie : rate limiting et contrôle d'accès

Une API authentifiée (lab #1) est protégée contre les accès non autorisés. Elle n'est pas encore protégée contre deux classes d'abus distincts : la **surcharge** (un client légitime ou malveillant qui appelle trop vite) et le **dépassement de droits** (un client authentifié qui accède à des ressources qu'il n'est pas censé voir). Ce lab ajoute exactement ces deux couches.

### Les trois algorithmes de rate limiting

Le rate limiting répond à une question simple : "ce client a-t-il le droit de faire une requête de plus ?" La subtilité est dans la définition de "trop". Chaque algorithme donne une réponse différente avec des compromis distincts.

**Fixed window** est le plus naïf : on compte les requêtes dans une fenêtre de temps fixe (ex: par minute), et on bloque quand le compteur dépasse le seuil. Le problème est structurel : un attaquant peut envoyer 100 requêtes à 23:59:59 et 100 autres à 00:00:00 — soit 200 requêtes en 2 secondes, sans que l'algorithme le détecte. Ce burst aux frontières de fenêtre est un vecteur d'attaque classique.

**Token bucket** (seaux à jetons) est l'algorithme recommandé pour les APIs. Chaque client dispose d'un seau de N jetons. Chaque requête consomme un jeton. Les jetons se reconstituent en continu à un taux fixe (ex: 1 jeton toutes les 6 secondes = 10/min). Si le seau est vide → 429. L'avantage : les bursts légitimes sont tolérés (vider le seau d'un coup est OK), mais on ne peut pas dépasser le débit moyen sur la durée.

**Sliding window log** est le plus précis mais aussi le plus coûteux : on stocke le timestamp de chaque requête et on compte dans une fenêtre glissante. Pas de burst aux frontières, mais `O(N)` en mémoire par utilisateur avec N requêtes dans la fenêtre. Utile pour les APIs très sensibles au taux exact, moins pertinent à grande échelle.

### Pourquoi limiter par token (user) et non par IP

Limiter par IP pénalise des utilisateurs légitimes derrière le même NAT (bureau d'entreprise, opérateur mobile) dès qu'un seul d'entre eux consomme trop. Limiter par identité JWT isole correctement chaque utilisateur. En pratique on applique les deux : une limite IP très laxiste pour les endpoints non-authentifiés (anti-scan), et une limite par token pour tout ce qui est authentifié.

### RBAC vs ABAC : quand utiliser quoi

**RBAC** (Role-Based Access Control) associe des permissions à des rôles, et des rôles à des utilisateurs. C'est statique, lisible, rapide à évaluer, et suffisant pour la grande majorité des APIs. `viewer` peut lire, `editor` peut écrire, `admin` peut tout faire.

**ABAC** (Attribute-Based Access Control) calcule les droits dynamiquement depuis des attributs du user, de la ressource, et du contexte. "Un editor peut modifier un document si et seulement si il en est le propriétaire ET si c'est pendant les heures de bureau ET si le document n'est pas archivé." Plus puissant, mais la complexité des politiques est un risque : des règles mal combinées créent des failles difficiles à auditer.

La pratique industrielle combine les deux : RBAC pour les grandes lignes (qui peut accéder à quelle catégorie de ressource), ABAC pour les règles fines d'ownership ou de contexte.

## 📋 Étape 1 — Rate limiter Go + Redis

```go
// middleware/ratelimit.go
package middleware

import (
  "context"
  "fmt"
  "net/http"
  "time"

  "github.com/redis/go-redis/v9"
)

var ctx = context.Background() // contexte partagé pour les appels Redis

type Limiter struct {
  rdb       *redis.Client
  capacity  int     // tokens dans le bucket
  refillSec float64 // 1 token toutes les X secondes
}

func NewLimiter(rdb *redis.Client, capacity int, refillSec float64) *Limiter {
  return &Limiter{rdb, capacity, refillSec}
}

// algo : on stocke (tokens, last_refill_unix_ms)
// À chaque hit : on recalcule combien de tokens ont été refillés depuis last_refill
const luaScript = `
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local refill_sec = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

local data = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(data[1]) or capacity
local ts = tonumber(data[2]) or now

-- refill "lazy" : on rajoute les jetons accumulés depuis le dernier passage
local elapsed = (now - ts) / 1000.0
local refill = elapsed / refill_sec
tokens = math.min(capacity, tokens + refill)

-- TTL = temps pour remplir un bucket vide. Au-delà, l'état est inutile
-- (le bucket serait de toute façon plein) → nettoyage auto des inactifs.
local ttl = math.ceil(capacity * refill_sec)

if tokens < 1 then
  redis.call('HSET', key, 'tokens', tokens, 'ts', now)
  redis.call('EXPIRE', key, ttl)
  return 0
end

tokens = tokens - 1
redis.call('HSET', key, 'tokens', tokens, 'ts', now)
redis.call('EXPIRE', key, ttl)
return 1
`

// On précompile le script : EVALSHA évite de renvoyer le corps Lua à chaque appel.
var rlScript = redis.NewScript(luaScript)

func (l *Limiter) Allow(key string) bool {
  now := time.Now().UnixMilli()
  res, err := rlScript.Run(ctx, l.rdb, []string{key},
    l.capacity, l.refillSec, now).Int()
  if err != nil {
    // fail-closed : si Redis est down, on refuse plutôt que de laisser passer
    // un flood non compté. Choix discutable : certains préfèrent fail-open
    // pour la dispo. À décider selon le contexte (DDoS vs panne Redis).
    return false
  }
  return res == 1
}

func (l *Limiter) Middleware(next http.HandlerFunc) http.HandlerFunc {
  return func(w http.ResponseWriter, r *http.Request) {
    user := r.Header.Get("X-User")        // posé par auth middleware
    if user == "" {
      http.Error(w, "no user", 401); return
    }
    key := fmt.Sprintf("rl:%s", user)
    if !l.Allow(key) {
      w.Header().Set("Retry-After", "60")
      http.Error(w, "rate limited", 429); return
    }
    next(w, r)
  }
}
```

Points importants de cette implémentation :
- Le **script Lua** s'exécute de manière atomique dans Redis — c'est crucial. Sans atomicité, deux requêtes simultanées liraient le même compteur (ex: 3 tokens), décideraient toutes les deux d'autoriser, et écriraient chacune `2` : on aurait laissé passer 2 requêtes pour le prix d'une. Avec Lua, la lecture, le calcul du refill et l'écriture forment une seule opération indivisible côté Redis (Redis est mono-thread sur l'exécution des commandes).
- `redis.NewScript` + `.Run()` utilise `EVALSHA` : le corps du script n'est envoyé qu'une fois, ensuite seul son hash SHA1 transite — moins de bande passante par requête. La lib retombe automatiquement sur `EVAL` si Redis ne connaît pas encore le script (ex: après un flush).
- `HSET` stocke un hash avec deux champs (`tokens` et `ts`) sous la clé `rl:username` (on utilise `HSET` et non `HMSET`, déprécié depuis Redis 4.0). `EXPIRE` pose une TTL = capacité × taux de refill, ce qui nettoie automatiquement les buckets des utilisateurs inactifs sans job de nettoyage séparé.
- Le refill est calculé **à la demande** (`elapsed / refill_sec`) plutôt que par un job périodique — technique dite "lazy refill". Aucun processus background, aucun timer, tout se calcule au moment de la requête.
- `Allow` est **fail-closed** : si Redis tombe, on refuse la requête. C'est un arbitrage disponibilité/sécurité explicite — fail-open laisserait un attaquant flooder l'API pendant une panne Redis. À assumer selon ton modèle de menace.
- `Retry-After: 60` informe le client de la durée à attendre — conforme à la RFC 6585 (qui définit le code 429), et permet aux clients bien codés de faire un backoff automatique.

> 💡 **Pourquoi un script Lua ?** Sans, on aurait 2 round-trips Redis et une race condition entre lecture et écriture. Lua = atomique côté Redis.

## 📋 Étape 2 — RBAC avec table de permissions

Modèle simple :

```go
// rbac/rbac.go
package rbac

type Role string
const (
  Viewer Role = "viewer"
  Editor Role = "editor"
  Admin  Role = "admin"
)

// Map déclarative — production : DB ou Casbin policy
var perms = map[Role]map[string]bool{
  Viewer: {"documents:read": true},
  Editor: {"documents:read": true, "documents:write": true},
  Admin:  {"*": true}, // wildcard
}

func Can(role Role, action string) bool {
  if perms[role]["*"] { return true }
  return perms[role][action]
}
```

La convention `action:ressource` (ex: `documents:read`, `users:write`, `admin:configure`) est le standard de facto dans les systèmes d'autorisation modernes (Casbin, Oso, Cedar d'AWS). Elle est lisible dans les logs, testable unitairement, et supporte naturellement les wildcards (`documents:*`). En production, cette map serait stockée en base et chargée au démarrage, pas codée en dur.

Middleware :

```go
func RequirePerm(action string) func(http.HandlerFunc) http.HandlerFunc {
  return func(next http.HandlerFunc) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
      role := rbac.Role(r.Header.Get("X-Role"))
      if !rbac.Can(role, action) {
        http.Error(w, "forbidden: requires "+action, 403); return
      }
      next(w, r)
    }
  }
}
```

Le message d'erreur `"forbidden: requires " + action` est intentionnellement verbeux ici pour faciliter le debug. En production, on renverrait juste `403 Forbidden` sans détail — indiquer quelle permission manque aide un attaquant à cibler ses efforts.

> 🔗 **Continuité avec le Lab #1** — deux petites modifs sur le code du Lab #1 sont nécessaires :
> 1. **Issuer** : `login` doit lire le rôle depuis la requête (ou la DB) au lieu de le coder en dur. Remplace `"role": "user"` par une valeur lue, ex. `role := r.FormValue("role"); if role == "" { role = "user" }` puis `"role": role`. ⚠️ En vrai, le rôle vient de TA base, jamais d'un champ que le client contrôle — ici c'est uniquement pour tester les différents rôles en lab.
> 2. **Auth middleware** : après vérification du token, poser le rôle pour le RBAC en aval — `if role, ok := claims["role"].(string); ok { r.Header.Set("X-Role", role) }`. Comme au Lab #1, on a déjà fait `r.Header.Del("X-Role")` en entrée du middleware, donc le client ne peut pas l'usurper.

## 📋 Étape 3 — Chaîner les middlewares

```go
func main() {
  rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
  limit := middleware.NewLimiter(rdb, 10, 6.0) // 10 tokens, 1 / 6s

  // viewers ont accès en lecture
  http.HandleFunc("/api/docs",
    middleware.Auth(
      limit.Middleware(
        middleware.RequirePerm("documents:read")(listDocs))))

  // editors+ ont accès en écriture
  http.HandleFunc("/api/docs/create",
    middleware.Auth(
      limit.Middleware(
        middleware.RequirePerm("documents:write")(createDoc))))

  http.ListenAndServe(":8080", nil)
}
```

L'ordre d'imbrication des middlewares est intentionnel : Auth en premier (pas la peine de toucher à Redis si le token est invalide), Rate-limit en second (on connaît l'utilisateur, on peut compter par user), RBAC en dernier (vérification la plus coûteuse si Casbin est utilisé). Chaque middleware court-circuite la chaîne en retournant directement s'il refuse la requête.

## 🧠 Patterns avancés (pour aller plus loin)

### Tiered limits par rôle

```
Viewer  : 100 req/min   (bucket 100, refill 1/0.6s)
Editor  : 500 req/min   (bucket 500, refill 1/0.12s)
Admin   : illimité      (skip middleware)
```

Les limites différenciées par rôle servent deux objectifs : protéger le service (un viewer ne peut pas saturer l'API) et donner de la valeur aux tiers payants (l'editor ou l'admin ont des quotas plus larges). Le skip total pour l'admin est acceptable si le compte admin est protégé par MFA et que ses actions sont loggées (cf. Lab #3).

### ABAC en complément (ownership)

```go
// Editor peut update SES documents
if action == "documents:update" && resource.Owner != user.ID {
  return false
}
```

Cette règle ABAC s'ajoute *après* le check RBAC, pas à la place. Un editor a le rôle qui lui donne `documents:update`, mais l'ABAC affine : uniquement sur ses propres documents. C'est le pattern "coarse-grained RBAC + fine-grained ABAC" décrit dans le quiz.

### Distributed denial : circuit breaker

Si 50% des requests retournent 5xx en 1 min → couper le backend en amont.
