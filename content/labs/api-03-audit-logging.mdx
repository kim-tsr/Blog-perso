## 🧠 Théorie : ce qui fait un audit log forensiquement utile

Un log de sécurité n'est pas un log d'application ordinaire. Sa fonction primaire n'est pas le debug en temps réel — c'est la **reconstitution après incident**. Quand quelque chose tourne mal (intrusion, escalade de privilèges, fuite de données), l'audit log est la seule source de vérité sur ce qui s'est passé, qui l'a fait, et dans quel ordre. Sa qualité détermine si l'enquête prend 20 minutes ou 3 jours.

Trois propriétés distinguent un audit log forensiquement utile :

**Immuabilité** : un attaquant qui a compromis un service tentera d'effacer ou de modifier les logs. En production, les logs doivent être expédiés en temps réel vers un système séparé (Loki, Elasticsearch, S3) que le service n'a pas le droit de modifier. L'idéal est un pipeline unidirectionnel : le service ne peut qu'écrire, jamais lire ni supprimer.

**Corrélation** : chaque log en isolation ne dit rien. Ce qui compte, c'est la séquence — "auth.success à 14:30:01, rbac.denied sur /admin à 14:30:02, rate_limit.exceeded à 14:30:05 depuis la même IP". Sans un identifiant commun (le `trace_id`) qui relie ces événements entre eux et à travers les services, la reconstitution est impossible à l'échelle.

**Richesse sémantique** : un log texte `"Alice a échoué à se connecter"` répond à "quoi". Un log structuré JSON avec `user`, `ip`, `reason`, `path`, `trace_id`, `ts` répond à "quoi, qui, d'où, pourquoi, et dans quel contexte". La différence est critique pour les règles de détection automatique : un SIEM ne peut pas raisonner sur du texte libre, il doit pouvoir filtrer sur des champs typés.

### Anatomie d'un log de sécurité bien fait

| Champ | Pourquoi |
|---|---|
| `ts` | Toujours en UTC ISO 8601 → tri lexicographique = tri chronologique |
| `level` | filtrage rapide (info / warn / error / critical) |
| `event` | catégorie sémantique (`auth.failure`, `rbac.denied`, `data.access`) |
| `user`, `ip` | acteur et origine — anonymiser si RGPD impose |
| `trace_id` | corrélation multi-services |
| `resource` | objet de l'action (ex: `document:42`) |
| `result` | success / failure / partial |
| `reason` | motif technique, pas pour l'utilisateur |

## 📋 Étape 1 — slog (Go 1.21+) en JSON

```go
// logging/logger.go
package logging

import (
  "context"
  "log/slog"
  "os"
)

var Logger *slog.Logger

func Init() {
  h := slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{
    Level: slog.LevelInfo,
  })
  Logger = slog.New(h)
}

// CtxKey est exporté pour que le middleware Trace et le logger partagent
// EXACTEMENT la même clé de contexte (sinon le lookup renvoie "" en silence).
type CtxKey string

const TraceIDKey CtxKey = "trace_id"

// Helper : log un événement de sécurité avec champs courants
func SecEvent(ctx context.Context, event string, attrs ...slog.Attr) {
  traceID, _ := ctx.Value(TraceIDKey).(string)
  base := []slog.Attr{
    slog.String("event", event),
    slog.String("trace_id", traceID),
  }
  Logger.LogAttrs(ctx, slog.LevelWarn, "sec_event", append(base, attrs...)...)
}
```

`slog.NewJSONHandler(os.Stdout, ...)` écrit un objet JSON par ligne sur stdout. Écrire sur stdout (et non dans un fichier) est la pratique "12-factor app" : le process ne gère pas la rotation, la rétention, ni l'expédition des logs — c'est la responsabilité de l'orchestrateur (Docker, Kubernetes) qui capture stdout et le passe à un agent de collecte. `slog.LevelInfo` comme niveau minimum évite que les logs debug inondent le SIEM en production. `LogAttrs` est plus performant que `Log` car il évite l'allocation d'une `[]any` intermédiaire.

## 📋 Étape 2 — Middleware trace_id

```go
// middleware/trace.go
package middleware

import (
  "context"
  "crypto/rand"
  "encoding/hex"
  "net/http"

  "yourapp/logging" // ajuste au chemin de ton module
)

// On réutilise la clé typée définie dans le package logging (logging.TraceIDKey)
// pour que le logger relise la même valeur. Une clé string nue ("trace_id")
// déclencherait un avertissement go vet et risquerait une collision inter-packages.

func newTraceID() string {
  b := make([]byte, 8)
  if _, err := rand.Read(b); err != nil {
    return "0000000000000000" // crypto/rand n'échoue quasiment jamais
  }
  return hex.EncodeToString(b)
}

func Trace(next http.HandlerFunc) http.HandlerFunc {
  return func(w http.ResponseWriter, r *http.Request) {
    tid := r.Header.Get("X-Trace-Id")
    if tid == "" { tid = newTraceID() }
    w.Header().Set("X-Trace-Id", tid)
    ctx := context.WithValue(r.Context(), logging.TraceIDKey, tid)
    next(w, r.WithContext(ctx))
  }
}
```

Ce middleware gère deux cas : si le client passe déjà un `X-Trace-Id` (propagé depuis un service upstream ou un API gateway), on le réutilise — c'est essentiel pour que le trace traverse toute l'architecture. Si le client n'en a pas, on en génère un. `crypto/rand` (non déterministe, basé sur l'entropie OS) garantit qu'il est imprévisible — un attaquant ne peut pas deviner les trace_id des autres utilisateurs. `context.WithValue` propage le trace_id dans tout le call stack sans avoir à le passer explicitement à chaque fonction.

> ⚠️ **Clé de contexte typée, pas une string nue** : on stocke avec `logging.TraceIDKey` (type `CtxKey`), pas avec la string `"trace_id"`. Deux raisons : `go vet` interdit les clés `context` de type string de base (risque de collision entre packages), et surtout le logger DOIT relire avec la même clé typée — `ctx.Value("trace_id")` (string) ne matcherait pas une valeur posée avec `CtxKey("trace_id")` et renverrait silencieusement `""`. Un trace_id vide dans tous les logs est un piège classique difficile à diagnostiquer.

> 🔒 **Faut-il faire confiance au `X-Trace-Id` du client ?** En périmètre interne (gateway → services), oui. Exposé directement à Internet, valide-le (longueur, charset hex) ou ignore-le : un attaquant pourrait injecter un trace_id contenant des caractères de contrôle pour polluer tes logs (cf. log injection, plus bas).

Place-le **en premier** dans la chaîne. Tous les middlewares suivants lisent le trace_id via `logging.SecEvent` (qui fait le `ctx.Value(logging.TraceIDKey)` pour eux) — ils n'ont rien à manipuler directement.

## 📋 Étape 3 — Logger les événements sensibles

Mise à jour du middleware auth du lab #1 :

> ⚠️ On reprend bien **toutes** les options de vérification du Lab #1 (`WithIssuer`, `WithAudience`, `WithExpirationRequired`) — le but ici est d'**ajouter le logging**, pas de relâcher la sécurité. Une erreur fréquente quand on instrumente un middleware existant est de le réécrire partiellement et de perdre une garde.

```go
func Auth(next http.HandlerFunc) http.HandlerFunc {
  return func(w http.ResponseWriter, r *http.Request) {
    r.Header.Del("X-User"); r.Header.Del("X-Role") // anti-spoof (cf. Lab #1)
    raw := strings.TrimPrefix(r.Header.Get("Authorization"), "Bearer ")
    tok, err := jwt.Parse(raw, keyFunc,
      jwt.WithValidMethods([]string{"RS256"}),
      jwt.WithIssuer("https://api.homelab.lan"),
      jwt.WithAudience("homelab-api"),
      jwt.WithExpirationRequired())
    if err != nil || !tok.Valid {
      reason := "invalid token"
      if err != nil { reason = err.Error() } // err peut être nil si tok.Valid==false seul
      logging.SecEvent(r.Context(), "auth.failure",
        slog.String("ip", r.RemoteAddr),
        slog.String("reason", reason),
        slog.String("path", r.URL.Path))
      http.Error(w, "invalid token", 401); return
    }
    claims, _ := tok.Claims.(jwt.MapClaims)
    sub, _ := claims["sub"].(string)
    logging.SecEvent(r.Context(), "auth.success",
      slog.String("user", sub),
      slog.String("ip", r.RemoteAddr))
    // ... pose X-User (= sub) puis next
  }
}
```

On logue `auth.failure` avec l'IP, la raison technique, et le path tenté. La raison (`err.Error()`) est précieuse en post-mortem mais ne doit pas être renvoyée au client — deux messages différents : un pour le log (verbeux) et un pour la réponse HTTP (minimal). Le path tenté aide à distinguer une attaque ciblée sur `/admin` d'une tentative générique.

> ⚠️ **`r.RemoteAddr` ≠ vraie IP client derrière un proxy**. `r.RemoteAddr` contient `ip:port` et, derrière un reverse-proxy/load-balancer, c'est l'IP du **proxy**, identique pour tous les clients — la détection par IP du Lab #4 serait alors inutile. En présence d'un proxy de confiance, lis `X-Forwarded-For` (premier élément) ou `X-Real-IP`, mais **uniquement** si le proxy est fiable (sinon le client peut forger l'en-tête). Extrais aussi l'IP seule via `net.SplitHostPort(r.RemoteAddr)` pour que les agrégations LogQL `by (ip)` soient propres.

Et le RBAC :

```go
if !rbac.Can(role, action) {
  logging.SecEvent(r.Context(), "rbac.denied",
    slog.String("user", r.Header.Get("X-User")),
    slog.String("role", string(role)),
    slog.String("action", action),
    slog.String("path", r.URL.Path))
  http.Error(w, "forbidden", 403); return
}
```

Loguer les refus RBAC avec l'action demandée et le rôle réel est clé pour la détection de Lab #4 : un user authentifié qui tente en série des actions au-delà de son rôle est un signal de **reconnaissance de permissions** (MITRE T1087). Sans ce log, ce pattern est invisible.

Ou directement, depuis Go, push vers Loki HTTP :

```go

http.Post("http://loki:3100/loki/api/v1/push", "application/json", payload)
```

## 📋 Étape 5 — Requêtes LogQL utiles

Dans Grafana → Explore → Loki :

### Tous les échecs d'auth des 5 dernières minutes

```logql
{app="api"} |= "auth.failure"
```

### Top 10 IP avec le plus d'échecs

```logql
topk(10,
  sum by (ip) (
    count_over_time({app="api"} | json | event="auth.failure" [5m])
  )
)
```

`| json` parse chaque ligne de log comme JSON et expose ses champs comme des labels temporaires pour le filtrage. `count_over_time` compte les occurrences dans une fenêtre glissante. `sum by (ip)` agrège par valeur du champ `ip`. `topk(10, ...)` ne retient que les 10 plus grandes valeurs — utile pour les dashboards, mais aussi pour la détection : si une IP dépasse un seuil, elle remonte en tête.

### Brute force suspect (>50 échecs/5min depuis une IP)

```logql
sum by (ip) (
  count_over_time({app="api"} | json | event="auth.failure" [5m])
) > 50
```

Cette requête peut être placée directement dans une règle d'alerte Loki → Alertmanager. Le seuil de 50 est à calibrer sur le volume normal de l'application — trop bas = faux positifs, trop haut = brute force lent non détecté.

→ tu pousses ça dans un Alertmanager rule (cf. Lab #4 homelab) → notif Slack.

## 📋 Étape 6 — Reconstituer un parcours

Imagine une plainte : "user alice s'est fait kick à 14h32".

```bash
# Récupérer le trace_id de la première req d'alice après 14:30
TID=$(logcli query '{app="api"} | json | user="alice"' --from="2026-06-01T14:30:00Z" --limit=1 | jq -r '.trace_id')

# Tout ce qui s'est passé sur cette requête
logcli query "{app=\"api\"} | json | trace_id=\"$TID\""
```

La puissance du `trace_id` : en deux requêtes, tu as toute la timeline de la requête d'Alice — auth, rate-limit, RBAC, handler — dans l'ordre chronologique, même si les logs viennent de plusieurs instances du service. Sans `trace_id`, corréler ces événements nécessite de croiser les timestamps (imprécis à la milliseconde près), les IPs (non uniques derrière un load balancer), et les usernames (pas disponibles avant auth). C'est une heure de grep contre 10 secondes de LogQL.

## 🧠 Anti-patterns à éviter

❌ **Logger les passwords en clair** : oui, ça arrive. Toujours filtrer avant slog.
❌ **Logger les JWT entiers** : leakent l'identité + permettent le replay.
❌ **Logger des PII sans nécessité** : RGPD. Hash ou anonymise.
❌ **Niveau debug en prod** : disque saturé + I/O latency.
❌ **Pas de rotation** : 1 fichier = 50 Go = OOM du logger.

## 🔬 Validation

- Un `curl -X POST` sans token → log JSON `auth.failure`
- Un même `curl` avec `X-Trace-Id: test123` → on retrouve les events avec ce trace_id
- Loki affiche les events filtrables par champ
- LogQL brute-force detection retourne 0 (situation normale)
- Tu fais 60 mauvais login en 1 min depuis la même IP → l'alerte se déclenche
