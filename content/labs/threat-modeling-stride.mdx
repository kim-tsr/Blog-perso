## 🧠 Pourquoi le threat modeling avant de coder ?

Une grande part des vulnérabilités les plus graves vient de **décisions d'architecture**, pas de bugs d'implémentation ponctuels. Un bug XSS se patche en 5 minutes. Une absence de séparation des privilèges, un secret partagé entre tous les services, une boundary manquante : ça nécessite de réécrire des services entiers. La règle empirique (popularisée par les travaux de Barry Boehm sur le coût des défauts logiciels) veut que le coût de correction d'une faille augmente d'un ordre de grandeur à chaque phase du cycle de développement : ce qui coûte ~1 heure en phase design peut coûter 100× plus une fois en production.

Le threat modeling intervient **avant** que le code existe — au moment du design — quand changer une décision coûte 100× moins cher. Ce n'est pas de la théorie abstraite : c'est une session de travail structurée (2-4 heures) qui produit une liste de menaces classifiées et un backlog de contre-mesures. L'output est directement actionnable par l'équipe de développement.

STRIDE, développé par des ingénieurs de Microsoft dans les années 2000, est la méthode la plus répandue pour structurer cette analyse. Elle force à parcourir systématiquement 6 catégories de menaces sur chaque flux de données d'un système — évitant les angles morts que l'intuition laisse souvent. La valeur de STRIDE n'est pas dans les 6 lettres de l'acronyme, mais dans la discipline de **couvrir chaque flux, catégorie par catégorie**.

### Les 6 catégories STRIDE : propriété brisée et exemple concret

Chaque lettre de STRIDE correspond à une propriété de sécurité que la menace cherche à violer. Connaître la propriété ciblée aide à identifier la contre-mesure naturelle :

| Catégorie | Propriété brisée | Exemple concret | Contre-mesure typique |
|---|---|---|---|
| **S**poofing | Authenticité | Se faire passer pour l'utilisateur admin via un token JWT forgé | MFA, asymmetric signing (RS256), mTLS |
| **T**ampering | Intégrité | Modifier un paquet en transit pour changer le montant d'une transaction | TLS (HMAC intégré), signatures numériques, checksums |
| **R**epudiation | Non-répudiation | Prétendre ne pas avoir effacé les logs incriminants | Logs append-only, timestamps signés, audit trail cryptographique |
| **I**nformation disclosure | Confidentialité | Stack trace exposant le chemin du fichier de config en prod | Error handling uniformisé, pas d'IDs séquentiels prévisibles |
| **D**enial of service | Disponibilité | Flood de requêtes pour épuiser les threads du serveur web | Rate limiting, circuit breakers, WAF |
| **E**levation of privilege | Autorisation | Exploiter une IDOR pour accéder aux données d'un autre utilisateur | Vérification d'autorisation côté serveur, RBAC, Row Level Security |

La propriété brisée est la clé : si vous cherchez des contre-mesures contre le **Spoofing**, vous cherchez des mécanismes d'**authentification**. Contre le **Tampering**, des mécanismes d'**intégrité**. Cette correspondance propriété-solution n'est pas coïncidentielle — STRIDE a été conçu pour mapper directement vers les catégories de contrôles de sécurité.

### STRIDE-per-element : toutes les menaces ne s'appliquent pas partout

Une finesse souvent ignorée : selon le **type d'élément** du DFD, seul un sous-ensemble des 6 catégories est pertinent. C'est ce qu'on appelle *STRIDE-per-element*, et ça évite de perdre du temps à chercher du « Repudiation » sur un flux de données. Le mapping de référence (Microsoft) :

| Type d'élément du DFD | S | T | R | I | D | E |
|---|:-:|:-:|:-:|:-:|:-:|:-:|
| **External entity** (utilisateur, API tierce) | ✔ | | ✔ | | | |
| **Process** (service, fonction) | ✔ | ✔ | ✔ | ✔ | ✔ | ✔ |
| **Data flow** (flux réseau) | | ✔ | | ✔ | ✔ | |
| **Data store** (DB, cache, fichier) | | ✔ | ✔* | ✔ | ✔ | |

\* Repudiation sur un data store concerne surtout les logs (un store qui *est* un journal d'audit : peut-on le falsifier ?). Les **processus** sont les éléments les plus exposés — ils cumulent les 6 catégories — d'où l'attention à leur porter en priorité.

L'étape critique et la plus souvent bâclée est la première : le **Data Flow Diagram**. Sans un DFD précis, l'analyse STRIDE devient une liste de menaces génériques sans ancrage dans l'architecture réelle. Le DFD doit montrer : les acteurs externes (utilisateurs, systèmes tiers), les processus (services, composants), les data stores (bases de données, caches, fichiers), et les flux de données entre eux. C'est intentionnellement différent d'un diagramme d'architecture infrastructure — l'objectif est de tracer comment les données circulent, pas comment les serveurs sont connectés.

## 🎯 Objectif

Apprendre à analyser une architecture (réelle ou hypothétique) en 4 étapes :
1. Dessiner le **Data Flow Diagram**
2. Identifier les **trust boundaries**
3. Appliquer **STRIDE** sur chaque flux
4. Prioriser avec une matrice **likelihood × impact**

On va appliquer ça à un cas concret : une API de chat avec auth JWT.

## 📐 Étape 2 — Tracer les trust boundaries

Une trust boundary apparaît partout où **le niveau de confiance change**. Le principe est simple : ce qui vient de l'extérieur de la boundary est suspect par défaut, ce qui vient de l'intérieur bénéficie d'un niveau de confiance plus élevé. Ces boundaries sont les points de contrôle où des mécanismes d'authentification, de validation, ou de filtrage doivent être appliqués.

```
                  ┌─────────┐
                  │  User   │   trust=0 (anonyme)
                  └────┬────┘
                       │
        ━━━━━━━━━━━━━━━┿━━━━━━━━━━━━━━━━ Boundary 1 : Internet ↔ DMZ
                       │
                       ▼
              ┌────────────────┐
              │   API Gateway  │   trust=app (vérifie token)
              └───┬─────────┬──┘
                  │         │
        ━━━━━━━━━━┿━━━━━━━━━┿━━━━━━━━━━━ Boundary 2 : DMZ ↔ internal
                  │         │
                  ▼         ▼
          ┌──────────┐  ┌──────────┐
          │ Auth svc │  │ Chat svc │   trust=high (services internes)
          └────┬─────┘  └────┬─────┘
               │              │
        ━━━━━━━┿━━━━━━━━━━━━━━┿━━━━━━━━━━ Boundary 3 : app ↔ data layer
               │              │
               └──────┬───────┘
                      ▼
                ┌──────────┐
                │ Postgres │   trust=critical
                └──────────┘
```

Chaque **flux qui traverse une boundary** doit être analysé avec STRIDE. Un flux interne qui ne traverse pas de boundary (ex : communication entre deux composants du même service dans le même process) est moins prioritaire, car l'attaquant devrait déjà avoir compromis l'environnement pour l'intercepter.

L'erreur classique est de ne modéliser que la boundary Internet/DMZ et d'ignorer les boundaries internes. Pourtant, une large part des compromissions sérieuses impliquent du **mouvement latéral** : l'attaquant entre par un service exposé, puis pivote vers des cibles internes (c'est tout le sens des tactiques *Lateral Movement* TA0008 de MITRE ATT&CK). C'est la boundary App/DB — et la segmentation réseau interne — qui limite les dégâts une fois un service de front compromis. Modéliser uniquement le périmètre, c'est le modèle « château fort » : dur en surface, mou à l'intérieur.

## 🔬 Étape 3 — Appliquer STRIDE flux par flux

Pour chaque catégorie, on se demande : *est-ce une menace plausible ici ? Quelle contre-mesure ?*

### Sur Boundary 1 (User → API Gateway)

| Menace | Question | Contre-mesure |
|---|---|---|
| **S**poofing | User non-auth peut se faire passer pour un autre ? | TLS + JWT signé, MFA pour actions sensibles |
| **T**ampering | User peut modifier le payload en transit ? | TLS (intégrité fournie par HMAC TLS) |
| **R**epudiation | User peut nier avoir envoyé un message ? | Audit log signé côté API, timestamp serveur |
| **I**nfo disclosure | Headers/erreurs leakent des infos ? | Pas de stack trace en prod, pas d'IDs séquentiels prévisibles |
| **D**oS | User flood l'API ? | Rate limit par IP + par token au gateway |
| **E**oP | Token JWT peut être forgé pour role=admin ? | JWT signé asymétriquement (RS256 pas HS256), validation stricte des claims |

La menace EoP via JWT mérite une attention particulière. Avec HMAC-SHA256 (`alg: HS256`), le même secret signe et vérifie — si un service back-end a accès au secret de vérification, il peut aussi forger des tokens. Avec RSA ou ECDSA (`alg: RS256`, `alg: ES256`), l'auth service détient la **clé privée** (signe), les autres services utilisent seulement la **clé publique** (vérifient). Un service compromis ne peut pas créer un token admin.

### Sur Boundary 2 (Gateway → microservices)

| Menace | Contre-mesure principale |
|---|---|
| Spoofing | mTLS entre services (PKI privée — cf. [lab step-ca](/labs/pki-step-ca)) |
| Tampering | mTLS apporte aussi l'intégrité |
| Info disclosure | NetworkPolicies pour limiter qui parle à qui ([lab homelab #2](/labs/homelab-02-k3s-cilium)) |
| EoP | RBAC service-to-service (chaque service a un compte SA limité) |

### Sur Boundary 3 (svc → Postgres)

| Menace | Contre-mesure |
|---|---|
| Spoofing | Auth Postgres + mTLS connexion DB |
| Tampering | Pas de DB partagée entre tenants (séparation par schema/db) |
| Info disclosure | Row Level Security pour multi-tenant, colonnes chiffrées pour PII |
| DoS | Connection pool dimensionné, pgBouncer en amont |
| EoP | Comptes app NON superuser, audit pg_audit |

## 📐 Étape 4 — Prioriser

Au lieu de DREAD (subjectif), une matrice simple :

```
                          IMPACT
                  Low      Med      High
              ┌────────┬────────┬────────┐
       High   │   M    │   H    │   C    │
              │        │        │critique│
   LIKELIHOOD ┼────────┼────────┼────────┤
       Med    │   L    │   M    │   H    │
              │        │        │        │
              ┼────────┼────────┼────────┤
       Low    │   L    │   L    │   M    │
              │        │        │        │
              └────────┴────────┴────────┘
```

La matrice likelihood × impact est délibérément simple (3×3 = 9 cases). L'objectif n'est pas une précision mathématique — c'est de **distinguer le critique du négligeable** pour prioriser le backlog. Deux analystes qui scorent la même menace indépendamment ne doivent pas diverger de plus d'une case — si c'est le cas, c'est un signal que la menace est mal définie et nécessite plus d'investigation.

Exemple de hiérarchisation après l'analyse :

| Menace | Likelihood | Impact | Score | Action |
|---|---|---|---|---|
| JWT forge (HS256 mal-configuré) | High | High | **CRITIQUE** | Migrer RS256 immédiatement |
| WebSocket flood | Med | Med | **M** | Rate limit par session |
| Stack trace exposé | High | Low | **M** | Strip en production |
| SQLi via ORM | Low | High | **H** | Parameterized queries (déjà fait) |
| DB compromise via shared password | Low | High | **H** | Secrets manager |

## 🧠 Anti-patterns courants

- ❌ **Threat modeling après le déploiement** : trop tard, coûte 100×
- ❌ **Exhaustivité fantasmée** : viser 100% des menaces → paralysie. Vise 80%, focus sur les boundaries
- ❌ **STRIDE sans data flow** : on liste des risques au hasard. Le diagramme est indispensable
- ❌ **DREAD comme dogme** : préférer matrices simples et reproductibles
