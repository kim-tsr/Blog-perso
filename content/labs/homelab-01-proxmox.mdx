## 🧠 Théorie : pourquoi un hyperviseur de type 1 ?

Avant de cliquer "Installer", il faut comprendre **ce qu'on installe**. Proxmox VE est un hyperviseur de **type 1** (bare-metal) : son noyau (Debian + KVM) tourne directement sur le matériel, sans couche OS intermédiaire. À l'opposé, VirtualBox ou VMware Workstation sont de **type 2** — ils s'exécutent comme n'importe quel processus au-dessus de ton macOS ou Ubuntu.

La différence n'est pas que théorique. Avec un type 2, chaque appel I/O d'une VM traverse l'hyperviseur ET l'OS hôte avant d'atteindre le matériel. Cela double les contextes, multiplie les couches réseau, et crée un point de défaillance unique : si l'OS hôte crashe ou redémarre, toutes tes VMs disparaissent. Sur un type 1, le "host" *est* le kernel de l'hyperviseur — plus compact, moins exposé.

Pour un homelab DevSecOps en mode "always-on", le type 1 est le seul choix raisonnable. Tu veux pouvoir rebooter sans peur, snapshotter sans interruption, et avoir une densité maximale sur le matériel modeste d'un mini PC.

## 🧠 Théorie : ZFS — le pourquoi du comment

ZFS n'est pas juste un système de fichiers. C'est la fusion de trois couches qu'on assemble habituellement à la main avec des outils séparés : le système de fichiers (ext4, xfs), le gestionnaire de volumes logiques (LVM), et la gestion du RAID (mdadm). En les unissant, ZFS peut garantir **l'intégrité end-to-end** : chaque bloc est accompagné d'un checksum SHA-256, vérifié à chaque lecture. La corruption silencieuse — fréquente sur les SSD consumer de qualité moyenne — est détectée immédiatement.

Pour des VMs, les **snapshots copy-on-write** changent la donne. Un snapshot COW est créé en temps constant (< 1 ms), quel que soit la taille du disque : seuls les blocs *modifiés depuis le snapshot* sont copiés, jamais la totalité. Résultat : tu peux prendre un snapshot avant chaque étape risquée et rollback instantanément si tu casses ton cluster au lab suivant.

La **compression lz4** transparente apporte en général 20-40 % de gain d'espace sur des systèmes de fichiers VM typiques, sans mesurable overhead CPU.

## 📋 Étape 1 — Préparer le média d'install

Télécharge l'ISO Proxmox depuis https://www.proxmox.com/en/downloads. Flash avec `dd` ou Balena Etcher :

```bash
sudo dd if=proxmox-ve_8.x-x.iso of=/dev/sdX bs=4M status=progress conv=fsync
```

La commande `dd` lit l'ISO bit-à-bit (`if=` = input file) et l'écrit directement sur la clé USB (`of=` = output file, **remplace `/dev/sdX` par ton périphérique réel, jamais le SSD système !**). `bs=4M` règle la taille de bloc sur 4 Mo pour maximiser le débit, et `conv=fsync` force un flush final — la clé est réellement écrite avant que la commande rende la main.

Boote dessus, installe sur le SSD système (le 256 Go), config réseau **IP fixe** (note bien l'IP — `192.168.1.10` dans la suite).

> 💡 **Pourquoi IP fixe ?** Si Proxmox récupère son IP via DHCP et que ton routeur la change après un reboot, tu perds l'accès web. Pour un nœud d'infrastructure, le DHCP est un bug d'attente.

## 📋 Étape 2 — Désactiver les repos entreprise

Sans abonnement payant, les repos `enterprise` génèrent une erreur à chaque `apt update`. Sur Proxmox :

```bash
# Repo PVE no-subscription
echo "deb http://download.proxmox.com/debian/pve bookworm pve-no-subscription" \
  > /etc/apt/sources.list.d/pve-install-repo.list

# Désactiver enterprise
sed -i 's/^/#/' /etc/apt/sources.list.d/pve-enterprise.list
sed -i 's/^/#/' /etc/apt/sources.list.d/ceph.list

apt update && apt -y dist-upgrade
```

Les deux `sed -i 's/^/#/'` commentent toutes les lignes des fichiers de dépôts enterprise — c'est plus propre que de les supprimer car un futur `apt update` n'a alors plus de référence cassée. Le `dist-upgrade` (vs `upgrade`) applique aussi les changements de dépendances, essentiel sur Proxmox qui refactorise parfois ses méta-paquets entre versions mineures.

## 📋 Étape 3 — Créer un pool ZFS sur le second disque

```bash
# Identifier le disque (attention à ne pas écraser le SSD système !)
lsblk

# Wipe puis création
zpool create -f -o ashift=12 tank /dev/sdb

# Datasets dédiés
zfs create tank/vms
zfs create tank/iso

# Compression + atime off pour les perf
zfs set compression=lz4 tank
zfs set atime=off tank
```

Quelques points-clés sur cette séquence :

- `-f` force la création même si ZFS détecte une signature de partition existante sur le disque. À n'utiliser **qu'après avoir vérifié avec `lsblk` que `/dev/sdb` est bien le second disque** — un `zpool create` est destructif.
- `ashift=12` aligne les blocs ZFS sur 4 Ko (2¹² = 4096 octets). Presque tous les SSD modernes utilisent des pages de 4 Ko physiquement — si ZFS ne sait pas ça et aligne sur 512 octets (ashift=9, la valeur legacy), chaque écriture "tombe" à cheval sur deux pages, divisant les performances par 2 à 3 en écriture aléatoire. Cette valeur **ne peut pas être changée après création du pool** — d'où l'importance de la fixer dès le départ.
- `zfs create tank/vms` crée un **dataset** (comme un répertoire intelligent) séparé pour les disques de VM. Séparer VMs et ISOs permet d'appliquer des propriétés différentes — par exemple plus de compression sur les ISOs, rétention de snapshots distincte.
- `atime=off` désactive la mise à jour de l'heure d'accès à chaque lecture de fichier. Sur ext4, chaque lecture écrit un timestamp — sur un SSD sous charge VM, ça génère une avalanche d'écritures inutiles.

Dans l'UI Proxmox → **Datacenter → Storage → Add → ZFS** : pour le stockage des disques de VM, choisis le dataset `tank/vms` et donne-lui l'ID `tank-vms` (champ *ID* du formulaire). Les ISOs vont sur un stockage de type *Directory* pointant sur `tank/iso` (ZFS ne stocke pas de fichiers ISO bruts, seulement des zvol de VM). Note bien l'ID `tank-vms` : c'est le nom qu'on réutilise dans les commandes `qm` plus bas.

> 💡 **Distinction dataset vs ID de stockage** : `tank/vms` est le nom ZFS du dataset ; `tank-vms` est l'identifiant que Proxmox lui donne dans sa config (`/etc/pve/storage.cfg`). Les deux peuvent différer — les commandes `qm` utilisent toujours l'**ID Proxmox**, pas le chemin ZFS.

## 📋 Étape 4 — Template Debian cloud-init

```bash
cd /root
wget https://cloud.debian.org/images/cloud/bookworm/latest/debian-12-genericcloud-amd64.qcow2

# Créer une VM template
qm create 9000 --name debian-12-tpl --memory 2048 --cores 2 \
  --net0 virtio,bridge=vmbr0
qm importdisk 9000 debian-12-genericcloud-amd64.qcow2 tank-vms
qm set 9000 --scsihw virtio-scsi-pci --scsi0 tank-vms:vm-9000-disk-0
qm set 9000 --ide2 tank-vms:cloudinit
qm set 9000 --boot order=scsi0 --bootdisk scsi0
qm set 9000 --serial0 socket --vga serial0
qm set 9000 --agent enabled=1
qm set 9000 --ciuser kim --sshkeys ~/.ssh/authorized_keys
qm template 9000
```

Cette séquence `qm` construit un template en plusieurs passes intentionnelles :

- `qm importdisk` importe l'image qcow2 dans le pool ZFS (`tank-vms`) sans démarrer la VM — le disque existe physiquement mais n'est pas encore attaché.
- Le nom de disque `vm-9000-disk-0` est celui que `qm importdisk` vient de créer sur le stockage `tank-vms` ; il s'affiche à la fin de la sortie d'`importdisk`. Si ton import affiche un autre nom (ex : `unused0`), adapte la commande `--scsi0`.
- `--scsihw virtio-scsi-pci --scsi0` attache le disque via le contrôleur VirtIO-SCSI — le plus performant pour Linux (vs IDE/SATA émulés). VirtIO présente un périphérique paravirtualisé : le pilote invité parle directement à l'hyperviseur au lieu d'émuler un vrai contrôleur matériel, ce qui supprime une couche de traduction coûteuse.
- `--ide2 tank-vms:cloudinit` crée un **second disque** (CDROM virtuel) qui contiendra les métadonnées cloud-init. À chaque clonage, ce CDROM sera personnalisé avec le hostname, l'IP et les clés SSH de la VM cible.
- `--boot order=scsi0` (syntaxe Proxmox VE 8 ; l'ancien `--boot c` est déprécié) force le boot sur le disque système, pas sur le CDROM cloud-init.
- `--serial0 socket --vga serial0` redirige la console sur un socket série — recommandé pour les images cloud Debian, qui sont configurées pour logguer sur `ttyS0`, et indispensable pour voir le boot si le réseau n'est pas encore monté.
- `--agent enabled=1` active le canal QEMU Guest Agent. L'image genericcloud n'embarque pas l'agent par défaut ; cloud-init l'installera (voir l'option `packages` ci-dessous) pour que Proxmox connaisse l'IP réelle de la VM et puisse la quiescer lors des snapshots.
- `--sshkeys` (avec un **s** ; `--sshkey` au singulier n'existe pas dans `qm`) injecte tes clés publiques dans le `authorized_keys` de l'utilisateur cloud-init.
- `qm template 9000` verrouille la VM en mode template : elle ne peut plus démarrer directement, elle sert uniquement de source pour `qm clone`.

> 💡 **Agent dans l'image** : pour que `--agent enabled=1` serve à quelque chose, l'agent doit être présent dans la VM. Le plus simple est de l'ajouter via cloud-init en éditant la conf du template : `qm set 9000 --cicustom "vendor=local:snippets/qemu-ga.yml"` avec un snippet qui fait `packages: [qemu-guest-agent]`. Sinon, installe-le manuellement au premier boot (`apt install qemu-guest-agent`).

## 📋 Étape 5 — Cloner les 3 VMs

```bash
# Master Kubernetes
qm clone 9000 100 --name k3s-master --full
qm set 100 --memory 4096 --cores 2 --ipconfig0 ip=192.168.1.20/24,gw=192.168.1.1
qm resize 100 scsi0 +18G
qm start 100

# Worker Kubernetes
qm clone 9000 101 --name k3s-worker --full
qm set 101 --memory 4096 --cores 2 --ipconfig0 ip=192.168.1.21/24,gw=192.168.1.1
qm resize 101 scsi0 +18G
qm start 101

# VM Services (DB, observabilité, etc.)
qm clone 9000 110 --name services --full
qm set 110 --memory 2048 --cores 2 --ipconfig0 ip=192.168.1.30/24,gw=192.168.1.1
qm resize 110 scsi0 +18G
qm start 110
```

`--full` force une copie complète du disque plutôt qu'un clone lié (linked clone). Un linked clone partage les blocs du template et est plus rapide à créer, mais supprime le template brise toutes les VMs qui en dépendent. Pour un homelab sérieux, `--full` donne des VMs totalement indépendantes.

`--ipconfig0 ip=.../24,gw=...` injecte la configuration réseau dans le CDROM cloud-init : au premier boot, cloud-init lit ce CDROM, configure l'interface eth0, puis disparaît (le CDROM est ensuite ignoré). Sans cette option, la VM démarrerait avec DHCP et tu perdrais les IPs fixes.

`qm resize 100 scsi0 +18G` étend le disque de la VM **avant le premier boot** — ZFS thin-provisionne la différence, mais la VM voit un disque de 20 Go. cloud-init gère automatiquement la croissance de la partition grâce à `growpart`.

## 🔬 Snapshot avant le lab suivant

C'est le moment d'utiliser ce pourquoi tu as choisi ZFS. Crée un snapshot de chaque VM pour pouvoir rollback si tu casses tout au Lab #2 :

```bash
for id in 100 101 110; do
  qm snapshot $id base-after-lab1 --description "Fin Lab #1 — VMs Debian propres"
done

# Lister les snapshots
zfs list -t snapshot
```

`qm snapshot` passe par ZFS pour créer un snapshot COW de chaque disque de VM. La boucle `for` prend les 3 snapshots en quelques secondes — l'opération est O(1), indépendante de la taille du disque. Si le Lab #2 brise un node, `qm rollback 100 base-after-lab1` ramène la VM à cet état précis en quelques secondes.
