## 🧠 Théorie : eBPF — exécuter du code dans le kernel sans modifier le kernel

eBPF (extended Berkeley Packet Filter) est la technologie la plus transformative du kernel Linux de la dernière décennie. L'idée de base : charger dans le kernel des **programmes sandboxés** qui s'exécutent à des points d'accroche précis — réception d'un paquet réseau, appel système (syscall), entrée dans une fonction kernel — sans toucher au code source, sans recompiler, sans redémarrer. Un **vérificateur** (BPF verifier) analyse statiquement chaque programme avant de l'injecter pour garantir qu'il ne peut pas planter le kernel ni créer de boucle infinie.

Avant eBPF, modifier le comportement du kernel nécessitait soit d'écrire un module kernel (risqué, fragile entre versions), soit de patcher le kernel lui-même (impossible en prod). C'est cette friction qui a longtemps bloqué l'innovation dans le réseau Kubernetes : iptables était lent mais "faisable", toute alternative nécessitait de toucher au kernel.

eBPF a rendu trois choses possibles en production : **Cilium** pour le réseau et les politiques (ce lab), **Falco** pour la détection d'intrusion (Lab #5), et **bpftrace/pyroscope** pour le profiling sans instrumentation. Ce sont les trois outils-phares de la pile DevSecOps moderne.

## 🧠 Théorie : Cilium — réseau Kubernetes sans iptables

Dans un cluster Kubernetes standard, deux composants gèrent le réseau : un **CNI** (Container Network Interface, ex : flannel, Calico) pour le routage L3 entre pods, et **kube-proxy** pour implémenter les Services Kubernetes via des règles iptables. Cette architecture fonctionne, mais iptables est une liste linéaire de règles : trouver la bonne règle pour un Service parmi 5000 prend O(N) comparaisons, et l'overhead devient mesurable à partir de ~500 Services.

Cilium remplace **les deux** avec un datapath eBPF unifié :

- Le routage pod-à-pod passe par des cartes de hachage eBPF (O(1)) au lieu de règles iptables
- Les Services Kubernetes sont résolus directement dans le kernel, avant que le paquet n'atteigne le socket
- Les NetworkPolicies sont évaluées en-ligne dans le datapath, sans passer par netfilter

Au-dessus du datapath, **Hubble** lit les événements eBPF de Cilium et les expose : chaque flux entre pods est visible avec son verdict (ALLOWED / DROPPED), sa raison, sa latence, et les métadonnées Kubernetes (namespace, pod name, label). C'est l'observabilité réseau native, sans sidecar.

## 📋 Étape 1 — Installer k3s sur le master sans CNI

On désactive flannel ET kube-proxy pour laisser la place à Cilium :

```bash
# Sur k3s-master (192.168.1.20)
curl -sfL https://get.k3s.io | sh -s - server \
  --flannel-backend=none \
  --disable-network-policy \
  --disable-kube-proxy \
  --disable=traefik \
  --node-ip=192.168.1.20 \
  --cluster-cidr=10.42.0.0/16 \
  --service-cidr=10.43.0.0/16

# Récupère le token pour le worker
sudo cat /var/lib/rancher/k3s/server/node-token
```

Chaque flag de cette commande a une raison précise :

- `--flannel-backend=none` désactive le CNI embarqué de k3s. Sans ça, flannel démarre et tente de créer des interfaces réseau que Cilium voudra aussi gérer — collision garantie.
- `--disable-network-policy` désactive le contrôleur de NetworkPolicy built-in de k3s qui s'appuierait sur iptables. Cilium gère les NetworkPolicies lui-même via eBPF.
- `--disable-kube-proxy` est le flag critique : il empêche le démarrage de kube-proxy sur chaque node. Sans lui, tu aurais deux systèmes de routing de Services actifs simultanément — résultat : des connexions aléatoirement cassées selon quel système répond en premier.
- `--cluster-cidr` (plage des IP de pods) et `--service-cidr` (plage des ClusterIP des Services) sont les valeurs par défaut de k3s — on les écrit explicitement pour les réutiliser à l'identique dans la config Cilium. Le `clusterPoolIPv4PodCIDRList` de Cilium **doit** correspondre au `--cluster-cidr` ; sinon Cilium attribue des IP de pods hors de la plage routée par k3s et le réseau ne monte pas.

> 💡 `--disable-kube-proxy` est critique : sans ça tu te retrouves avec **deux** systèmes de service routing qui se marchent dessus. Ce flag est stable dans k3s depuis longtemps ; assure-toi simplement d'être sur une version récente (k3s ≥ v1.27, idéalement le canal `stable` 2025).

## 📋 Étape 2 — Joindre le worker

```bash
# Sur k3s-worker (192.168.1.21)
TOKEN="<le-token-récupéré>"
curl -sfL https://get.k3s.io | K3S_URL=https://192.168.1.20:6443 K3S_TOKEN="$TOKEN" sh -
```

Le worker k3s démarre en mode **agent** uniquement (pas de control plane) : il exécute kubelet pour gérer les pods, mais délègue toute décision d'ordonnancement au master via l'API server (port 6443). Le token, lu dans `/var/lib/rancher/k3s/server/node-token`, est un secret partagé qui authentifie le worker auprès du master.

Le kubeconfig n'existe que sur le **master** (l'agent n'a pas de control plane). Reviens donc sur `k3s-master` pour piloter le cluster :

```bash
# Sur k3s-master (192.168.1.20)
export KUBECONFIG=/etc/rancher/k3s/k3s.yaml
kubectl get nodes -o wide
```

> 💡 Le fichier `/etc/rancher/k3s/k3s.yaml` n'est lisible que par root (mode 600). Plutôt que d'élargir ses permissions (`chmod 644` exposerait les credentials cluster-admin à tout utilisateur de la VM), lance `kubectl` en root ou via `sudo`, ou copie ce fichier vers `~/.kube/config` de ton poste en remplaçant `127.0.0.1` par `192.168.1.20`.

Les deux nodes apparaissent en `NotReady` — normal, pas de CNI encore. Sans CNI, le réseau pod-à-pod est inexistant et kubelet rapporte NotReady jusqu'à ce qu'il soit opérationnel.

## 📋 Étape 3 — Installer Cilium

```bash
# Installer le CLI Cilium sur le master
CILIUM_CLI_VERSION=$(curl -s https://raw.githubusercontent.com/cilium/cilium-cli/main/stable.txt)
curl -L --remote-name-all https://github.com/cilium/cilium-cli/releases/download/${CILIUM_CLI_VERSION}/cilium-linux-amd64.tar.gz
sudo tar xzvfC cilium-linux-amd64.tar.gz /usr/local/bin

# Installer Cilium dans le cluster
cilium install \
  --set ipam.operator.clusterPoolIPv4PodCIDRList=10.42.0.0/16 \
  --set kubeProxyReplacement=true \
  --set k8sServiceHost=192.168.1.20 \
  --set k8sServicePort=6443 \
  --set hubble.relay.enabled=true \
  --set hubble.ui.enabled=true \
  --set hubble.metrics.enabled="{dns,drop,tcp,flow,port-distribution,icmp,http}" \
  --set prometheus.enabled=true \
  --set operator.prometheus.enabled=true

cilium status --wait
```

Les paramètres Cilium installent le datapath eBPF complet :

- `kubeProxyReplacement=true` active le remplacement total de kube-proxy. Cilium lit directement la liste des Services depuis l'API Kubernetes et programme les règles BPF correspondantes dans chaque node — sans passer par iptables.
- `k8sServiceHost` et `k8sServicePort` sont nécessaires car, en mode `kubeProxyReplacement`, Cilium doit pouvoir joindre l'API server pour bootstrapper — avant même que les Services Kubernetes soient programmés dans BPF.
- `hubble.relay.enabled=true` déploie Hubble Relay, un composant qui agrège les flows de tous les nodes. Sans lui, tu ne verrais les flows que du node local.
- `prometheus.enabled=true` et `operator.prometheus.enabled=true` exposent un port `/metrics` sur l'agent et l'operator Cilium ; `hubble.metrics.enabled` active en plus les métriques de flux (DNS, drops, débit). On en a besoin **dès maintenant** car le Lab #4 viendra scraper ces endpoints avec Prometheus — autant les activer à l'installation plutôt que de réinstaller Cilium plus tard.

Vérifie : `kubectl get nodes` → les nodes passent `Ready` dès que Cilium a programmé les interfaces.

## 🧠 Pourquoi `kubeProxyReplacement=true` change la performance

La différence entre kube-proxy (iptables) et Cilium (eBPF) est fondamentalement algorithmique. kube-proxy traduit chaque Service Kubernetes en une chaîne de règles iptables traversées linéairement à chaque paquet. Avec 1000 Services, un paquet peut traverser des milliers de règles. Avec Cilium, chaque Service est une entrée dans une hash map BPF — la recherche est O(1), indépendamment du nombre de Services.

## 📋 Étape 4 — Ouvrir Hubble UI

Hubble Relay et l'UI ont déjà été activés à l'étape 3 (`hubble.relay.enabled` et `hubble.ui.enabled`). Vérifie qu'ils tournent, puis ouvre un port-forward :

```bash
cilium status        # la ligne Hubble doit être "OK"
cilium hubble ui     # ouvre automatiquement un port-forward vers le service hubble-ui
```

`cilium hubble ui` crée un port-forward `kubectl` vers le Service `hubble-ui` du namespace `kube-system` et ouvre ton navigateur. Va sur http://localhost:12000 → tu vois en temps réel **chaque flux** entre pods, classé par namespace.

> 💡 Si tu pilotes le cluster en SSH (pas de navigateur sur la VM), lance plutôt `kubectl port-forward -n kube-system svc/hubble-ui 12000:80 --address 0.0.0.0` puis ouvre `http://192.168.1.20:12000` depuis ton poste.

## 📋 Étape 5 — Déployer une app test avec NetworkPolicy

```bash
kubectl create ns demo
kubectl -n demo create deployment whoami --image=traefik/whoami
kubectl -n demo expose deployment whoami --port=80
kubectl -n demo run client --image=curlimages/curl --command -- sleep infinity

# Test : ça doit marcher
kubectl -n demo exec client -- curl -s whoami | head -3
```

Maintenant on coupe avec une NetworkPolicy Cilium **zero-trust** (deny-all puis allow explicite) :

```yaml
# deny-all-then-allow.yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: deny-all-ingress
  namespace: demo
spec:
  endpointSelector:
    matchLabels:
      app: whoami
  ingress: []   # ← bloque tout
---
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: allow-client
  namespace: demo
spec:
  endpointSelector:
    matchLabels:
      app: whoami
  ingress:
    - fromEndpoints:
        - matchLabels:
            run: client
      toPorts:
        - ports: [{ port: "80", protocol: TCP }]
```

La logique de ces deux policies est additive : `deny-all-ingress` sélectionne les pods `app=whoami` et déclare une liste d'ingress **vide** — ce qui signifie "aucun flux autorisé". La deuxième policy `allow-client` ajoute une exception explicite uniquement pour les pods avec le label `run=client`, uniquement sur le port 80/TCP. Cilium applique la politique la plus permissive qui correspond : aucun flux n'est autorisé sauf ce que `allow-client` liste.

```bash
kubectl apply -f deny-all-then-allow.yaml
kubectl -n demo exec client -- curl -s --max-time 3 whoami
# → fonctionne (client autorisé)
```

Mais depuis un autre pod sans le label `run=client`, c'est bloqué :

```bash
kubectl -n demo run snoop --rm -it --image=curlimages/curl --command -- curl -s --max-time 3 whoami
# → timeout
```

Dans Hubble UI tu vois deux flows :
- 🟢 `demo/client → demo/whoami` : ALLOWED
- 🔴 `demo/snoop → demo/whoami` : DROPPED `policy-denied`

La valeur de Hubble ici : `timeout` vu du pod ne te dit pas *pourquoi* ça timeout (policy ? DNS ? pod down ?). Hubble te donne le verdict précis `policy-denied` — tu sais exactement ce qui bloque sans avoir à deviner.
