## Théorie : l'architecture de Kubernetes

Kubernetes est un **orchestrateur de containers** : il automatise le déploiement, la mise à l'échelle et la gestion d'applications containerisées sur un cluster de machines. L'idée centrale est de traiter l'infrastructure comme un ensemble de ressources déclaratives — tu décris l'état désiré (2 replicas de cette image, exposés sur ce port, avec ces limites mémoire), et Kubernetes converge en permanence vers cet état. Si un container crash, il est redémarré. Si un node tombe, les pods sont reschedules ailleurs. L'infrastructure est self-healing par conception.

Le cluster Kubernetes se divise en deux plans : le **control plane** (le cerveau) et les **worker nodes** (les muscles). Le control plane ne fait pas tourner les workloads applicatifs — il gère l'état du cluster. Cette séparation est fondamentale pour la résilience : un worker node qui tombe n'affecte pas le control plane, qui peut continuer à scheduler des pods sur les nodes survivants.

### Les composants du control plane en détail

**kube-apiserver** est le point d'entrée unique de toute interaction avec le cluster. Chaque `kubectl`, chaque composant interne, chaque controller passe par l'API REST qu'il expose. Il valide les ressources (admission controllers), les stocke dans etcd, et notifie les watchers. Il est le seul composant qui parle directement à etcd.

**etcd** est la base de données distribuée clé-valeur qui stocke l'état complet du cluster. Dans k3s, etcd est remplacé par défaut par SQLite (suffisant pour moins de 100 nodes), ou par kine (abstraction SQL sur postgres/mysql) pour la haute disponibilité sans déployer etcd complet. La perte d'etcd = la perte du cluster : sauvegarder etcd est aussi critique que sauvegarder une base de données de production.

**kube-scheduler** observe en continu les pods non assignés à un node et choisit le meilleur candidat selon un algorithme en deux phases : Filtering (élimine les nodes qui ne satisfont pas les contraintes : resources requests, node selectors, taints/tolerations, affinity) puis Scoring (classe les nodes restants selon des priorités : répartition de charge, localité des données, etc.).

**kube-controller-manager** bundle des dizaines de boucles de contrôle. Le Deployment controller maintient le bon nombre de replicas. Le ReplicaSet controller crée/supprime des pods. Le Node controller détecte les nodes qui ne répondent plus. Chaque controller surveille l'état via l'API et agit pour l'aligner sur l'état désiré — le même pattern de reconciliation loop qu'ArgoCD.

### k3s vs k8s vanilla : pourquoi choisir k3s

k3s n'est pas une version "simplifiée" ou moins robuste de Kubernetes — c'est une distribution optimisée pour les environnements contraints qui passe les mêmes conformance tests CNCF que k8s vanilla. Sa principale différence architecturale : tous les composants du control plane sont compilés dans un seul binaire de ~70 MB. Cela simplifie drastiquement le déploiement, les mises à jour, et la surface d'attaque.

| Aspect | k3s | k8s vanilla |
|---|---|---|
| Binaire | 1 (~70 MB) | ~7 binaires (~1 GB) |
| Store par défaut | SQLite | etcd (HA cluster) |
| Ingress | Traefik bundled | None (à installer) |
| LoadBalancer | ServiceLB (Klipper) | None (cloud-controller-manager) |
| Storage | local-path bundled | None (CSI à installer) |
| Cas d'usage | edge, IoT, dev, < 100 nodes | prod massif, multi-AZ |
| Certifié CNCF | oui | oui |

### Les objets Kubernetes essentiels

La hiérarchie des objets Kubernetes suit une logique de composition : un Deployment gère des ReplicaSets qui gèrent des Pods qui contiennent des containers. À chaque niveau, Kubernetes ajoute une couche de capacité opérationnelle (rolling update au niveau Deployment, self-healing au niveau ReplicaSet, co-localisation au niveau Pod).

## Objectif

Après ce lab, vous aurez un cluster **k3s** fonctionnel, une application **whoami** déployée, et un service exposé via **Traefik** — l'ingress fourni par défaut. C'est le point de départ idéal pour tout futur lab Kubernetes.

## Étape 1 — Installer k3s

```bash
curl -sfL https://get.k3s.io | sh -

# Vérifier que le service tourne
sudo systemctl status k3s
```

Le script d'installation télécharge le binaire k3s, le place dans `/usr/local/bin/`, crée un service systemd `k3s.service` et le démarre. Le binaire unique fait office de serveur API, scheduler, controller-manager, kubelet, et runtime containerd simultanément. En production, on passe des flags au script via des variables d'environnement (ex: `INSTALL_K3S_EXEC="server --tls-san mon-ip-publique"`) pour configurer le comportement.

```bash
sudo chmod 644 /etc/rancher/k3s/k3s.yaml
export KUBECONFIG=/etc/rancher/k3s/k3s.yaml
kubectl get nodes
```

Le fichier `/etc/rancher/k3s/k3s.yaml` est le kubeconfig généré par k3s : il contient le certificat CA du cluster, un certificat client **admin**, et l'adresse du serveur API. Sans `KUBECONFIG` ou `~/.kube/config`, kubectl ne sait pas comment se connecter au cluster. En mode multi-cluster, on merge plusieurs kubeconfigs ou on utilise `kubectl config use-context`.

> ⚠️ `chmod 644` rend ce kubeconfig **lisible par tous les utilisateurs locaux** — donc un accès admin complet au cluster pour quiconque a un shell sur la machine. Acceptable en lab mono-utilisateur, jamais en prod. Préférable : copier le fichier dans `~/.kube/config` (propriété de votre user, `chmod 600`) plutôt que d'élargir les droits du fichier système.

## Étape 2 — Déployer une application

Créons un déploiement simple :

```bash
kubectl create deployment whoami --image=traefik/whoami --replicas=2
kubectl expose deployment whoami --port=80
```

`kubectl create deployment` crée un objet Deployment dans le cluster via l'API. Le Deployment controller détecte ce nouvel objet, crée un ReplicaSet, qui crée les Pods (2 ici, grâce à `--replicas=2` — utile pour voir le load-balancing du Service plus loin). Le scheduler assigne chaque Pod à un node (ici le seul), kubelet reçoit la notification, tire l'image via containerd, et démarre le container. `kubectl expose` crée un Service de type ClusterIP qui sélectionne tous les Pods portant le label `app=whoami` — ce label est ajouté automatiquement par `kubectl create deployment`. L'image `traefik/whoami` écoute sur le port 80 par défaut, d'où `--port=80`.

```bash
kubectl get pods,svc -l app=whoami
```

Le flag `-l app=whoami` filtre les ressources par label — c'est le même sélecteur qu'utilise le Service pour router le trafic. Si vous voyez `0/1 READY` pour un pod, vérifiez `kubectl describe pod <nom>` pour les events.

## Étape 3 — Exposer via Ingress

Créez `ingress.yaml` :

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: whoami
spec:
  rules:
    - host: whoami.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: whoami
                port:
                  number: 80
```

Un Ingress est une règle de routage HTTP — il ne fait rien par lui-même. C'est le **Ingress Controller** (ici Traefik, bundlé avec k3s) qui lit ces règles et configure son reverse proxy en conséquence. Quand une requête arrive sur Traefik avec `Host: whoami.local`, Traefik la route vers le Service `whoami` sur le port 80, qui la distribue aux Pods correspondants. `pathType: Prefix` signifie que toute requête commençant par `/` match cette règle.

```bash
kubectl apply -f ingress.yaml
echo "$(hostname -I | awk '{print $1}') whoami.local" | sudo tee -a /etc/hosts
curl http://whoami.local
```

`kubectl apply` est la commande déclarative recommandée : elle crée la ressource si absente, ou la met à jour si elle existe déjà. `kubectl create` échoue si la ressource existe — réservé aux cas où on veut interdire la recréation accidentelle.

## Étape 4 — Debug courant

```bash
# Voir les events récents
kubectl get events --sort-by=.lastTimestamp

# Inspecter un pod
kubectl describe pod whoami-xxxxx

# Voir les logs
kubectl logs whoami-xxxxx

# Logs du crash précédent
kubectl logs whoami-xxxxx --previous

# Entrer dans le pod
kubectl exec -it whoami-xxxxx -- sh
```

`kubectl get events` est la commande de diagnostic la plus utile : elle liste tous les événements du cluster (création, scheduling, pull d'image, erreurs). `--sort-by=.lastTimestamp` les trie chronologiquement — les problèmes récents apparaissent à la fin. `kubectl describe pod` enrichit l'affichage avec les events spécifiques au pod, ses conditions (Ready, Initialized, ContainersReady), et ses probes. `kubectl logs --previous` récupère les logs du container qui vient de crasher — indispensable pour diagnostiquer un `CrashLoopBackOff`.

## Pitfalls courants

❌ **kubeconfig avec mauvais droits** : `sudo chmod 644 /etc/rancher/k3s/k3s.yaml` (ou KUBECONFIG perso).
❌ **CrashLoopBackOff sans regarder les logs** : 90% du temps, c'est une env var ou un secret manquant.
❌ **Service sans matching labels** : `kubectl describe svc` montre 0 endpoint = selector ne match aucun pod.
❌ **Pas de resource limits** : un pod gourmand peut OOM le node.
❌ **Exposer Traefik directement sur port 80 sans TLS** : ok en lab, jamais en prod.
