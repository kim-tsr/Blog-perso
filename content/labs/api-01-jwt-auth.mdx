## 🧠 Théorie : qu'est-ce qu'un JWT exactement ?

L'authentification par token repose sur un principe simple : au lieu de maintenir une session côté serveur (état partagé, coûteux à scaler), on donne au client une **preuve cryptographique** de son identité. Le serveur peut vérifier cette preuve à chaque requête sans aller chercher quoi que ce soit en base. C'est le fondement du modèle **stateless** qui permet de faire tourner 50 replicas d'une API sans synchronisation d'état entre elles.

Un JWT (JSON Web Token, RFC 7519) est la forme la plus répandue de cette preuve. Il est constitué de 3 parties encodées en base64url, séparées par des points. Le **header** déclare l'algorithme de signature et l'identifiant de la clé utilisée. Le **payload** contient les *claims* — les affirmations sur l'identité de l'utilisateur (qui il est, quand le token expire, pour quelle audience il est valide). La **signature** est le HMAC ou la signature RSA qui garantit que personne n'a modifié les deux premières parties.

Point critique souvent mal compris : le payload n'est **pas chiffré**, seulement encodé en base64. N'importe qui peut le décoder et lire son contenu. Un JWT *authentifie* et *garantit l'intégrité* — il ne protège pas la confidentialité. Ne jamais y mettre de mot de passe, clé privée, ou donnée trop sensible.

La durée de vie du token est un équilibre de sécurité : un token court (15 min) limite la fenêtre d'exploitation si volé, mais nécessite un mécanisme de **refresh**. Un token long (24h) est confortable mais transforme chaque vol en accès durable. La pratique industrielle combine un `access_token` court pour les appels API et un `refresh_token` opaque (stocké côté serveur, révocable) pour en obtenir un nouveau sans redemander les credentials.

### JWT en trois parties

```
eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCIsImtpZCI6InYxIn0.eyJzdWIiOiJraW0i...fQ.MEUCIQDk...signature
└──────────── header ────────────┘ └─── payload ───┘ └─ signature ─┘
```

Les trois segments sont séparés par des points (`.`). Détaillons chacun :

- **Header** (base64url) : `{ "alg": "RS256", "typ": "JWT", "kid": "v1" }` — `alg` déclare l'algorithme, `kid` identifie la clé de signature pour la rotation. *Risque si on fait confiance à `alg` : voir l'attaque alg:none plus bas.*
- **Payload** (base64url) : `{ "sub": "kim@example.com", "exp": 1717246800, "role": "user", "iss": "...", "aud": "..." }` — les claims standardisés (RFC 7519) et ceux de l'application.
- **Signature** : `sign(base64url(header) + "." + base64url(payload), private_key)` — recalculée à la vérification ; invalide si l'un des deux segments est modifié d'un seul octet.

> 💡 **base64url, pas base64** : le JWT utilise l'alphabet *base64url* (RFC 4648 §5) — `-` et `_` au lieu de `+` et `/`, et **sans padding `=`**. C'est pour rester sûr dans une URL ou un header HTTP. C'est pourquoi le décodage manuel plus bas nécessite une conversion.

### OAuth vs OIDC vs JWT

Ces trois termes désignent des niveaux d'abstraction différents, souvent confondus :

<Stack layers={[
  { label: "OIDC (OpenID Connect)", hint: "auth + identité du user → id_token (JWT) + access_token", accent: "v" },
  { label: "OAuth 2.0", hint: "autorisation → accès à une ressource → access_token (opaque ou JWT)", accent: "c" },
  { label: "JWT", hint: "format de token signé — utilisé comme transport par OAuth/OIDC", accent: "a" },
]} caption="JWT est le format ; OAuth 2.0 et OIDC sont les protocoles qui l'utilisent" bottom="first" />

OAuth 2.0 répond à la question "le user m'autorise-t-il à accéder à sa ressource ?" — il produit un `access_token`. OIDC ajoute par-dessus "qui est le user ?" — il produit un `id_token` (toujours un JWT signé). Dans ce lab on implémente directement l'émission JWT sans passer par un IDP complet, ce qui est le cas classique pour une API interne.

### HS256 vs RS256 : pourquoi l'asymétrique gagne en prod

Avec **HS256** (HMAC-SHA256), la même clé secrète signe *et* vérifie. En microservices, si 5 services doivent vérifier des tokens, ils ont tous la clé de signature — compromettre l'un d'eux permet de forger des tokens valides pour tous. Avec **RS256**, seul l'issuer possède la clé privée. Les services vérificateurs n'ont que la clé publique, qui ne permet que de vérifier, jamais de signer. La surface d'attaque est réduite à l'issuer seul.

## 📋 Étape 1 — Générer les paires de clés RSA

```bash
mkdir -p ./keys
# Clé v1
openssl genpkey -algorithm RSA -out keys/v1.pem -pkeyopt rsa_keygen_bits:2048
openssl rsa -in keys/v1.pem -pubout -out keys/v1.pub

# Clé v2 (pour démontrer la rotation plus tard)
openssl genpkey -algorithm RSA -out keys/v2.pem -pkeyopt rsa_keygen_bits:2048
openssl rsa -in keys/v2.pem -pubout -out keys/v2.pub
```

`genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048` génère une paire RSA 2048 bits — assez pour RS256, compatible FIPS. `rsa -pubout` en extrait la clé publique au format PEM. On génère deux paires dès maintenant pour pouvoir démontrer la rotation à l'étape 6 sans interrompre le service.

## 📋 Étape 2 — Issuer Go simple

```go
// issuer/main.go
package main

import (
  "crypto/rsa"
  "encoding/base64"
  "encoding/json"
  "log"
  "math/big"
  "net/http"
  "os"
  "time"

  "github.com/golang-jwt/jwt/v5"
)

var privKeys = map[string]*rsa.PrivateKey{}
var activeKid = "v1"

func loadKey(kid, path string) {
  b, err := os.ReadFile(path)
  if err != nil { log.Fatalf("lecture clé %s: %v", path, err) }
  k, err := jwt.ParseRSAPrivateKeyFromPEM(b)
  if err != nil { log.Fatalf("parse clé %s: %v", path, err) }
  privKeys[kid] = k
}

func login(w http.ResponseWriter, r *http.Request) {
  // (simplifié) — en vrai on vérifie un login/password contre une DB
  username := r.FormValue("user")
  if username == "" { http.Error(w, "missing user", 400); return }

  claims := jwt.MapClaims{
    "sub":  username,
    "role": "user",
    "iss":  "https://api.homelab.lan",
    "aud":  "homelab-api",
    "iat":  time.Now().Unix(),
    "exp":  time.Now().Add(15 * time.Minute).Unix(),
  }
  tok := jwt.NewWithClaims(jwt.SigningMethodRS256, claims)
  tok.Header["kid"] = activeKid
  signed, err := tok.SignedString(privKeys[activeKid])
  if err != nil { http.Error(w, "signing error", 500); return }
  json.NewEncoder(w).Encode(map[string]string{"jwt": signed})
}

// JWKS : exposer les clés publiques au format RFC 7517 (JWK Set)
// n et e sont les paramètres de la clé publique RSA, en base64url big-endian.
func jwks(w http.ResponseWriter, r *http.Request) {
  keys := []map[string]any{}
  for kid, priv := range privKeys {
    pub := priv.Public().(*rsa.PublicKey)
    n := base64.RawURLEncoding.EncodeToString(pub.N.Bytes())
    e := base64.RawURLEncoding.EncodeToString(big.NewInt(int64(pub.E)).Bytes())
    keys = append(keys, map[string]any{
      "kid": kid, "kty": "RSA", "alg": "RS256", "use": "sig",
      "n": n, "e": e,
    })
  }
  w.Header().Set("Content-Type", "application/json")
  json.NewEncoder(w).Encode(map[string]any{"keys": keys})
}

func main() {
  loadKey("v1", "../keys/v1.pem")
  loadKey("v2", "../keys/v2.pem")

  http.HandleFunc("/login", login)
  http.HandleFunc("/.well-known/jwks.json", jwks)
  log.Fatal(http.ListenAndServe(":8081", nil))
}
```

Points clés de cet issuer :
- `jwt.MapClaims` contient les claims RFC 7519 standards : `iss` (émetteur), `aud` (audience attendue), `iat` (émission), `exp` (expiration). Sans `iss` et `aud`, un token émis pour une API pourrait être réutilisé sur une autre.
- `tok.Header["kid"] = activeKid` ajoute le key ID dans le header — c'est ce qui permet à l'API de choisir la bonne clé publique lors de la vérification.
- L'endpoint `/.well-known/jwks.json` suit la RFC 7517 (JWK Set) : chaque clé publique RSA est sérialisée via son module `n` et son exposant `e` (base64url, big-endian, sans padding). Des services tiers (Keycloak, Auth0, l'IdP de ton cloud) exposent exactement ce format — ton API pourrait donc, en remplaçant le chargement de fichiers par un fetch + cache du JWKS distant, vérifier des tokens émis par n'importe quel IDP compatible sans jamais détenir de clé privée.

## 📋 Étape 3 — Serveur de ressource avec vérif stricte

```go
// api/main.go
package main

import (
  "crypto/rsa"
  "fmt"
  "log"
  "net/http"
  "os"
  "strings"

  "github.com/golang-jwt/jwt/v5"
)

var pubKeys = map[string]*rsa.PublicKey{}

func loadPub(kid, path string) {
  b, err := os.ReadFile(path)
  if err != nil { log.Fatalf("lecture pubkey %s: %v", path, err) }
  k, err := jwt.ParseRSAPublicKeyFromPEM(b)
  if err != nil { log.Fatalf("parse pubkey %s: %v", path, err) }
  pubKeys[kid] = k
}

// CRITIQUE : on force RS256 + on regarde kid pour choisir la clé
func keyFunc(t *jwt.Token) (interface{}, error) {
  if _, ok := t.Method.(*jwt.SigningMethodRSA); !ok {
    return nil, fmt.Errorf("alg non autorisé: %s", t.Method.Alg())
  }
  kid, _ := t.Header["kid"].(string)
  pk, ok := pubKeys[kid]
  if !ok { return nil, fmt.Errorf("kid inconnu: %s", kid) }
  return pk, nil
}

func authMiddleware(next http.HandlerFunc) http.HandlerFunc {
  return func(w http.ResponseWriter, r *http.Request) {
    // CRITIQUE : purger tout X-User/X-Role envoyé par le client.
    // Sinon un attaquant pose lui-même "X-User: admin" et court-circuite l'auth.
    r.Header.Del("X-User")
    r.Header.Del("X-Role")

    h := r.Header.Get("Authorization")
    if !strings.HasPrefix(h, "Bearer ") {
      http.Error(w, "missing bearer", 401); return
    }
    raw := strings.TrimPrefix(h, "Bearer ")

    tok, err := jwt.Parse(raw, keyFunc,
      jwt.WithValidMethods([]string{"RS256"}),   // ← anti alg:none
      jwt.WithIssuer("https://api.homelab.lan"),
      jwt.WithAudience("homelab-api"),
      jwt.WithExpirationRequired(),
    )
    if err != nil || !tok.Valid {
      http.Error(w, "invalid token", 401); return  // pas de détail au client
    }
    claims, ok := tok.Claims.(jwt.MapClaims)
    if !ok { http.Error(w, "invalid claims", 401); return }
    sub, ok := claims["sub"].(string)
    if !ok || sub == "" { http.Error(w, "missing sub", 401); return }
    r.Header.Set("X-User", sub)
    next(w, r)
  }
}

func me(w http.ResponseWriter, r *http.Request) {
  fmt.Fprintf(w, "Hello, %s\n", r.Header.Get("X-User"))
}

func main() {
  loadPub("v1", "../keys/v1.pub")
  loadPub("v2", "../keys/v2.pub")

  http.HandleFunc("/api/me", authMiddleware(me))
  http.ListenAndServe(":8080", nil)
}
```

La `keyFunc` est le coeur de la sécurité :
- La vérification `t.Method.(*jwt.SigningMethodRSA)` force le type d'algorithme en Go, indépendamment de la valeur `alg` dans le header. Sans ça, une lib naïve lirait `"alg":"none"` depuis le token et n'appliquerait pas de vérification de signature. C'est aussi cette vérif qui bloque l'attaque dite de **confusion d'algorithme** (algorithm confusion) : un attaquant pose `alg:HS256` et signe le token en HMAC avec la clé **publique RSA** (qui est… publique) comme secret. Si le serveur récupérait aveuglément la clé associée au `kid` et la passait à un vérificateur HMAC, le token forgé passerait. En forçant `SigningMethodRSA` ici, ce vecteur est mort.
- `jwt.WithValidMethods([]string{"RS256"})` est une deuxième barrière au niveau de la lib — les deux ensemble éliminent la faille alg:none (classe de bugs popularisée par l'advisory Auth0 de 2015 sur de nombreuses libs JWT) et la confusion HS/RS.
- `jwt.WithIssuer` et `jwt.WithAudience` empêchent les **replay cross-service** : un token émis pour une audience `homelab-api` ne sera pas accepté par un service qui attend une autre `aud`.
- `jwt.WithExpirationRequired()` refuse explicitement les tokens sans claim `exp` — sans ça, une lib permissive accepterait des tokens éternels.
- On renvoie un message d'erreur **générique** (`invalid token`) au client : le détail de l'erreur (`err.Error()`) sera loggé côté serveur au Lab #3, jamais exposé. Dire *pourquoi* un token est rejeté aide un attaquant à le forger par essai-erreur.

> 💡 **Pourquoi `kid` lookup et pas une seule clé en dur ?** Le `keyFunc` lit `kid` depuis le header (non signé, donc non fiable en soi) **uniquement pour choisir une clé dans un set fermé que TU contrôles** (`pubKeys`). Un `kid` inconnu → rejet immédiat. On ne fait jamais confiance au `kid` pour autre chose (ex : aller chercher une URL arbitraire — c'est un vecteur SSRF dans les implémentations naïves de JWKS).

## 📋 Étape 4 — Tester la chaîne

> ⚠️ **Note sur les chemins** : les deux `main.go` chargent les clés via `../keys/...`, donc ils doivent être lancés depuis leur propre sous-dossier (`issuer/` et `api/`). On utilise des sous-shells `( ... )` pour que chaque `cd` reste local et ne casse pas le suivant.

```bash
# Démarrer chaque service dans un sous-shell (le cd ne fuit pas)
( cd issuer && go run main.go ) &
( cd api && go run main.go ) &
sleep 1   # laisser les serveurs binder leurs ports

# Obtenir un token
TOKEN=$(curl -s -X POST -d "user=kim" http://localhost:8081/login | jq -r .jwt)
echo "$TOKEN"

# Décoder le payload (juste base64url, AUCUNE crypto)
# tr remet le base64url en base64 standard, puis on rajoute le padding
echo "$TOKEN" | cut -d. -f2 | tr '_-' '/+' | base64 -d 2>/dev/null | jq

# Appeler l'API
curl -H "Authorization: Bearer $TOKEN" http://localhost:8080/api/me
# → Hello, kim
```

`cut -d. -f2` extrait le deuxième segment du JWT (le payload). Comme c'est du **base64url**, on reconvertit `_`/`-` en `/`/`+` avec `tr` avant de passer à `base64 -d` (certaines implémentations de `base64` refusent l'alphabet url et le padding manquant). C'est la démonstration concrète que le payload est lisible par n'importe qui : **ne jamais y mettre de secret**. La signature, elle, reste invérifiable sans la clé — c'est elle qui garantit l'intégrité, pas le secret du contenu.

## 📋 Étape 5 — Tester les attaques classiques

### Attaque 1 : alg=none

```bash
# Forger un token avec alg: none et claims falsifiés
HEADER=$(echo -n '{"alg":"none","typ":"JWT"}' | base64 | tr -d '=' | tr '/+' '_-')
PAYLOAD=$(echo -n '{"sub":"attacker","role":"admin","iss":"https://api.homelab.lan","aud":"homelab-api","exp":99999999999}' | base64 | tr -d '=' | tr '/+' '_-')
FORGED="${HEADER}.${PAYLOAD}."

curl -H "Authorization: Bearer $FORGED" http://localhost:8080/api/me
# → 401 invalid token: alg non autorisé
```

Ce script construit un JWT "à la main" avec `alg:none` et une troisième partie (signature) **vide**. L'astuce `tr -d '=' | tr '/+' '_-'` convertit le base64 standard en base64url (suppression du padding `=`, `_` et `-` à la place de `/` et `+`). Le serveur reçoit un token aux claims `role:admin` mais sans signature : `jwt.WithValidMethods([]string{"RS256"})` (et le test `SigningMethodRSA` dans `keyFunc`) le rejette avant même de regarder les claims. *Risque si omis : escalade de privilèges triviale.*

### Attaque 2 : Token expiré

Pour fabriquer un token déjà expiré sans modifier l'issuer, on baisse temporairement le `exp` à `time.Now().Add(-1 * time.Minute).Unix()` dans `login`, on relance l'issuer, et on rejoue le flow :

```bash
TOKEN=$(curl -s -X POST -d "user=kim" http://localhost:8081/login | jq -r .jwt)
curl -i -H "Authorization: Bearer $TOKEN" http://localhost:8080/api/me
# → HTTP/1.1 401  (le log serveur précise : token is expired)
```

`jwt.WithExpirationRequired()` couplé à la vérification automatique de `exp` par la lib rejette le token. Sans `exp`, un token volé resterait valide indéfiniment — d'où l'importance de l'`access_token` court + `refresh_token` révocable.

### Attaque 3 : Mauvaise audience

On rejoue avec un issuer configuré pour `aud: "autre-api"` (un token parfaitement signé, mais destiné à un autre service) :

```bash
# token signé avec aud="autre-api"
curl -i -H "Authorization: Bearer $TOKEN_AUTRE_AUD" http://localhost:8080/api/me
# → HTTP/1.1 401  (token has invalid audience)
```

`jwt.WithAudience("homelab-api")` refuse un token valide mais émis pour une autre cible. C'est la défense contre le **replay cross-service** : voler un token sur l'API de facturation ne donne pas accès à l'API RH.

## 📋 Étape 6 — Rotation des clés

Activer v2 sans casser les tokens v1 en circulation :

```go
// Dans issuer/main.go, change activeKid = "v2"
// Les nouveaux tokens sont signés par v2
// L'API verifier connaît toujours v1 ET v2 → les anciens tokens restent valides
// jusqu'à leur expiration naturelle (15 min)
```

La rotation se fait en deux temps : d'abord on change la clé de signature (les nouveaux tokens utilisent v2), ensuite on retire la clé publique v1 seulement après que tous les tokens v1 ont expiré. Avec `exp=15min`, c'est automatique en moins d'un quart d'heure. Sans `kid`, on ne saurait pas quelle clé publique utiliser pour vérifier chaque token — la rotation serait impossible sans coupure.
