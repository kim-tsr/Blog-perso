## 🧠 Théorie : GitOps — bien plus que "des YAML sur GitHub"

GitOps n'est pas une pratique informelle. C'est une **discipline opérationnelle** définie formellement par OpenGitOps avec 4 principes. Le point de départ est une frustration concrète : dans les équipes qui "font du CI/CD", il est courant qu'un déploiement en prod soit le résultat d'un `kubectl apply` lancé à la main par quelqu'un en urgence. Deux semaines plus tard, plus personne ne sait ce qui tourne réellement en production — le dépôt Git dit une chose, le cluster en fait une autre.

GitOps résout ce problème par un principe simple : **Git est la source de vérité unique, et un agent dans le cluster est responsable de faire converger l'état réel vers l'état Git**. Jamais l'inverse.

| # | Principe | Ce que ça interdit |
|---|---|---|
| 1 | **Déclaratif** | Les scripts impératifs (`kubectl run`, `helm upgrade --install` à la main) |
| 2 | **Versionné et immutable** | Les modifications directes au cluster sans passer par un commit |
| 3 | **Pull automatique** | Le CI qui pousse vers le cluster avec un kubeconfig externe |
| 4 | **Réconciliation continue** | La config "en place" qui dérive silencieusement sans être détectée |

La conséquence la plus forte : un **rollback** redevient un `git revert`. L'historique Git *est* l'historique de production.

## 🧠 Théorie : push-based vs pull-based — la question de sécurité

La distinction technique entre push et pull cache une différence de sécurité fondamentale. Dans un pipeline push, le runner CI (GitHub Actions, Jenkins) détient un **kubeconfig avec droits d'écriture** sur le cluster. Ce credential est exposé hors du cluster — dans des variables d'environnement CI, dans des logs, dans la mémoire du runner. Si le runner est compromis (dépendance malveillante, supply chain attack, worker partagé), l'attaquant obtient un accès direct au cluster.

Dans un pipeline pull, **aucun credential cluster ne sort du cluster**. ArgoCD lit Git (accès lecture seule sur un repo public, ou avec une deploy key à portée limitée) et applique lui-même les changements via l'API interne. La surface d'attaque est réduite à Git et au contrôle d'accès au dépôt.

## 📋 Étape 1 — Installer ArgoCD

```bash
kubectl create namespace argocd
kubectl apply -n argocd \
  -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
kubectl wait --for=condition=available --timeout=300s \
  -n argocd deployment/argocd-server

# Mot de passe initial
kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath="{.data.password}" | base64 -d ; echo
```

L'installation d'ArgoCD déploie plusieurs composants distincts : `argocd-server` (API + UI), `argocd-repo-server` (clone et analyse les dépôts Git), `argocd-application-controller` (compare et réconcilie), et `argocd-dex-server` (authentification SSO). Le `kubectl wait --for=condition=available` bloque jusqu'à ce qu'`argocd-server` soit prêt, mais en pratique les autres composants démarrent en parallèle — attends encore 30 secondes après le wait avant de te connecter.

Le mot de passe initial est stocké dans un Secret Kubernetes. Le pipeline `base64 -d` le décode (les Secrets Kubernetes sont encodés en base64, pas chiffrés — le chiffrement at-rest est une configuration séparée).

Port-forward pour accéder à l'UI :

```bash
kubectl port-forward -n argocd svc/argocd-server 8080:443 --address=0.0.0.0
```

→ https://192.168.1.20:8080 (login : `admin`).

`--address=0.0.0.0` expose le port-forward sur toutes les interfaces du master, pas seulement localhost — ce qui te permet de te connecter depuis ton poste via l'IP de la VM.

## 📋 Étape 2 — Préparer le dépôt Git

```
homelab-gitops/
├── apps/
│   └── whoami/
│       ├── namespace.yaml
│       ├── deployment.yaml
│       ├── service.yaml
│       └── networkpolicy.yaml
└── infra/                  ← pour les labs suivants
```

Contenu de `deployment.yaml` :

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: whoami
  namespace: demo
spec:
  replicas: 2
  selector: { matchLabels: { app: whoami } }
  template:
    metadata: { labels: { app: whoami } }
    spec:
      containers:
        - name: whoami
          image: traefik/whoami:v1.10
          ports: [ { containerPort: 80 } ]
          resources:
            requests: { cpu: 50m, memory: 32Mi }
            limits:   { cpu: 200m, memory: 128Mi }
```

Quelques points importants dans ce YAML :

- `selector.matchLabels` et `template.metadata.labels` doivent correspondre exactement — c'est ainsi que le Deployment sait quels pods il contrôle. Une incohérence ici cause une erreur de validation ou des comportements inattendus.
- `requests` et `limits` sont **tous les deux nécessaires** : `requests` dit au scheduler ce que le pod a besoin de façon garantie (il ne sera jamais placé sur un node qui n'a pas ces ressources libres), et `limits` dit au kernel (via cgroups) de tuer le processus s'il dépasse ce plafond. Sans `requests`, le scheduler place les pods aléatoirement. Sans `limits`, un pod en fuite peut asphyxier tout le node.
- L'image est épinglée sur `:v1.10` plutôt que `:latest` — en GitOps, `latest` est une anti-pattern car deux syncs identiques pourraient déployer des versions différentes.

Commit + push.

## 📋 Étape 3 — Connecter le dépôt à ArgoCD

```yaml
# argocd-app.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: whoami
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/<ton-user>/homelab-gitops.git
    targetRevision: main
    path: apps/whoami
  destination:
    server: https://kubernetes.default.svc
    namespace: demo
  syncPolicy:
    automated:
      prune: true       # supprime ce qui n'est plus en Git
      selfHeal: true    # ramène l'état du cluster vers Git
    syncOptions:
      - CreateNamespace=true
```

La ressource `Application` est le cœur d'ArgoCD. `source` décrit **où** est l'état désiré (dépôt + branche + sous-dossier), `destination` décrit **où** l'appliquer (cluster + namespace). ArgoCD supporte plusieurs sources par Application (multi-source), utile pour combiner Helm chart + values depuis un dépôt séparé.

`prune: true` et `selfHeal: true` sont deux mécanismes orthogonaux :
- `prune` surveille les **suppressions depuis Git** : si tu supprimes un Service du dépôt, ArgoCD supprime aussi la ressource du cluster. Sans `prune`, les ressources supprimées de Git restent en production indéfiniment.
- `selfHeal` surveille les **modifications manuelles du cluster** : si tu `kubectl scale` ou edites un pod à la main, ArgoCD détecte la divergence et ré-applique l'état Git. C'est la réconciliation continue.

```bash
# Nettoie d'abord le déploiement manuel du Lab #2
kubectl delete -n demo deployment whoami
kubectl delete -n demo service whoami

# Applique
kubectl apply -f argocd-app.yaml
```

## 📋 Étape 5 — Rollback par revert Git

Modifie `deployment.yaml` en Git : remplace `image: traefik/whoami:v1.10` par `image: nginx:1.27`. Commit + push. ArgoCD redéploie.

Tu n'aimes pas ?

```bash
git revert HEAD
git push
```

→ ArgoCD remet `whoami`. **Ton `git log` est ton historique de production.**

`git revert HEAD` crée un *nouveau* commit qui inverse les changements du dernier commit, sans réécrire l'historique. C'est important : en GitOps, tu ne fais jamais `git reset --hard` en production (ça réécrit l'historique et peut désynchroniser d'autres contributeurs). Le revert est traçable — tu vois dans le log "revert du déploiement nginx".

## 🧠 Pourquoi le pattern app-of-apps

Le pattern app-of-apps résout un problème de bootstrapping : comment déployer tous tes composants ArgoCD depuis Git, y compris ArgoCD lui-même ? La réponse : une Application "root" qui pointe vers un dossier contenant d'autres Applications.

```
homelab-gitops/
├── bootstrap/
│   └── root-app.yaml    ← Application qui pointe vers apps/
└── apps/
    ├── whoami.yaml      ← Application whoami
    ├── monitoring.yaml  ← Application prometheus (lab #4)
    └── falco.yaml       ← Application falco (lab #5)
```

Tu appliques `root-app.yaml` une seule fois → ArgoCD découvre les Applications enfants et les déploie en cascade. Résultat : un cluster vierge peut être entièrement bootstrappé avec un seul `kubectl apply -f bootstrap/root-app.yaml`. On l'utilisera aux Labs #4 et #5.
