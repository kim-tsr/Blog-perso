## 🧠 Théorie : les 3 piliers de l'observabilité

L'observabilité est la capacité à **comprendre l'état interne d'un système depuis ses sorties externes**. En pratique, on distingue trois types de sorties complémentaires, chacune répondant à une question différente.

Les **métriques** (Prometheus) sont des valeurs numériques horodatées : taux de requêtes, latence p99, utilisation CPU. Elles répondent à "combien" et "à quel rythme". Elles sont compactes, indexables, et permettent l'alerting sur des seuils. Leur limite : elles ne disent pas *pourquoi* une valeur a changé.

Les **logs** (Loki) sont des événements textuels : stack traces, requêtes HTTP, messages d'erreur. Ils répondent à "que s'est-il passé exactement". Ils sont verbeux et coûteux à indexer — c'est pourquoi Loki indexe uniquement les labels (app, namespace, pod) et non le texte lui-même. On filtre d'abord par label, puis on grep dans le texte : 10× moins cher qu'ElasticSearch pour 80% des cas Kubernetes.

Les **traces** (Tempo, Jaeger) sont des graphes de causalité entre services : une requête entrante génère N appels internes, chacun avec une durée. Elles répondent à "où ça bloque dans la chaîne". Pour ce homelab, on ne déploie pas Tempo (complexité supplémentaire), mais l'architecture ci-dessous en réserve la place.

## 🧠 Théorie : Prometheus — le modèle pull et les time-series

Prometheus fonctionne en mode **pull** : c'est lui qui interroge les endpoints `/metrics` de tes applications, toutes les X secondes. Ce modèle est contra-intuitif (on pourrait penser que l'app "envoie" ses métriques) mais présente des avantages : Prometheus contrôle le rythme, il détecte immédiatement si une cible est DOWN (pas de réponse), et les targets n'ont pas besoin de connaître l'adresse de Prometheus.

Chaque série temporelle (time-series) est identifiée par un nom de métrique et un ensemble de **labels** : `http_requests_total{method="POST", status="200", service="whoami"}`. Les labels sont la clé de PromQL : tu peux agréger, filtrer, grouper. La règle d'or : garder les labels à faible cardinalité (pas d'IP, pas d'user ID, pas de timestamp dans un label — sinon Prometheus explose en RAM).

## 📋 Étape 1 — Ajouter le stack dans le dépôt Git

Dans ton dépôt `homelab-gitops/`, ajoute :

```
infra/
├── monitoring/
│   ├── namespace.yaml
│   ├── kube-prometheus-stack.yaml   # Application ArgoCD pointant sur Helm chart
│   └── loki-stack.yaml
```

`kube-prometheus-stack.yaml` (Application ArgoCD type Helm) :

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: kube-prometheus-stack
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://prometheus-community.github.io/helm-charts
    chart: kube-prometheus-stack
    targetRevision: 75.6.0   # épingle une version testée ; vérifie la dernière sur artifacthub.io
    helm:
      values: |
        grafana:
          adminPassword: changeme
          service:
            type: NodePort
            nodePort: 30080
        alertmanager:
          service:
            type: NodePort
            nodePort: 30093
        prometheus:
          prometheusSpec:
            retention: 7d
            storageSpec:
              volumeClaimTemplate:
                spec:
                  resources:
                    requests:
                      storage: 10Gi
  destination:
    server: https://kubernetes.default.svc
    namespace: monitoring
  syncPolicy:
    automated: { prune: true, selfHeal: true }
    syncOptions: [ CreateNamespace=true ]
```

Quelques choix dans ces values Helm méritent une explication :

- `type: NodePort` avec `nodePort: 30080` expose Grafana directement sur le port 30080 de chaque node — accessible via `http://192.168.1.20:30080` sans ingress. C'est le compromis homelab : pas de LoadBalancer externe, pas de certificat TLS géré, mais accessible immédiatement. (Pour rappel, la plage NodePort autorisée par défaut est `30000-32767`.)
- On expose aussi Alertmanager sur `30093` : c'est l'UI qu'on consultera au Lab #5 (`http://192.168.1.20:30093`) pour voir arriver les alertes Falco.
- `retention: 7d` limite la rétention Prometheus à 7 jours. Sur un homelab avec 10 Go alloués, c'est le bon équilibre. Prometheus stocke les time-series compressées (~1-3 bytes/sample) mais une semaine de métriques Kubernetes complètes peut atteindre plusieurs Go.
- `volumeClaimTemplate` demande un PersistentVolumeClaim de 10 Gi pour la TSDB Prometheus. Sans ça, les métriques sont dans l'`emptyDir` du pod et disparaissent au restart. k3s fournit la StorageClass `local-path` par défaut, donc le PVC se provisionne tout seul sur le disque du node — pas de configuration de stockage supplémentaire requise.

> 💡 **Versions de charts** : les `targetRevision` épinglés ici sont des versions testées au moment de l'écriture. Les charts Helm évoluent vite ; avant de copier, vérifie la dernière version stable sur [artifacthub.io](https://artifacthub.io) et adapte. Épingler une version exacte (jamais `*` ni `latest`) est une règle GitOps — deux syncs doivent toujours déployer le même bundle.

Commit + push. ArgoCD détecte la nouvelle app au prochain cycle de réconciliation (≤ 3 min, ou immédiatement si tu déclenches un *Refresh* manuel dans l'UI).

## 📋 Étape 3 — Ajouter Loki + Promtail

`loki-stack.yaml` :

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: loki-stack
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://grafana.github.io/helm-charts
    chart: loki-stack
    targetRevision: 2.10.2
    helm:
      values: |
        loki:
          enabled: true
        promtail:
          enabled: true
        grafana:
          enabled: false  # on a déjà la nôtre
  destination:
    server: https://kubernetes.default.svc
    namespace: monitoring
  syncPolicy:
    automated: { prune: true, selfHeal: true }
```

Loki-stack déploie deux composants :

- **Loki** : le backend de stockage et d'indexation des logs. Il ne fait que stocker les chunks compressés et les index de labels — il n'indexe *jamais* le texte brut.
- **Promtail** : le collecteur, déployé en DaemonSet sur chaque node. Il lit les fichiers de logs de tous les pods (`/var/log/pods/...`), ajoute les labels Kubernetes (namespace, pod, container), et envoie à Loki. C'est transparent pour les applications.

`grafana.enabled: false` désactive l'instance Grafana de loki-stack car tu en as déjà une via kube-prometheus-stack. Avoir deux Grafanas sur le même namespace serait une collision de service.

Commit + push.

Dans Grafana → **Connections → Add data source → Loki** → URL `http://loki:3100` → Save & Test.

## 📋 Étape 4 — Scraper les métriques réseau de whoami via Cilium

Le projet `traefik/whoami` n'expose pas d'endpoint `/metrics` applicatif. Plutôt que de modifier l'image, on observe le trafic de whoami depuis le **plan réseau** : Cilium (Lab #2) expose déjà des métriques de flux sur le port `9962` de chaque agent, grâce aux flags `prometheus.enabled` et `hubble.metrics.enabled` activés à l'installation. Il reste à dire à Prometheus de les scraper :

```yaml
# Dans homelab-gitops/apps/whoami/ — servicemonitor-cilium.yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: cilium-agent
  namespace: monitoring
  labels:
    release: kube-prometheus-stack   # ← clé : permet à Prometheus de l'adopter
spec:
  selector:
    matchLabels:
      k8s-app: cilium
  namespaceSelector:
    matchNames: [ kube-system ]
  endpoints:
    - port: prometheus      # port nommé 9962 sur le Service cilium-agent
      interval: 30s
```

Un `ServiceMonitor` est une Custom Resource installée par kube-prometheus-stack. Prometheus Operator surveille tous les ServiceMonitors du cluster et met à jour dynamiquement la configuration de scraping — sans redémarrer Prometheus ni éditer son configmap à la main.

- `labels.release: kube-prometheus-stack` est **indispensable** : par défaut, le Prometheus déployé par ce chart n'adopte que les ServiceMonitors portant le label de sa `release` (le `serviceMonitorSelector`). Sans ce label, ton ServiceMonitor est ignoré silencieusement — c'est l'erreur n°1 des débutants. Vérifie le nom exact avec `kubectl get prometheus -n monitoring -o yaml | grep -A3 serviceMonitorSelector`.
- `selector.matchLabels: {k8s-app: cilium}` pointe vers le Service `cilium-agent` exposé dans `kube-system`.
- `namespaceSelector` autorise Prometheus à scraper hors de son propre namespace.
- `port: prometheus` est le **nom** du port (9962) tel que défini sur le Service Cilium — on référence par nom, pas par numéro, pour rester robuste si le port change.

> 💡 Plus simple en pratique : Cilium sait créer ce ServiceMonitor lui-même si tu installes avec `--set prometheus.serviceMonitor.enabled=true`. On le fait ici à la main pour comprendre le mécanisme.

## 📋 Étape 5 — Dashboard custom

Dans Grafana → **Dashboards → New → Import → JSON** :

```json
{
  "title": "Whoami — Homelab",
  "panels": [
    {
      "type": "stat",
      "title": "Replicas",
      "targets": [{
        "expr": "kube_deployment_status_replicas{deployment=\"whoami\",namespace=\"demo\"}"
      }]
    },
    {
      "type": "timeseries",
      "title": "Réseau in/out (bytes/s)",
      "targets": [{
        "expr": "sum(rate(cilium_forward_bytes_total{}[1m]))"
      }]
    }
  ]
}
```

Les deux requêtes PromQL illustrent deux patterns différents :

- `kube_deployment_status_replicas{...}` est une **gauge** (valeur instantanée) exposée par kube-state-metrics. Pas de `rate()` — tu veux la valeur actuelle, pas un taux.
- `sum(rate(cilium_forward_bytes_total{}[1m]))` calcule le **taux d'octets** (bytes/seconde) en lissant sur une fenêtre glissante de 1 minute. `cilium_forward_bytes_total` est un **counter** (toujours croissant) — `rate()` est obligatoire pour extraire une valeur utile. `sum()` agrège tous les labels (tous les pods, toutes les directions).

## 📋 Étape 6 — Première alerte

Crée une **PrometheusRule** qui alerte si whoami a moins d'1 replica disponible :

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: whoami-availability
  namespace: monitoring
spec:
  groups:
    - name: whoami
      rules:
        - alert: WhoamiDown
          expr: kube_deployment_status_replicas_available{deployment="whoami"} < 1
          for: 1m
          labels: { severity: critical }
          annotations:
            summary: "whoami n'a aucune replica dispo"
```

`for: 1m` est capital : l'alerte ne passe en "firing" qu'après **1 minute continue** où la condition est vraie. Sans ce délai, un restart de pod (quelques secondes à 0 replica) déclencherait immédiatement une alerte critique — un bruit insupportable. En prod SRE, on dit "burn rate" : l'alerte doit représenter un problème réel, pas un événement transitoire normal.

`labels: { severity: critical }` est ce qu'Alertmanager utilisera pour router : tu peux configurer une route `severity=critical → PagerDuty` et `severity=warning → Slack` sans modifier la règle elle-même.

Test : `kubectl scale -n demo deploy whoami --replicas=0` → après 1 min, l'alerte passe firing dans Alertmanager.

> ⚠️ **Attention au self-heal ArgoCD** : whoami est désormais géré par ArgoCD (Lab #3) avec `selfHeal: true`. Ton `scale --replicas=0` sera annulé sous ~3 min, ce qui résout l'alerte tout seul. C'est exactement le comportement attendu — mais pour un test propre, fais le scale juste après avoir lancé la commande et observe la fenêtre avant que ArgoCD ne recolle, ou suspends temporairement l'app dans l'UI ArgoCD.
